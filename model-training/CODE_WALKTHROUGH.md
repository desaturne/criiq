# model-training — Code Walkthrough

This is a file-by-file explanation of every module in `model-training/`, what it does, and how it works internally. It complements `README.md` (setup/usage) and `ALGORITHMS.md` (the math/modeling concepts explained on their own terms) — this document walks the actual *code structure*: what each function computes, why it's built the way it is, and how the files connect.

`model-training` never writes to the database `data-collection` builds (`db.py` opens it in SQLite's read-only URI mode, enforced at the driver level, not just by convention) — it only reads from `criiq.db` and layers three things on top:

1. **Feature engineering** (`features/`) — turning raw per-match stats into a leakage-safe training table (`historical.py`) and an equivalent live-scoring feature vector (`current.py`), sharing one canonical column schema (`schema.py`) so a model trained on one validly scores inputs from the other.
2. **The recommendation engine** (`recommend/`, `selection/`) — a composite, explainable scoring formula (`score.py`) blending a trained WPA regressor with rule-based adjustments (matchup history, phase fit, risk, strike-rate penalty), narrated in plain English (`explain.py`), and turned into an actual constrained Playing XI via an optimizer (`selection/optimize.py`).
3. **The match simulator** (`simulate/`) — a ball-by-ball Monte Carlo engine (`engine.py`) plus two genetic-algorithm optimizers (`ga_batting.py`, `ga_bowling.py`) that search for the best batting order / bowling rotation subject to cricket's actual legal constraints (max 4 overs per bowler, no consecutive overs, etc).

`cli.py` is the single entry point tying all of this together as one `argparse` program; `tests/` (covered in its own section at the end) exercises nearly all of it.

## How the two main flows actually connect, end to end

The sections below document every file individually, each ending in its own "How it connects" pointer — but stitching two dozen of those together to see a full request's path takes work. Here's that path traced up front, for the two things a coach actually triggers:

**Building a recommended XI** (`cli.py`'s `cmd_recommend`, or the backend's `recommend` subprocess call):
1. `roster.team_pool` — the real, eligibility-filtered, point-in-time-safe candidate pool for a team (excludes retired/`UNKNOWN`/inactive players, with a dormant-associate-team fallback).
2. `RecommendationScorer.__init__` — loads the persisted models (`recommend.train.load_models`/`load_metadata`), optionally told which team it's scoring *for* (`team=`) so opponent-strength can use real head-to-head history.
3. `score_many` → per-player `score()` — `model_part` (the trained WPA regressors, or a shrinkage fallback for cold-start players) `+ matchup_part + phase_fit_part + standing_part + risk_part + strike_rate_part + opponent_strength_part`, then a pool-wide synergy bonus (`team_need_part`) added across everyone at once.
4. `selection.optimize.select_xi` — the MILP that actually picks the constrained 11 from the *entire* scored pool, not a pre-truncated shortlist.
5. `selection.optimize.role_highlights` / `best_fielder` — specialist call-outs (best finisher/power-hitter/anchor/fielder) computed independently of who made the constrained XI, since the composite score can bury a genuine specialist.
6. `recommend.explain.explain` (opt-in) — turns one player's `components` dict into coach-facing sentences, including named-XI head-to-head lines and a fielding callout threaded in from steps 4-5.
7. `recommend.shap_explain.explain_prediction` (opt-in, `--shap`) — a mathematically exact per-feature attribution of the WPA prediction itself, a different and more rigorous question than `explain()`'s narrative.
8. `recommend.render.render_team_sheet` / structured JSON — the final presentation layer.

**Simulating a match** (`cli.py`'s `cmd_simulate`, or the two GA optimizer subcommands):
1. `simulate.outcomes.build_outcome_model` + `build_player_profiles` — the empirical, matchup-adjusted per-ball outcome distribution and every player's batting/bowling profile for this specific pairing.
2. `simulate.engine.simulate_match` → `simulate_innings` → `simulate_ball`/`select_bowler` — the actual ball-by-ball Monte Carlo loop, one legal delivery at a time, repeated `n_reps` times.
3. `simulate.keymoments.detect_key_moments`, `simulate.scorecard.py`, `simulate.report.py` — post-processing a representative rep (or aggregating across all reps) into a human-readable result.
4. `simulate.ga_bowling.optimize_bowling_rotation` / `simulate.ga_batting.optimize_batting_order` are alternative *front ends* onto step 2 — each genetic algorithm's fitness function is "run `simulate_innings` and see what happens," repeated across generations, not a separate simulation mechanism.
5. `simulate.lineup_explain.explain_bowling_rotation` / `explain_batting_order` (opt-in, `--explain`) — baseline comparison and sensitivity testing on top of whichever GA ran.

### `model-training/criiq_models/cli.py`

**Purpose:** This is the entire command-line surface of `model-training` — a single argparse program (`criiq_models`) with one subcommand per pipeline stage: building features, training models, backtesting, recommending an XI, explaining a score, analyzing a coach's own XI, simulating a match, and running genetic-algorithm optimizers for batting order / bowling rotation. It is the "glue" layer: it never contains modeling logic itself, only orchestrates calls into `features/`, `evaluate/`, `recommend/`, `selection/`, and `simulate/`, and formats their outputs as JSON or human-readable text. `main()` is the actual entry point invoked when the package is run as `python -m criiq_models ...` or via its console script.

**Key pieces:**

Helper/utility functions (used across multiple subcommands):
- `_pp(obj)` — pretty-prints any object as indented JSON (`default=str` so things like `Path`/`Timestamp` fall back to their string form).
- `_find_player(conn, name)` — fuzzy `LIKE '%name%'` search against `canonical_name` or `unique_name`, capped at 10 rows.
- `_resolve_venue_arg(conn, venue_arg)` — turns a user-typed ground name into a `venue_id` via `venues.resolve_venue`; if the name is ambiguous, prints all candidate grounds and returns `ok=False` so the caller aborts instead of silently scoring with `venue_id=None`.
- `_resolve_player_name(conn, name)` — same ambiguity-handling pattern for a single player name: 0 matches → error, >1 matches → print "did you mean" list and abort, exactly 1 → return its `player_id`.
- `_resolve_player_list(conn, players, player_ids)` — resolves a comma-separated `--players` (fuzzy names) or `--player-ids` (raw ids) argument into a list of ids, reusing `_resolve_player_name` per name so any one ambiguous name aborts the whole list.
- `_resolve_xi(conn, players_arg, player_ids_arg, label)` — like `_resolve_player_list` but requires **exactly 11** resolved ids (used by `simulate`/`optimize-*`, which need a literal, complete Playing XI in batting order).
- `_batting_groups(conn, player_ids, fmt)` — splits an XI into three role bands for the batting-order GA: the two players with the lowest `batting_position_median` become the "openers" band, the rest split into "top/middle" (batting-capable) vs "tail" (`role_bucket == "bowler"`). Missing position data sorts to `+inf` so the opener cut still always yields exactly 2 names.
- `_primary_bowlers(conn, bowler_pool, fmt)` — the up to 5 recognized specialist bowlers (`role_bucket == "bowler"`); if fewer than 5 exist, tops up with all-rounders ranked by real bowling workload (`COUNT(*)` of `player_match_impact` rows with `balls_bowled>0`), mirroring a captain short on frontline options.
- `_bowling_pool(conn, xi_ids, fmt)` — filters an XI down to bowling-capable players (`bowling_capable(role_bucket)`).
- `_name_map(conn, player_ids)` — id → `canonical_name` lookup dict, falling back to the raw id if no name is found.
- `_parse_force_dismissal(conn, spec)` — parses a `"NAME_OR_ID:OVER:BALL"` string (rsplit on `:` so names with colons aren't an issue) into `{player_id, over, ball}` for the simulator's "what if she got out here" scenario.

Subcommand implementations (`cmd_*`, each opens its own `sqlite3` connection via `db.connect()` and closes it before returning):
- `cmd_features` — calls `features.historical.build_training_table` and prints the row count + date range (a sanity-check command, not used in the actual training pipeline itself).
- `cmd_train` — calls `recommend.train.train`, pretty-prints the returned metadata (this is what actually fits and persists the WPA regressors). With `--background-only`, skips fitting entirely and instead calls `recommend.train.rebuild_background` — for regenerating just the SHAP background sample on an already-trained scope (e.g. artifact sets saved before that file existed).
- `cmd_backtest` — calls `evaluate.backtest.backtest`, prints the temporal-holdout report.
- `cmd_rank_backtest` — calls `evaluate.rank_backtest.rank_backtest`, prints the ranker-vs-regression comparison.
- `cmd_teams` — lists known team names via `roster.known_teams`.
- `cmd_winprob` — loads the persisted empirical win-probability grid (`WinProbLookup`) for a given format/gender and looks up a single game state (innings, wickets, balls remaining, runs required/score), also deriving a `phase` label (powerplay/middle/death) from balls bowled so far.
- `cmd_recommend` — the core "pick an XI" flow: resolves venue and opponent-XI args, gets the team's eligible pool (`roster.team_pool`), builds `RecommendationScorer(conn, args.format, args.gender, team=args.team)` (passing the coach's own team so `_opponent_strength_part` can use real head-to-head history) and scores every pool player with `score_many`, then runs `select_xi` (a constrained optimizer) to get the actual XI. Also computes: per-archetype "role highlights" (best finisher/power-hitter/anchor across the whole pool, via `role_highlights`), a "fielder" highlight (`best_fielder(scored)`, the pool's strongest fielding record, surfaced the same way as a role archetype but never fed into the composite score), a head-to-head matrix against the named opponent XI (`head_to_head_matrix`, only if opponent players were given), and a "lopsided matchup" check (`strength_context`) — if this team is much stronger (ICC-rank gap ≥ `lopsided_icc_gap`), it builds an alternate "rotation XI" that rests the top `rotation_rest_count` scorers so the coach has a viable weaker lineup to field. With `--explain`/`--pretty`, attaches `explain()`'s plain-language reasoning per player — threading through `h2h_batting`/`h2h_bowling` (the per-player slice of the head-to-head matrix against the *named* opponent XI) and `is_best_fielder` (whether this player is the `best_fielder` result) for both the selected XI and the wider pool, not just a "best alternative" per slot (the top-scoring not-selected player in the same `slot_category`). `--pretty` renders a text team sheet via `render_team_sheet`; otherwise it prints structured JSON including a `pools` view (`role_pools`) grouping the shortlist into batting/all-rounder/bowling buckets for a UI's "pick your XI" screen.
- `cmd_explain` — scores a single named/id'd player against an opponent (and optional venue) and prints `explain()`'s full component breakdown.
- `cmd_analyze_xi` — scores a coach's own hand-picked 11 (not the algorithm's optimal pick) against the same constraints `recommend` enforces, via `analyze_xi`; reports total/average score, constraint violations, and a comparison to the provably-optimal XI. Resolves any "missing" player ids (named in the pool but not actually found) to real names for a useful warning message.
- `cmd_simulate` — the ball-by-ball Monte Carlo match simulator entry point. Resolves both literal XIs (must be exactly 11 each, in batting order), builds each side's bowling pool and warns if fewer than 5 bowling-capable players exist (can't legally complete 20 overs under the 4-overs-max rule), builds the `outcome_model` (ball-outcome probabilities from `simulate.outcomes.build_outcome_model`) and loads the win-probability lookup grid, builds per-player batting/bowling profiles (`build_player_profiles`), then calls `simulate.engine.simulate_match` for `n_simulations` Monte Carlo reps. Post-processes: detects "key moments" from the representative rep's ball log, builds batting/bowling scorecards and bowling-rotation summaries for both innings, optionally re-runs the whole simulation with a forced dismissal scenario, and either dumps one big JSON blob (`--json`) or prints a full human-readable report (score lines, coach's-perspective narrative, scorecards, bowling rotation, and a saved win-probability chart + artifact files via `plot_win_probability`/`save_simulation_artifacts`).
- `cmd_optimize_bowling` — resolves both XIs, checks the bowling side has ≥5 bowling-capable players, builds the outcome model + player profiles, then runs `ga_bowling.optimize_bowling_rotation` (a genetic algorithm over legal over-by-over bowler assignments) — by default constrained so the up to 5 recognized specialists take the full quota (`--no-primary-bowlers` disables this). Prints or JSON-dumps the resulting over-by-over rotation and expected runs conceded, and always writes `bowling_rotation.json` to `--out-dir`.
- `cmd_optimize_batting` — mirror of the above for batting order: runs `ga_batting.optimize_batting_order` over role-banded groups (openers/top-middle/tail) by default, optimizing either expected score or (with `--target`) win probability of chasing a specific total. Writes `batting_order.json`.

`build_parser()` wires up an `argparse.ArgumentParser` with `prog="criiq_models"` and one required subparser per command listed above (`features`, `train`, `backtest`, `rank-backtest`, `teams`, `recommend`, `explain`, `analyze-xi`, `simulate`, `optimize-bowling`, `optimize-batting`, `winprob`). Every subcommand takes `--format`/`--gender` defaulting to `SETTINGS.format`/`SETTINGS.gender`. Commands needing a full 11-player side accept both a `--X-players` (comma-separated fuzzy names) and `--X-player-ids` (raw ids) variant. Simulation/optimization commands share `--venue`, `--seed` (omitted by default for genuine randomness — a fixed value is only for reproducing an exact run), `--pop-size`/`--generations` (GA controls), and `--json` (machine-readable output, skipping any file/chart artifacts). Each subparser's `set_defaults(func=cmd_*)` is what makes `main()`'s single `args.func(args)` call dispatch to the right handler. `main(argv=None)` just parses and dispatches; the `if __name__ == "__main__":` guard lets the file be run directly as a script.

**Explainability flags, added since this section was first written:**
- `recommend --shap` and `explain --shap` (both implemented via `recommend/shap_explain.py`'s `explain_prediction`) attach a per-player SHAP feature-contribution breakdown to the WPA prediction — `recommend`'s loads one shared background sample (`load_background`) and attaches `shap` to every XI/pool player's entry via the local `_shap_entry` closure; `explain` attaches it once to the single requested player. `--shap` implies `--explain`/the detailed per-player loop in both cases; `--pretty`'s rendering (`render_player_explanation`) also accepts the SHAP result if present.
- `optimize-batting --explain` and `optimize-bowling --explain` (implemented via `simulate/lineup_explain.py`'s `explain_batting_order`/`explain_bowling_rotation`) attach a naive-baseline comparison, adjacent-swap sensitivity check, and (batting only) a contingency plan to the GA's result — see that module's own section below for the mechanics.

There's also a startup block (module top, lines 18-22) that reconfigures `sys.stdout`/`sys.stderr` to UTF-8 — guarding for older Python or embedding contexts where `.reconfigure` doesn't exist — because Windows consoles default to legacy codepages that mangle the em dashes used throughout `explain.py`'s narrative text.

**How it connects:** Imports from nearly every subpackage: `config`, `db`, `evaluate.backtest`/`rank_backtest`, `features.historical`, `recommend.explain`/`matchup_matrix`/`render`/`score`/`strength`/`train`, `roster`, `venues`, `selection.optimize`, `features.common`/`current`, and the whole `simulate` package. Nothing imports `cli.py` back — it's the leaf/entry-point of the dependency graph.

### `model-training/criiq_models/config.py`

**Purpose:** Single source of truth for every tunable constant used across training, scoring, and selection — thresholds, weights, window sizes, and file-system paths. Centralizing these means every module (`features/*`, `recommend/*`, `selection/*`, `cli.py`) reads the same `SETTINGS` singleton instead of hardcoding magic numbers, so a tuning change only happens in one place.

**Key pieces:**
- Path constants: `PACKAGE_DIR`/`ROOT_DIR` derived from `__file__`; `DEFAULT_DB` points at `data-collection/data/criiq.db` (the DB is built and owned by the sibling `data-collection` package — `model-training` only reads it, never writes). `DB_PATH` is overridable via the `CRIIQ_DB` env var. `ARTIFACTS_DIR`/`RECOMMENDATION_ARTIFACTS_DIR` (overridable via `CRIIQ_MODEL_ARTIFACTS`) are where trained models and recommendation artifacts get persisted.
- `DEFAULT_FORMAT = "T20"`, `DEFAULT_GENDER = "female"` — parametrized defaults, not hardcoded assumptions; women's T20I is just what the whole pipeline defaults to when a caller doesn't specify.
- `Settings` (a frozen dataclass, so it's immutable/hashable) holds every tunable, each documented inline with *why* it has that value:
  - `min_matches_for_model = 10` — below this many career matches, skip the learned model entirely and fall back to rule-based scoring (a cold-start gate).
  - `form_window_matches = 15`, `form_recency_lambda = 0.9` — the rolling-form window size and per-step geometric decay used by `recency_weighted_mean`.
  - `shrinkage_prior_matches = 8` — the "prior strength" `k` in the Bayesian shrinkage formula used throughout `features/common.py`.
  - `secondary_discipline_weight = 0.4` — an all-rounder's weaker discipline counts at 40% weight, so a merely-decent all-rounder can't structurally outscore a pure specialist.
  - `wpa_scale = 450.0` — rescales tiny raw WPA values (median ~0, 99th percentile ~+0.086) into the composite score's points scale, calibrated so an elite average WPA (~0.09) lands near the model-driven score cap (45) without maxing it out.
  - `opponent_form_matches = 20`, `opponent_strength_cap_weak = 30.0`/`opponent_strength_scale_weak = 1.2`, `opponent_strength_cap_strong = 20.0`/`opponent_strength_scale_strong = 0.4` — feed `recommend/score.py`'s `opponent_strength_part`: how many recent matches the opponent's win-rate is computed over, and the asymmetric cap/scale applied below vs. at-or-above a 50% opponent win rate (a weaker opponent gets a steeper, wider-capped bonus; a stronger one a gentler, narrower-capped penalty).
  - `sr_penalty_cap = 6.0`, `sr_penalty_scale = 20.0`, `experience_full_matches = 50` — parameters for `recommend/score.py`'s strike-rate soft penalty: below-par career SR is docked, but the deduction is bounded and discounted by an experience/game-awareness factor that saturates at 50 matches.
  - `opener_position_threshold = 2.5`, `min_openers = 2` — a player counts as "opener-capable" if her median batting position is ≤ 2.5; the XI selection must include at least 2 such players.
  - `excluded_statuses = ("RETIRED_ALL", "RETIRED_FORMAT")`, `inactive_status = "INACTIVE"`, `unknown_status = "UNKNOWN"` — eligibility gating used by `roster.team_pool`. The inline comment is explicit that `RETIRED_*` only ever comes from data-collection's manual override CSV, which is normally empty — so in practice it matches nothing, and `UNKNOWN` (no international appearance for 540-1095 days) is what actually does the real-world work of excluding recently-retired players; see `roster.py`'s section for the concrete case this was built to fix.
  - `finisher_low_impact_threshold = 5.0` — the `model_part` cutoff below which `recommend/explain.py` adds its "WPA can undervalue a genuine finisher" caveat for a `finisher`/`power hitter` archetype.
  - `xi_size=11`, `min_batting_capable=5`, `min_bowling_capable=5`, `min_keepers=1`, `pool_size=20` — hard constraints for the constrained XI-selection optimizer.
  - `lopsided_icc_gap = 3`, `rotation_rest_count = 4` — used by `recommend/strength.py` to flag a mismatch (this team has ≥3 more ICC-ranked players than the opponent) and to decide how many top performers to rest in the rotation XI.
  - `backtest_test_fraction = 0.2` — the fraction of matches (by date, not row) held out for `evaluate/backtest.py`.
  - `random_state = 42` — the fixed seed for reproducible model training.
  - `domestic_form_max_effective_matches = 10` — caps the sample size fed into shrinking domestic-league form toward the international career prior, so domestic volume can never fully outweigh the international record; explicitly noted as a placeholder pending a real grid-search once domestic data volume grows.
  - `shap_background_size` / `shap_top_features = 8` *(new)* — how many training rows `train.py` samples into the persisted SHAP background set (`recommend/shap_explain.py`'s permutation explainer needs a background distribution for the non-tree-path sub-estimator), and how many top-magnitude feature contributions `explain_prediction` surfaces per prediction instead of returning the full feature list every time.
- `SETTINGS = Settings()` — the module-level singleton every other file imports.
- `ensure_dirs()` — creates the artifacts directories if missing.

**How it connects:** Imported by essentially every other file in the package (`db.py`, `roster.py`, `features/*`, `evaluate/*`, `cli.py`, and the `recommend`/`selection`/`simulate` packages not covered in this batch) via `from .config import SETTINGS` or `from ..config import SETTINGS`. It imports nothing from within the package itself — it's a leaf dependency.

### `model-training/criiq_models/db.py`

**Purpose:** The single chokepoint for opening the SQLite database that `data-collection` builds. Its whole job is to guarantee every consumer in `model-training` gets a **read-only** connection, since this package must never mutate the data-collection-owned database.

**Key pieces:**
- `connect(db_path=None)` — resolves the path (falling back to `config.DB_PATH`), raises a clear `FileNotFoundError` with an actionable message if the DB doesn't exist yet (telling the user to run `data-collection`'s pipeline or set `CRIIQ_DB`). It then opens the connection via SQLite's URI form `file:{path}?mode=ro` with `uri=True` — this is what actually enforces read-only access at the SQLite driver level, not just by convention. Sets `conn.row_factory = sqlite3.Row` so query results support both index and dict-style (`row["col"]`) access, which is used pervasively throughout the codebase (e.g. `row["primary_role"]`).

**How it connects:** `connect()` is called at the top of essentially every `cmd_*` function in `cli.py`, and imported wherever a fresh connection is needed outside the CLI flow (tests, `evaluate/*` when invoked directly). It imports only `config.DB_PATH`.

### `model-training/criiq_models/evaluate/backtest.py`

**Purpose:** Temporal-holdout evaluation of the two contribution regressors (`batting_wpa`, `bowling_wpa`) that `recommend/train.py` fits. This is the honesty check on model quality: it retrains fresh copies of the same regressors on a train/test split by **match date** (never by row), so it estimates real-world generalization rather than in-sample fit. It's invoked via `cli.py`'s `backtest` subcommand.

**Key pieces:**
- `_top_quartile_hit_rate(df, target)` — for each held-out match (grouped by `match_id`, skipping matches with <4 players), computes whether the model's top-25%-by-prediction among players who actually played overlaps with the top-25%-by-actual-value. Returns the mean overlap fraction across matches, or `None` if no match qualified. This is explicitly documented as a *modest* proxy for selection quality — it does not attempt to reconstruct "would the model have picked this XI from the full squad", since bench-player features for historical matches aren't cleanly available; it only checks whether the model spots standout performers among those who played.
- `backtest(conn, fmt, gender)`:
  1. Builds the full leakage-safe training table via `features.historical.build_training_table`.
  2. Splits by date: `cutoff = dates.quantile(1 - backtest_test_fraction)` (default 0.2, so the most recent ~20% of matches by date become the test set) — `train_df` is everything strictly before the cutoff, `test_df` on/after.
  3. For each target in `TARGETS` (`batting_wpa`, `bowling_wpa`): drops NaN rows for that target from train/test; skips (with a `"note"`) if fewer than 50 training rows or an empty test set.
  4. Fits a **fresh** model via `recommend.train._make_model(target)`, training on `MODEL_FEATURES` against the **clipped** target (`_clip_target`, same clipping production training uses) — but scores predictions against the **raw, unclipped** actual test values, so the reported error reflects real-world performance honestly rather than the training-time transformation.
  5. Computes MAE, a baseline MAE (mean-predictor: `|actual - train_mean|`), Pearson correlation between prediction and actual, and the top-quartile hit rate above.
- Returns a dict with `cutoff_date`, row counts, and a per-target sub-dict of these metrics.

**How it connects:** Imports `config.SETTINGS`, `features.historical.build_training_table`, `features.schema.MODEL_FEATURES`/`TARGETS`, and `recommend.train._clip_target`/`_make_model` (reaching into recommend's private helpers to guarantee it evaluates the *exact same* modeling procedure production training uses). Called only from `cli.py`'s `cmd_backtest`.

### `model-training/criiq_models/evaluate/rank_backtest.py`

**Purpose:** Answers an empirical question: is a dedicated learning-to-rank model worth adding on top of the existing pointwise WPA regressors, or does simply ranking players by the sum of the two regressors' predictions already rank well enough? The recommendation engine's actual job is *ranking* ("who's most valuable to pick"), not regression, so this module fits an `LGBMRanker` on the same temporal holdout `evaluate/backtest.py` uses and compares its ranking quality against the regression-based baseline `select_xi` currently uses. Invoked via `cli.py`'s `rank-backtest` subcommand.

**Key pieces:**
- `_combined_label(df)` — `batting_wpa.fillna(0) + bowling_wpa.fillna(0)`, the ranking target: total match value.
- `_graded_relevance(label, n_grades=5)` — LightGBM's `lambdarank` objective needs small non-negative integer relevance grades, not raw continuous values. Bins the combined-WPA label into quantile grades via `pd.qcut(..., duplicates="drop")` (dropping duplicate bin edges handles the large mass of exact zeros — e.g. players uninvolved in bowling — collapsing several quantile cut points together), then fills any resulting NaN grade with 0.
- `_group_sizes(df)` — per-`match_id` group sizes, the "query group" structure `lambdarank` needs (it ranks within each match, treating both teams' players combined as one group).
- `_top_k_hit_rate(df, score_col, label_col, k=11)` — per match (skipping matches with fewer than `k` rows), overlap fraction between the actual top-11-by-label and the predicted top-11-by-score — literally, "does it pick the right people."
- `_mean_spearman(df, score_col, label_col)` — per-match Spearman rank correlation between predicted and actual order (skipping matches with <3 rows or a constant label), averaged across matches. Chosen over NDCG because NDCG's standard `2^relevance - 1` gain formula doesn't behave sensibly for a continuous, frequently-negative quantity like WPA.
- `rank_backtest(conn, fmt, gender)`:
  1. Builds the training table, drops rows with both `batting_wpa` and `bowling_wpa` missing, computes the combined `label`.
  2. Splits by date the same way as `backtest.py` (cutoff at the `1 - backtest_test_fraction` quantile); aborts with a `"note"` if train has <200 rows or test has <50.
  3. Fits `LGBMRanker(objective="lambdarank", n_estimators=300, max_depth=6, learning_rate=0.05, random_state=SETTINGS.random_state)` on the graded training labels grouped by match.
  4. Scores the test set with the ranker, reporting `top_11_hit_rate` and `spearman`.
  5. Also loads the currently-persisted regression models (`recommend.train.load_models`) and, if both `batting_wpa`/`bowling_wpa` models exist, computes the same two metrics for their combined prediction as a `regression_baseline` — or notes that no persisted regressors exist yet if `train` hasn't been run.
- The module's docstring makes clear the decision rule: `select_xi`'s objective only switches from the composite score to a ranker's output if this comparison shows a *meaningful* improvement (decision reported via `cli.py`'s docstring, not automated in code).

**How it connects:** Imports `config.SETTINGS`, `features.historical.build_training_table`, `features.schema.MODEL_FEATURES`, and (lazily, inside the function) `recommend.train.load_models`. Depends on `lightgbm.LGBMRanker` and `scipy.stats.spearmanr`. Called only from `cli.py`'s `cmd_rank_backtest`.

### `model-training/criiq_models/features/common.py`

**Purpose:** Shared statistical building blocks — Bayesian shrinkage toward a prior, and recency-weighted averaging — used by both the training-time feature builder (`historical.py`) and the live-scoring feature builder (`current.py`), so small-sample stats (like "record vs this specific opponent" with 2 matches) don't produce wild, overconfident numbers. Explicitly mirrors the shrinkage/recency ideas already used in `data-collection` (`min_innings_bayesian`, `rfi_lambda`).

**Key pieces:**
- `shrink(observed, n, prior, prior_strength=SETTINGS.shrinkage_prior_matches)` — the scalar shrinkage formula: `shrunk = (n * observed + k * prior) / (n + k)`, where `k` (default 8, from `SETTINGS.shrinkage_prior_matches`) represents "matches of prior strength" the raw observation is blended against. If `observed`/`n` is missing (None, ≤0, or NaN), falls back to `prior`; if `prior` is missing, falls back to `observed` — i.e. it degrades gracefully instead of erroring when either side is absent.
- `shrink_series(observed, n, prior, prior_strength=...)` — the vectorized (pandas Series) version used when building the whole training table at once. Coerces to numeric via `pd.to_numeric(errors="coerce")`, computes the same weighted-blend formula, guards division by zero (`denom.where(denom != 0, np.nan)`), and falls back element-wise to `prior` wherever `observed` is NaN. The key design point (stated in the docstring): shrinking toward the career prior keeps the feature *continuous* as `n → 0` — there's no cliff between "no data" (n=0, which just returns the prior) and "one noisy match" (n=1, mostly prior + a little signal).
- `recency_weighted_mean(values, order, decay=SETTINGS.form_recency_lambda)` — weights `values` (ordered ascending by `order`, oldest first) so the *most recent* value gets weight 1.0 and each step further back multiplies by `decay` (default 0.9): weight = `decay ** steps_back`. Uses `order.rank(method="first")` to get a stable positional index even if `order` has ties, masks out NaN values before weighting, and returns `None` if there's no valid data or the total weight is ≤0.
- `safe_div(numer, denom)` — simple division guard: returns `None` if `denom` is `None`, `0`, or NaN, else `numer/denom`.
- `role_bucket(role)` — normalizes the free-text `role` field down to one of `{"batter", "bowler", "all-rounder"}`, or `"unknown"` for anything else (catches noisy Wikidata values like "goalkeeper").
- `batting_capable(bucket)` / `bowling_capable(bucket)` — simple membership checks (`batter`/`all-rounder` are batting-capable; `bowler`/`all-rounder` are bowling-capable).

**How it connects:** Imported by `features/historical.py` (`role_bucket`, `shrink_series`), `features/current.py` (`recency_weighted_mean`, `role_bucket`, `shrink`), `features/style_matchup.py` (`shrink`), and `cli.py` (`bowling_capable`). Imports only `config.SETTINGS`.

### `model-training/criiq_models/features/current.py`

**Purpose:** Builds the live-scoring feature vector for one player "as of right now" — the exact same `MODEL_FEATURES` shape `historical.py` produces for training rows, but with no leakage concern: since the match being scored genuinely hasn't happened, using a player's *entire* history up to today is correct (unlike `historical.py`, which must restrict to "before this training row's date" to avoid leaking the future into the label). It also builds `ExtraContext` — everything `recommend/score.py` needs for the parts of the composite score that are *not* part of the trained model (opponent-specific matchups, phase profile, venue history, eligibility/risk flags, descriptive batting profile).

**Key pieces:**
- `resolve_role(conn, player_id, fmt)` → `(role_bucket, is_keeper, batting_position_median)`. Prefers the data-driven `player_role_final` table (built from batting position + ball-count workload, refined via Wikipedia-sourced keeper/role lookups in data-collection's `role_finalize.py`); falls back to the noisier `player_registry.role` only if a player has no `player_role_final` row at all. `batting_position_median` has no fallback — it's simply `None` if `player_role_final` hasn't been rebuilt since the player's matches were ingested.
- `_player_match_history(conn, player_id, fmt)` — pulls the full per-match history from `player_match_impact` joined to `matches` (for `venue_id`) and left-joined to `player_match_wpa` (for `batting_wpa`/`bowling_wpa`), ordered by date. Derives `wickets_when_bowled = wickets.where(balls_bowled > 0)` because `wickets` is stored as 0 (not NULL) even in matches she didn't bowl at all — masking avoids diluting the wicket-taking signal with non-bowling matches.
- `build_model_features(conn, player_id, opponent, venue_id, fmt)` — the main feature-vector builder. Step by step:
  1. Initializes every key in `MODEL_FEATURES` to `None`, sets `career_matches = len(hist)`.
  2. Computes `age_years` from `players.date_of_birth` if available (an objective fact with no leakage risk — computed even for a debutant); coverage is only ~36% of players.
  3. If history is empty, still resolves `role_bucket` and returns early (a debutant still needs a role).
  4. Otherwise computes plain career means: `career_bat_contribution_pct`, `career_bowl_contribution_pct`, `career_bat_sr`, `career_bowl_economy`, `career_batting_wpa`, `career_bowling_wpa`, `career_bowl_wickets_per_match` (mean of the masked `wickets_when_bowled`).
  5. Computes descriptive-only extras not in `MODEL_FEATURES` (`career_bowl_dot_pct`, `career_bowl_boundary_pct`) — noted as *tried* as model inputs but rejected because they made the bowling-WPA holdout correlation worse (0.103 → as low as 0.088); kept only for `explain.py`'s plain-language narrative, which carries no prediction risk.
  6. Computes discipline-specific sample sizes (`career_bat_matches`, `career_bowl_matches`, `career_batting_wpa_matches`, `career_bowling_wpa_matches`) — used by `score.py` to shrink contribution/WPA toward a prior with the *correct* denominator (e.g. a specialist bowler with 100 career matches but only 3 batting innings should shrink hard on the batting side specifically).
  7. Computes recency-weighted "form" features over the last `SETTINGS.form_window_matches` (15) matches via `recency_weighted_mean`, mirroring the career features but recency-biased.
  8. Computes vs-opponent stats (`vs_opp_matches`, shrunk `vs_opp_bat_contribution_pct`/`vs_opp_bowl_contribution_pct` via `shrink()` toward the career mean, plus `vs_opp_win_pct`) and vs-venue stats similarly, shrunk toward career baseline. The docstring notes `shrink()` with `n=0` simply returns the career prior — this keeps "no venue specified" behaving in-distribution with what training rows see as venue-match-count approaches 0 (confirmed via a specific sanity check — "Mandhana-vs-Hemalatha" — that an abrupt cliff otherwise produces unstable predictions).
  9. Reads `player_domestic_form` (already precomputed "as of last refresh" by data-collection, so no leakage-safety reconstruction needed here unlike `historical.py`), caps the sample size at `SETTINGS.domestic_form_max_effective_matches` (10) before shrinking `batting_wpa_per_match`/`bowling_wpa_per_match` toward the international career WPA.
  10. Resolves `role_bucket` last and returns the completed `row` dict.
- `ExtraContext` — a dataclass holding everything used by `score.py`/`explain.py` but *not* fed to the trained model: name, role/keeper/position, batting and bowling matchup stats vs the opponent, phase profile, importance/win/POTM/ICC-rank, retirement/eligibility flags, venue-specific setting/chasing stats and "bogey bowler," archetype, batting hand/bowling style, a descriptive batting profile (strike rate, boundary%, dot%, sixes, best phase), and game-awareness signals (`setting_strike_rate`, `chasing_strike_rate`, `bat_consistency`).
- `build_extra_context(conn, player_id, opponent, fmt, gender, opponent_roster=None, venue_id=None, opponent_players=None)` — assembles the whole `ExtraContext`:
  - Name lookup.
  - Batting matchup: queries `dismissal_matchup` filtered either to the opponent's *named specific XI* (`opponent_players`, via `bowler_id IN (...)`) or, when not given, to the whole opponent team (`bowler_team=?`). Computes `matchup_dismissal_rate = dismissals/balls` and `matchup_runs_per_ball = runs/balls` if `balls > 0`.
  - Bowling matchup (symmetric, newer addition): how well *this player* has bowled against the opponent's specific current batters. Since `dismissal_matchup` has no `batting_team` column, it resolves the opponent's batters via `opponent_players` if given, else the pre-computed `opponent_roster`, else a fresh `roster.team_pool` call — then filters `dismissal_matchup` by `bowler_id=? AND batter_id IN (...)`.
  - Phase profile: reads all rows from `player_phase` for this player/format into a `{phase: {...}}` dict.
  - Venue stats: `player_by_venue` for setting/chasing average and strike rate at this ground; plus a "bogey bowler" query against `venue_dismissal_matchup` (top dismisser from this specific opponent, at this specific venue, ordered by dismissals then balls).
  - `player_impact` row: `importance_score`, `win_pct`, `potm_rate`, `setting_strike_rate`, `chasing_strike_rate`.
  - `bat_consistency`: computed from all `player_match_impact.bat_contribution_pct` values (needs ≥5 innings) as `1 / (1 + coefficient_of_variation)` — 1.0 means perfectly steady match-to-match, →0 means wildly variable ("boom or bust").
  - Role/keeper/position via `resolve_role`.
  - `player_registry` row: retirement status, recall flag, age advisory, selection rate, ICC rank, status reason, recent domestic activity.
  - `players` row: bowling style, batting hand.
  - `player_advanced` row: archetype, plus `_attach_batting_profile` parses `profile_json`.
- `_attach_batting_profile(ctx, profile_json)` — parses the JSON `profile_json` column's `"batting"` block onto the context (strike rate, boundary%, dot%, sixes, six rate), then finds the batter's single best phase — the phase with the highest strike rate among phases she's faced ≥30 balls in — purely descriptive, feeding only `explain.py`'s narrative, never the model.

**Non-obvious data shapes:** `hist` DataFrame columns: `date, opponent, won, bat_strike_rate, bat_contribution_pct, economy, wickets, balls_bowled, bowl_contribution_pct, bowl_dot_pct, bowl_boundary_pct, batting_wpa, bowling_wpa, venue_id, wickets_when_bowled`. `ExtraContext.phase_profile` is `{phase_name: {phase, bat_strike_rate, bat_team_percentile, bowl_economy, bowl_team_rank, bowl_team_size}}`.

**How it connects:** Imports `config.SETTINGS`, `roster.team_pool`, `features.common.{recency_weighted_mean, role_bucket, shrink}`, `features.schema.MODEL_FEATURES`. Used by `cli.py` (`resolve_role` directly) and by `recommend/score.py` (both `build_model_features` and `build_extra_context`, inferred from this file's own docstrings referencing `score.py`'s usage).

### `model-training/criiq_models/features/historical.py`

**Purpose:** Constructs the leakage-safe training table — one row per `(player_id, match_id)` in `player_match_impact`, with every feature reconstructed as it would have looked *before* that match happened (so training never sees the future). This is the training-time counterpart to `features/current.py`; both must produce the exact same `MODEL_FEATURES` column set so a model trained on one generalizes correctly to inputs from the other. The target columns are `batting_wpa`/`bowling_wpa` (from data-collection's `wpa.py`), deliberately not contribution-share, because contribution-share can't distinguish a match-winner from a fringe player padding stats in a low-stakes game.

**Key pieces:**
- `_weighted_recent(window, decay)` — the scalar recency-weighted-mean computation used inside a rolling window: given an array `window` (oldest→newest), builds weights `decay ** arange(n-1, -1, -1)` (so the last element gets weight `decay**0 = 1`), masks NaNs, and returns the weighted average (or `NaN` if all missing/empty).
- `_rolling_form(grouped_col, window, decay)` — applies `_weighted_recent` via `s.shift(1).rolling(window, min_periods=1).apply(...)` on a groupby column. The `.shift(1)` is what makes this leakage-safe: it excludes the *current* row's own value from its own rolling window, only ever looking backward.
- `_attach_domestic_form(conn, df, fmt)` — bridges two separate event streams: the international rows already in `df`, and domestic-league rows from `player_match_wpa` (`team_type='club'`). Uses `pd.merge_asof(direction="backward")` rather than a plain groupby/transform, because an international row isn't part of the domestic-only subgroup being rolled — a transform wouldn't align back onto it. For each international row, `merge_asof` finds the most recent domestic checkpoint at or before that date. The domestic rolling form itself (`domestic_form_batting_wpa`/`bowling_wpa`, via the same `_weighted_recent` logic) is **not** shifted, because by the time a later international row looks it up via `merge_asof`, it's already strictly in the past relative to that row — shifting would be redundant, not a leakage fix. Implementation detail: since `df["date"]` must stay a plain string for other callers, the function creates temporary `_date_dt`/`_orig_order` columns for the merge and drops them afterward, restoring original row order. Finally shrinks the domestic WPA values toward the player's international career WPA, capping the effective sample size at `domestic_form_max_effective_matches` (10) via `shrink_series`.
- `build_training_table(conn, fmt, gender)` — the main entry point:
  1. Reads `player_match_impact` joined to `matches` (for `venue_id`) and left-joined to `player_match_wpa`, filtered by format/gender, sorted by `(player_id, date)`. Returns an empty (but correctly-columned) DataFrame if nothing matches.
  2. Masks `wickets_when_bowled = wickets.where(balls_bowled > 0)` (same rationale as `current.py`: `wickets` is 0, not NULL, for non-bowling matches).
  3. Per-player **expanding** (career-to-date, all-history) means via `groupby("player_id").transform(lambda s: s.shift(1).expanding().mean())` for contribution%, strike rate, economy, WPA, and wickets-when-bowled — the `.shift(1)` again excludes the current row.
  4. Per-player **rolling recency-weighted** form features over `SETTINGS.form_window_matches` (15) via `_rolling_form`, for the same set of columns.
  5. Vs-opponent features: grouped by `(player_id, opponent)`, `vs_opp_matches = cumcount()` (0-indexed count of prior matches vs that opponent), raw expanding means of bat/bowl contribution%, then **shrunk** toward the (already-computed) career means via `shrink_series` — explicitly because a live-scoring query with no venue/opponent history would otherwise present `venue_matches=0` paired with a *missing* mean, a combination that literally never occurs in training data (every played match has a real venue), which was confirmed to destabilize predictions if not handled this way. `vs_opp_win_pct` similarly, as `100 * shift(1).expanding().mean()` of `won`.
  6. Vs-venue features: identical pattern, grouped by `(player_id, venue_id)`.
  7. Calls `_attach_domestic_form` to merge in domestic-league form.
  8. Role bucket: reads `player_registry.role` (mapped through `role_bucket`) as a fallback, and `player_role_final.primary_role` as the preferred source — merges both, takes `primary_role.fillna(registry_role_bucket)`, explicitly noted as matching `features/current.py`'s `resolve_role` preference order so train and score agree.
  9. Casts `role_bucket` and other `CATEGORICAL_FEATURES` to pandas `"category"` dtype (LightGBM/sklearn model requirement for categorical handling).
  10. Returns `df[ID_COLUMNS + MODEL_FEATURES + TARGETS]` — the exact final schema.
- Explicitly notes `age_years` was tried as a model feature and rejected after an ablation showed it made prediction correlation worse in 3 of 4 (gender, target) combinations — it's only computed at live-scoring time as descriptive context, never here.
- Also notes dismissal matchups aren't reconstructed here at all (no per-match granularity in the source table); that signal only exists at live-scoring time in `recommend/score.py`.

**Non-obvious data shapes:** Final table columns = `ID_COLUMNS` (`player_id, match_id, date, opponent, venue_id`) + `MODEL_FEATURES` (25 numeric + `role_bucket` categorical) + `TARGETS` (`batting_wpa, bowling_wpa`).

**How it connects:** Imports `config.SETTINGS`, `features.common.{role_bucket, shrink_series}`, `features.schema.{CATEGORICAL_FEATURES, ID_COLUMNS, MODEL_FEATURES, TARGETS}`. Consumed by `cli.py` (`cmd_features`), `evaluate/backtest.py`, `evaluate/rank_backtest.py`, and (per its own docstring) `recommend/train.py`.

### `model-training/criiq_models/features/schema.py`

**Purpose:** The canonical, single-source list of feature/target column names that both `historical.py` (training) and `current.py` (live scoring) must produce identically — this is what guarantees a model trained on one feature builder's output can validly score inputs from the other.

**Key pieces:**
- `NUMERIC_FEATURES` — 25 numeric columns: `career_matches`, `career_bat_contribution_pct`, `career_bowl_contribution_pct`, `career_bat_sr`, `career_bowl_economy`, `career_batting_wpa`, `career_bowling_wpa`, `career_bowl_wickets_per_match`, then the `form_*` equivalents of the same 7 (excluding `career_matches`), then `vs_opp_matches`, `vs_opp_bat_contribution_pct`, `vs_opp_bowl_contribution_pct`, `vs_opp_win_pct`, `venue_matches`, `venue_bat_contribution_pct`, `venue_bowl_contribution_pct`, `domestic_form_matches`, `domestic_form_batting_wpa`, `domestic_form_bowling_wpa`.
- `CATEGORICAL_FEATURES = ["role_bucket"]`.
- `MODEL_FEATURES = NUMERIC_FEATURES + CATEGORICAL_FEATURES` — the exact input column list any trained model expects, in order.
- `TARGETS = ["batting_wpa", "bowling_wpa"]` — the two regression targets, explicitly WPA rather than contribution-share for the reason noted in `historical.py`.
- `ID_COLUMNS = ["player_id", "match_id", "date", "opponent", "venue_id"]` — identifying (non-feature, non-target) columns carried alongside the training table for grouping/joining/debugging (e.g. `evaluate/backtest.py` groups by `match_id`, `evaluate/rank_backtest.py` sorts by `match_id`).

**How it connects:** Imported by `features/historical.py`, `features/current.py`, `evaluate/backtest.py`, `evaluate/rank_backtest.py`, and (implied) `recommend/train.py`. Imports nothing — it's a pure constants module.

### `model-training/criiq_models/features/style_matchup.py`

**Purpose:** A secondary, style-aware refinement of the batting-vs-bowling matchup signal used in `recommend/score.py`. The primary/aggregate signal (`dismissal_matchup`) captures a batter's record against specific bowlers or teams; this module instead asks "how does she fare against the opponent's *style mix* (pace vs spin), weighted by her own vs-pace/vs-spin split?" It's explicitly documented as secondary/backup because style coverage is only available for 13 major nations and is coarser than specific-bowler history.

**Key pieces:**
- `STYLE_EDGE_CAP = 5.0` — hard cap (in both directions) on the points this signal can contribute.
- `opponent_bowling_mix(conn, opponent, fmt, gender, opponent_roster=None)` — computes `{"pace": share, "spin": share}` from the normalized value counts of `player_styles.bowling_style` across the opponent's eligible bowlers (`roster.team_pool`, or a pre-computed `opponent_roster` passed in to avoid recomputing it per player — noted as previously the actual runtime bottleneck at ~0.6s/call in pool-wide scoring). Returns `None` if fewer than 2 bowlers have a known style (not enough signal).
- `style_matchup_edge(conn, player_id, opponent, career_dismissal_rate, fmt, gender, opponent_roster=None)`:
  1. Returns `{"available": False, "edge_part": 0.0}` immediately if `career_dismissal_rate` is `None` (the same aggregate dismissal-rate value `score.py` computes elsewhere, passed in to keep both signals consistent) — or if the opponent's bowling mix or the player's `player_advanced.profile_json` isn't available.
  2. Pulls `vs_bowling_type` from the batting block of `profile_json` (a dict like `{"pace": {"balls": ..., "dismissals": ...}, "spin": {...}}`).
  3. For each style (`pace`, `spin`) in the opponent's mix, if the player has enough balls faced against that style: computes `raw_rate = dismissals/balls`, shrinks it toward `career_dismissal_rate` via `shrink()` with `prior_strength = shrinkage_prior_matches * 6` (48 — a much stronger prior than the standard 8, since per-style splits are noisier/smaller samples than per-opponent ones), then accumulates a mix-share-weighted average (`weighted_rate += share * shrunk_rate`, `total_weight += share`).
  4. Normalizes by `total_weight`; if zero, returns unavailable.
  5. `edge_part = clip((career_dismissal_rate - weighted_rate) * 120, -5.0, 5.0)` — a *positive* edge means the player dismisses less often against this specific style mix than her career baseline (i.e. she's better suited against this opponent's bowling profile), scaled by 120 and capped at ±5.
  6. Returns `{available: True, edge_part, weighted_dismissal_rate, opponent_bowling_mix}`.

**How it connects:** Imports `config.SETTINGS`, `features.common.shrink`, `roster.team_pool`. Consumed by `recommend/score.py` (per this file's own docstring, as a secondary signal alongside the aggregate `dismissal_matchup` computation).

### `model-training/criiq_models/roster.py`

**Purpose:** Derives "which national team does this player currently represent" and the pool of eligible players for a given team — a foundational lookup every recommendation/simulation command needs (`cli.py`'s `cmd_recommend`, `cmd_analyze_xi`, `cmd_simulate`, etc. all start from `roster.team_pool`). Its core design problem, stated up front in the module docstring: neither `player_registry.nationality` (entirely NULL for T20) nor `players.nationality` (~28% populated) reliably answers "which team" — so a player's current team is instead derived from the team recorded on her most recent actual match appearance (`match_players.team`), which is complete and authoritative.

**Key pieces:**
- `_player_id_map(conn)` → `(unambiguous: {identifier: player_id}, split: {(identifier, gender): player_id})`. Handles a known Cricsheet data quirk: a handful of raw identifiers (e.g. `"A Sharma"`) are reused across two genuinely different real people of different genders. `data-collection`'s `identity.resolve_players` already splits these into distinct, stable `player_id`s (one per gender). This function mirrors that same split logic locally rather than importing data-collection's code — the module docstring elsewhere in the codebase (referenced here) states this package deliberately never imports data-collection's own code, only reads its DB.
- `player_current_teams(conn, fmt, gender)` — one row per `player_id`: her current team + most recent international-appearance date. Deliberately filters to `team_type='international'` only — `matches`/`match_players` also carries domestic league fixtures (WBBL, WPL, etc.) whose `team1`/`team2` are franchise names, not countries; without this filter, a player's recent domestic schedule could resolve her "current team" to a franchise, silently dropping her from her actual country's pool. Logic: reads all appearances (name, team, date) for the format/gender, maps player names to identifiers via `identifier_map`, then identifiers to `player_id`s via the unambiguous/split maps from `_player_id_map`, drops unresolved rows, and for each player keeps only the row at `idxmax()` of `date` (i.e. her latest appearance).
- `team_pool(conn, team, fmt, gender, include_inactive=False)` — the actual selectable roster for a team:
  1. Filters `player_current_teams` output to the given team.
  2. Joins to `player_registry` for `retirement_status`, `recall_flag`, `recent_domestic_activity`.
  3. `excluded = retirement_status in SETTINGS.excluded_statuses` (`RETIRED_ALL`, `RETIRED_FORMAT`) — always dropped, no override.
  4. `inactive = (retirement_status == "INACTIVE") & (recall_flag == 0) & (recent_domestic_activity == 0)` — a player is treated as inactive (and excluded unless `include_inactive=True`) only if she's *both* flagged INACTIVE *and* has no recall flag *and* no recent domestic activity; any one of those overrides it. The docstring is explicit this is a selection-eligibility carve-out, not a correction to `retirement_status` itself — that label is meant to stay an honest, international-only fact. It even references a specific bug this distinction caught: a player who was INACTIVE internationally but active domestically was incorrectly showing as "ACTIVE" because her domestic recency had been folded directly into the classification — which was fixed at the source in data-collection's `registry.py`, not patched here.
  5. **`unknown = (retirement_status == "UNKNOWN") & (recent_domestic_activity == 0)`** — a third, separate eligibility category on top of `excluded`/`inactive`. `UNKNOWN` is data-collection's label for "no international appearance in the 540-1095 day window" — a player who has just retired from a format sits in this band for roughly three years before ageing into `INACTIVE`. A real, concrete bug this closes: V Kohli and RG Sharma, both retired from T20Is in June 2024, were still being offered up for India's XI before this check existed, because nothing was excluding the `UNKNOWN` band. `recall_flag` is deliberately *not* a carve-out here the way it is for `inactive` above — every `UNKNOWN` row has `recall_flag=1` by construction (the flag is what marks this exact staleness band), so honouring it would cancel the exclusion outright; only recent domestic activity earns a way back in.
  6. Returns `player_id`s where `~excluded & (include_inactive | ~(inactive | unknown))`.
  7. **Dormant-associate-team fallback:** if step 6's pool, after the `UNKNOWN` exclusion, comes out smaller than `SETTINGS.xi_size` (11), the function falls back to the pre-`UNKNOWN` rule (`~excluded & ~inactive`) instead. Associate/qualifier sides that play so rarely their entire squad reads as `UNKNOWN` (Maldives, Mongolia, Greece, ...) would otherwise be left with no fieldable XI at all — their last known squad is judged more useful than an empty pool. A side with any genuinely active core never reaches this branch (the docstring's example: India men keep 22 of 42 players even with a whole generation newly retired).
- `known_teams(conn, fmt, gender)` — distinct `team1`/`team2` values from `matches` for the format/gender, sorted, `UNION`'d (so a team appearing only as `team2` in some rows is still included).

**Non-obvious data shapes:** `player_current_teams` returns columns `player_id, team, last_appearance_date`.

**How it connects:** Imports `config.SETTINGS` only. Imported by `features/current.py` (`team_pool`, for opponent-roster resolution), `features/style_matchup.py` (`team_pool`), and `cli.py` (`known_teams`, `team_pool`).

### `model-training/criiq_models/recommend/explain.py`

**Purpose:** Turns the numeric output of `RecommendationScorer.score()` (a dict of additive `components`) into coach-facing English sentences. It is explicitly a "narration" layer: every sentence it writes is derived from a number already present in `scored["components"]`, nothing is invented or independently computed. This is the layer that makes the recommendation engine's score explainable rather than a black box.

**Key pieces:**

- `explain(scored, alternative=None, slot=None, h2h_batting=None, h2h_bowling=None, is_best_fielder=False) -> dict`: takes one player's `score()` output (plus, optionally, the next-best alternative for the same team-sheet slot from `selection/optimize.slot_category`, the slot name itself, named-XI head-to-head dicts, and whether `selection/optimize.best_fielder` picked this player), and returns `{"player_id", "name", "score", "summary": [sentences...], "components"}`.
  - Step 1 — headline: `"{name} rates {score}/100 for this matchup against {opponent}{keeper tag}."`
  - Step 2 — competitive framing: if `alternative` is given, adds "Picked for {slot} ahead of {alt_name} (score X), the next-best available option there." If no alternative but a `slot` is given, says it's "an uncontested pick." This directly answers "why this player and not someone else."
  - Step 3 — descriptive profile: hand/archetype/age line, bowling style line, then `_append_batting_profile` (below).
  - Step 4 — model explanation: if `components["model_applied"]` is True, states the predicted batting/bowling win-probability-added (as a signed percentage via the local `_pct` helper) and the resulting `model_part` points, framed as "based on N career matches." If the model was *not* applied (cold start), it instead reports the `cold_start_reason` and falls back to describing the career-baseline WPA that was shrunk in as a substitute — explicitly telling the coach this is a lower-confidence estimate, not silently presenting it the same way as a model-backed number.
  - Step 5 — a deliberate caveat: if `archetype in ("finisher", "power hitter")` and `model_part <= SETTINGS.finisher_low_impact_threshold` (5.0, not 0 — a small amount of impact still counts as "low" for this warning), it explicitly warns that WPA-based scoring can undervalue a genuine finisher/hitter ("this rating is driven by win-probability-added... not raw hitting"), telling the coach to look manually. This is a hand-written override for a known blind spot of the scoring formula, not a generic template line.
  - Step 6 — strike-rate penalty explanation: only fires if `strike_rate_part < 0`; explains the career SR vs. the gender/format benchmark, and if `game_awareness_factor > 0` with signals present, notes the penalty was partially offset by "game awareness" (naming which signals: experience, big_moment, chasing, consistency).
  - Step 7 — bowling style descriptor: dot-ball % vs boundary % determines whether the text calls the bowler "control-focused... building pressure with dot balls" (dot_pct >= 3x boundary_pct), "attacking, prone to conceding boundaries" (boundary_pct >= 15), or "a balanced containment profile" otherwise — a simple three-way heuristic on real numbers, not a model.
  - Step 8 — matchup lines built from `score()`'s own aggregate numbers: dismissal-history vs. opponent bowlers (only if `matchup_balls_vs_opponent_bowlers > 0`, else explicitly "No recorded history against {opponent}'s specific bowlers"), style-matchup edge (pace/spin mix vs. this batter's vs-style record, only if `style_matchup_available`), and symmetric bowling-matchup line (batters this bowler has faced, if `bowl_matchup_balls_vs_opponent_batters > 0`).
  - Step 8b — **named-XI head-to-head lines**, a separate signal from step 8's aggregate numbers: if `h2h_batting` has a `best`/`bogey` entry (from `recommend/matchup_matrix.head_to_head_matrix`, real per-pair dismissal history against the *specific* opponent XI named for this fixture, not the opponent's team-wide average), renders "best to target is X (SR ... in ... balls)" / "bogey bowler is Y (... dismissals in ... balls)". Symmetric block for `h2h_bowling` ("has X's number" / "Y counters well"). Both are opt-in params the caller (`cli.py`) threads through per fixture, since they need the *named* opposing XI, not just the opponent name.
  - Step 9 — phase-fit and team-need bonuses: only rendered if their respective component is > 0 (never claims a bonus that wasn't earned).
  - Step 10 — track record (`importance_score`/`win_pct`/ICC rank), venue-specific record (matches played there, runs/wickets contribution %, batting-first vs. chasing splits, and a "bogey bowler" callout if one exists), domestic form, **fielding record** (catches/run-outs/stumpings/dismissals-per-match from `score.py`'s `player_fielding` query — only if `fielding_matches > 0`; if `is_best_fielder`, phrased as "Also the sharpest fielder among the players considered here... a real edge in the field," otherwise a plain "In the field: ..." line), retirement/status flags, and finally risk flags (age advisory, inconsistent selection history, recalled-after-inactive, or included on domestic activity rather than international recall) — only emitted when `risk_part < 0`.
  - Every sentence-emission is gated behind a truthy/non-null check on the underlying number, so the narration never states something the score didn't actually account for.

- `_append_batting_profile(lines, inp, archetype)`: a private helper, purely descriptive (never scored) — gated on `bat_balls >= 30` so a tailender's tiny sample isn't narrated as if meaningful. Reports strike rate, boundary %, dot %, sixes/six-rate, and best phase (translated via `_PHASE_LABEL`, e.g. `"powerplay"` → `"powerplay (overs 1-6)"`).

- `explain_many(scored_players) -> list[dict]`: trivial `[explain(s) for s in scored_players]`, no alternative/slot/h2h/fielding wiring (used where per-slot competitive framing isn't needed).

**How it connects:** Imports `config.SETTINGS` (for `finisher_low_impact_threshold`) — otherwise pure formatting over an already-computed dict, relying on the module docstring's reference to `score.py`'s `components` and `selection/optimize.slot_category`'s slot naming convention. Called by `recommend/render.py` (via the CLI) and by `cli.cmd_recommend`'s `--explain` path, which is also what supplies the `h2h_batting`/`h2h_bowling`/`is_best_fielder` arguments (see that section).

### `model-training/criiq_models/recommend/matchup_matrix.py`

**Purpose:** Builds a head-to-head matchup matrix between two named XIs (not whole squads) — "my batters vs their bowlers" and "my bowlers vs their batters" — purely by aggregating real ball-by-ball history from the `dismissal_matchup` table. It is a pure read/aggregation module: pairs with zero recorded balls are simply omitted from the output, never estimated or guessed at.

**Key pieces:**

- `_MIN_PAIR_BALLS = 6`: a one-over threshold — a pairing with fewer real balls faced is not surfaced at all, to avoid reporting a 2-ball fluke as a "matchup."
- `_rows(conn, fmt, id_col, id_values, other_col, other_values)`: builds and runs a parameterized `SELECT ... FROM dismissal_matchup WHERE format=? AND {id_col} IN (...) AND {other_col} IN (...) AND balls >= 6`. `id_col`/`other_col` are swapped between calls to get the batting view (`batter_id`/`bowler_id`) and bowling view (`bowler_id`/`batter_id`) from the same query shape.
- `head_to_head_matrix(conn, my_ids, opponent_ids, fmt=SETTINGS.format) -> dict`: the main entry point, returning `{"batting": {...}, "bowling": {...}}` keyed by *my* player's name (short-circuits to empty dicts if either id list is empty).
  - **Batting side:** for each real `(batter_id, bowler_id)` row, computes `dismissal_rate = dismissals/balls` and `strike_rate = 100*runs/balls`, grouped by batter name into a list of per-bowler entries.
  - **Bowling side:** symmetric, but computes `wicket_rate = dismissals/balls` and `economy = 6*runs/balls`.
  - `_bat_summary(matchups)`: sorts matchups by balls faced descending, then picks a `"bogey"` bowler (max by `(dismissals, dismissal_rate)` tuple — dismissals first, rate breaks ties) and a `"best"` matchup (max runs scored off that bowler).
  - `_bowl_summary(matchups)`: symmetric — `"best"` (max `(dismissals, wicket_rate)`) and `"most_expensive"` (max runs conceded).

**How it connects:** Reads the same `dismissal_matchup` table as `criiq_data`'s matchup ingestion and `simulate/outcomes.py`'s `load_matchup_lookup`. Its output feeds `recommend/render.py`'s head-to-head section in the rendered team sheet, and is invoked from the CLI's `cmd_recommend` when an opponent's named XI is supplied.

### `model-training/criiq_models/recommend/render.py`

**Purpose:** Pure text-rendering layer — turns the structured output of `select_xi`/`explain`/`analyze_xi` into a human-readable, fixed-width (`_WIDTH = 78`) plain-text team sheet or custom-XI analysis. Computes nothing new; every number it prints was already computed upstream.

**Key pieces:**

- `_wrap(text)`: wraps a line to `_WIDTH - len(_INDENT)` chars using `textwrap.wrap`, indenting continuation lines by two extra spaces — used for every reasoning sentence so long explanations don't blow past 78 columns.
- `_POOL_SECTIONS = [("batter","BATTING POOL"), ("all-rounder","ALL-ROUNDER POOL"), ("bowler","BOWLING POOL")]`: the fixed order/labels used to split the shortlist the way a coach actually thinks about a squad.
- `render_team_sheet(...) -> str`: the main renderer.
  - Prints a header banner with team/opponent/venue.
  - If `model_metadata` given, prints training provenance (trained-at timestamp, row count, format/gender).
  - If `strength_context["lopsided"]` and this team is the `stronger_side`, prints a "MATCHUP CONTEXT" note pointing the coach at the rotation XI below.
  - `_render_player(i, p)`: shared row-renderer for a numbered player line (`name`, `role_bucket`, `(wk)`/`[XI]` tags, score) plus its wrapped reasoning sentences underneath.
  - Renders each of the three role pools (batting/all-rounder/bowling), each sorted by `-score`, then an "UNRECOGNIZED ROLE" trailing section for anyone whose `role_bucket` doesn't match the three known buckets — so nobody with an odd role gets silently dropped from the printed roster.
  - If `role_options` given (best-per-archetype specialists from `role_highlights`), prints a "SPECIALIST ROLE OPTIONS" section, tagging `[XI]` for anyone already selected.
  - Prints the "PLAYING XI (batting order)" section in the order `xi_explained` was already given (i.e., `select_xi`'s `_team_sheet_order`), then the `constraints` line (min batting/bowling-capable, keepers, openers).
  - If `head_to_head` data is non-empty, prints a "HEAD-TO-HEAD" section: for each of my batters, "troubled by X" (bogey) / "scores off X" (best) sentences; for each of my bowlers, "has X's number" (best) / "leaks to X" (most_expensive) sentences.
  - If `rotation_xi` given (the lopsided-match rest-players scenario), prints a "ROTATION XI" section listing who's rested and the substitute lineup.
  - Explicit design note in the docstring: `xi_explained` (the final constrained XI) is shown *separately* from `pool_explained` (the wider ranked shortlist) because the MILP selector can trade a top-ranked specialist for a required keeper/opener, so the XI is not simply "the pool's top 11."
- `render_xi_analysis(team, opponent, venue_id, xi_explained, analysis) -> str`: renders `selection/optimize.analyze_xi`'s output — a coach's own hand-picked XI scored and checked against the same constraints `select_xi` enforces. Prints each player + reasoning, a composition summary (`size/xi_size`, batting/bowling-capable counts vs. required, keeper/opener counts), any constraint `violations`, and a comparison to the AI's own optimal XI: the score gap, and two lists — players in the optimal XI but not chosen, and players chosen but not in the optimal XI. Warns about any `missing_player_ids` (ids not found in the eligible pool) up front.

**How it connects:** Consumes dicts produced by `recommend/score.py` (via `explain.py`), `recommend/strength.py` (`strength_context`), `recommend/matchup_matrix.py` (`head_to_head_matrix`), and `selection/optimize.py` (`select_xi`, `analyze_xi`, `role_pools`, `role_highlights`). Called directly by the CLI's recommend/analyze commands. Imports only `textwrap` from the standard library — no other project module.

### `model-training/criiq_models/recommend/score.py`

**Purpose:** The core composite, explainable player-scoring engine — the heart of the recommendation system. Combines a machine-learned prediction of expected win-probability-added (WPA) with several rule-based adjustments (matchup history, phase fit, standing, risk, strike-rate penalty) into one 0–100 score, with every contributing term stored separately in a `components` dict so nothing is a hidden black box. Deliberately scores WPA (real impact on winning), not contribution-share, because contribution-share can't distinguish a proven match-winner from a fringe player padding stats in low-stakes matches.

**Key pieces:**

- `RecommendationScorer.__init__(conn, fmt, gender, models=None, team=None)`: loads the trained models (`load_models`) and metadata (`load_metadata`) scoped to `(fmt, gender)` — explicitly noted that these must always be passed through together, since loading a different gender's models silently would be a real bug. `team` (added later than the rest of `__init__`) is the side being scored *for* — when known, it lets `_opponent_strength_part` use real head-to-head history against that specific opponent instead of the opponent's generic form; `cli.py`'s `cmd_recommend` passes `team=args.team`. Computes empirical `_priors` once, and caches both opponent rosters (`_opponent_roster_cache`) and opponent-strength values (`_opponent_strength_cache`) per-opponent since `score_many` scores a whole pool against the same opponent repeatedly.
- `_opponent_roster(opponent)`: memoized wrapper around `team_pool`.
- `_recent_win_pct(team, opponent)`: last `SETTINGS.opponent_form_matches` (20) completed internationals for `team`, either generally (`opponent=None`) or head-to-head against a named `opponent`, returning `(win_pct, sample_size)`.
- `_opponent_strength_part(opponent)`: a bonus/penalty for facing a given opponent. Computes the opponent's generic recent win rate; if `self.team` is known, also computes the *head-to-head* win rate and shrinks it toward the generic rate via `shrink()` (prior strength `SETTINGS.shrinkage_prior_matches`) so a thin head-to-head sample doesn't overwhelm the signal. Applies an asymmetric cap/scale: below 50% opponent win rate (a weaker opponent) uses a steeper `scale_weak`/wider `cap_weak`; at or above 50% (a stronger opponent) uses a gentler `scale_strong`/narrower `cap_strong` (`SETTINGS.opponent_strength_cap_weak/scale_weak/cap_strong/scale_strong`). Result is `max(-cap, min(cap, (50.0 - opponent_win_pct) * scale))`, cached per opponent.
- `_compute_priors()`: computes fallback priors used when a player has no empirical history to shrink toward:
  - `batting_wpa`/`bowling_wpa`: mean WPA across all players currently on any team in this (fmt, gender) scope (from `player_match_wpa`), falling back to `0.0` if the scope is empty.
  - `dismissal_rate`: mean of `bat_strike_rate / (100 * bat_average)` across the same scope (falls back to `0.05`).
  - `batter_sr_benchmark`: median strike rate among "real batters" (`bat_average >= 15`, i.e. excludes tailenders), computed separately per gender because men's/women's T20 SR distributions differ — this benchmark is later used both for the strike-rate penalty and the game-awareness "chasing" signal.
- `_game_awareness(feats, ctx)`: a `[0,1]` factor averaged over up to 4 available signals — `experience` (`career_matches / SETTINGS.experience_full_matches`, capped at 1), `big_moment` (`importance_score/100`, as a clutch-play proxy), `chasing` (chasing SR relative to the gender SR benchmark), `consistency` (`bat_consistency` directly). Only ever used to *reduce* the strike-rate penalty below, never to reward — comment explicitly states this.
- `_strike_rate_penalty(feats, ctx, bucket)`: a **soft, never-positive** penalty for a batting-capable player whose career SR is below the gender par. Returns `(0.0, awareness)` if the player isn't batting-capable, has no career SR, or is at/above par. Otherwise: `shortfall = (benchmark - career_sr) / benchmark`; `raw = min(sr_penalty_cap, shortfall * sr_penalty_scale)`; final `penalty = -round(raw * (1 - awareness_factor), 1)` — i.e. high game-awareness offsets (shrinks toward zero) the penalty, but can never turn it positive.
- `score(player_id, opponent, venue_id=None, opponent_players=None) -> dict`: the main per-player scorer. Walks through building each additive component:
  1. **`model_part`** — Loads `feats` (`build_model_features`) and `ctx` (`build_extra_context`). If `career_matches >= SETTINGS.min_matches_for_model` and models exist (`model_applied=True`), runs the trained sklearn regressors on the feature row to predict `batting_wpa`/`bowling_wpa` directly. Otherwise (cold start), falls back to `shrink()` of the player's own career WPA aggregate toward the computed prior, weighted by observed match count. NaN aggregates are normalized to `None`. Then: only credits a discipline if the player's `role_bucket` suggests it (`batting_capable`/`bowling_capable`) *or* there's genuine observed history for that axis (`has_bat_data`/`has_bowl_data`) — this stops `shrink()`'s bare prior (when zero real observations exist) from being awarded to an axis the player doesn't actually play, e.g. crediting a specialist batter's "bowling WPA" with a league-average prior. The best ("primary") discipline is credited at full weight; any secondary discipline is added at a discount (`SETTINGS.secondary_discipline_weight`) — explicitly to avoid capping every specialist below any all-rounder with two merely-decent disciplines. `model_part = min(45.0, (primary + secondary_bonus) * SETTINGS.wpa_scale)`. If the model wasn't applied, this is further scaled by a `confidence = min(1.0, career_matches / min_matches_for_model)` ramp — protecting against a 3-match player who happened to bowl well vs. weak opposition being over-rated by a shrink-based estimate.
  2. **`matchup_part`** — sum of three sub-parts, each clamped to `[-8, 8]`:
     - `aggregate_matchup_part`: shrinks the player's real dismissal rate vs. this specific opponent's bowlers toward their career dismissal rate (using `shrink()` with `prior_strength = shrinkage_prior_matches * 6`), then scales `(career_rate - shrunk_rate) * 120` — a *lower* dismissal rate than career is a *favourable* matchup, hence the subtraction direction.
     - `style["edge_part"]` from `style_matchup_edge` (opponent's pace/spin mix vs. this batter's vs-style record), scoped to the named opponent XI if given, else the whole team roster.
     - `bowl_matchup_part`: the symmetric bowling-side signal — shrinks wicket rate vs. this opponent's specific batters toward career bowling wicket rate, scaled by `175` (not 120) — the module comment explains this scale was calibrated so a one-std-dev edge in bowling wicket-rate (std ~0.019) reads as comparably sized to a one-std-dev edge in batting dismissal-rate (std ~0.028). Polarity is opposite of batting: a *higher* wicket rate here is *good*.
  3. **`phase_fit_part`** — `min(8.0, best_bat_pct/100 * 4 + best_bowl_rank_score * 4)`, where `best_bat_pct` is the player's best-phase batting percentile among teammates, and `best_bowl_rank_score = 1 - (rank-1)/(size-1)` for whichever phase their bowling rank (within the team) is best.
  4. **`standing_part`** — `min(20.0, importance_score * 0.15 + (5.0 if icc_rank is not None else 0))`.
  5. **`risk_part`** — subtracts points for `age_advisory` (−3), `INCONSISTENT` retirement status (−5), or `INACTIVE` with a recall flag or recent domestic activity (−4).
  6. **`strike_rate_part`** — from `_strike_rate_penalty` above.
  7. **`opponent_strength_part`** — from `_opponent_strength_part(opponent)` above; folded into the same additive total as every other component, not a separate multiplier.
  - `total = round(clamp(model_part + matchup_part + phase_fit_part + standing_part + risk_part + strike_rate_part + opponent_strength_part, 0, 100), 1)`.
  - Also queries `player_fielding` (catches/run-outs/stumpings/dismissals/dismissals-per-match, see `data-collection/criiq_data/fielding.py`) purely descriptively — these `fielding_*` fields land in `components.inputs` for `explain.py`'s "In the field: ..." narration and `selection/optimize.best_fielder`'s ranking, but are never added into the numeric score itself.
  - Returns a rich dict: top-level `player_id`, `name`, `role_bucket`, `is_keeper`, `batting_position_median`, `opponent`, `venue_id`, `score`, and `components` (each additive part plus a large `inputs` sub-dict of every raw number behind them, including the fielding fields above — with NaN-to-None normalization throughout, since pandas SQL reads return `NaN` rather than `None` for missing values, and `explain.py` must never render `"nan%"`).
- `score_many(player_ids, opponent, venue_id=None, opponent_players=None) -> list[dict]`: scores every player individually, then computes `compute_team_need` once across the whole pool and applies `player_team_need_bonus` per player, adding it into both `components["team_need_part"]` and the final `score` (re-clamped to 100).

**How it connects:** Imports from `features/common.py` (`batting_capable`, `bowling_capable`, `shrink`), `features/current.py` (`build_extra_context`, `build_model_features`), `features/schema.py` (`MODEL_FEATURES`), `features/style_matchup.py` (`style_matchup_edge`), `roster.py` (`player_current_teams`, `team_pool`), and this package's own `team_need.py` and `train.py`. Its output feeds `explain.py`, `selection/optimize.py` (`select_xi`, `analyze_xi`), and `render.py`.

### `model-training/criiq_models/recommend/strength.py`

**Purpose:** Computes relative team strength between two sides, specifically to detect a "lopsided" matchup where a stronger team could afford to rest frontline players. Documents a real dead end: raw mean `importance_score` turns out useless for this because associate nations pad their importance beating other associates (Nepal's top-11 mean importance ~70 vs. India's ~79 — not a meaningful gap). The signal that actually works is **how many players hold a current ICC ranking** (India 6 vs. Nepal 1 vs. Oman 0, men's, live DB) — a genuine proxy for "world-class player count" since ICC *country* rankings aren't ingested, only per-player ones.

**Key pieces:**

- `team_strength(conn, team, fmt, gender) -> dict`: returns `{team, icc_ranked, pool_size}`. `icc_ranked` is a `COUNT(*)` of the team's eligible pool (`team_pool`) where `player_registry.icc_rank IS NOT NULL`.
- `strength_context(conn, team, opponent, fmt, gender) -> dict`: computes `team_strength` for both sides, `gap = mine.icc_ranked - theirs.icc_ranked`. `lopsided` is True only when `gap >= SETTINGS.lopsided_icc_gap` **and** the opponent has `<= 1` ICC-ranked player **and** this team has `>= 1`. Both conditions matter: a big gap alone (say India 6 vs Australia 5, gap 1) wouldn't fire, and the design goal stated in the docstring is that "India-vs-Nepal fires, India-vs-Australia does not." Returns `stronger_side` (whichever team has the positive gap, `None` if tied).

**How it connects:** Uses `roster.team_pool` and `config.SETTINGS`. Its output (`strength_context`) is consumed by `recommend/render.py` to print the "MATCHUP CONTEXT" note and drive the rotation-XI section, and presumably by the CLI when assembling a rotation-XI recommendation.

### `model-training/criiq_models/recommend/team_need.py`

**Purpose:** A synergy-aware bonus that a player's standalone score (from `score.py`) can't express: a team thin on death-overs bowling should value a death specialist *more* in this specific pool than her isolated number suggests, mirroring how a real coach's 7th/8th pick depends on who's already picked. Rather than a fully sequential re-scoring algorithm (harder to keep provably well-behaved alongside the MILP selector), this computes a single transparent bonus once per recommendation, added as its own visible `team_need_part` component (never folded silently into `model_part`).

**Key pieces:**

- `PHASES = ("powerplay", "middle", "death")`, `TEAM_NEED_CAP = 5.0`.
- `_phase_benchmarks(conn, fmt, gender)`: format-wide average combined (`batting_wpa_per_match + bowling_wpa_per_match`, NaN-filled to 0) per phase from `player_phase_wpa`, scoped to the correct gender via a join through `player_match_wpa` → `matches.gender` (not `players.gender`, which is NULL for all but ~32 identifiers affected by a cross-gender-collision fix — this is the same gender-resolution technique used throughout the codebase). The docstring explicitly notes this fixed a real, previously-shipped bug where the benchmark blended men's and women's data together, comparing a women's pool against the wrong reference population.
- `_pool_phase_averages(conn, player_ids, fmt)`: same combined-WPA-per-phase average, but scoped to just this specific candidate pool (not gender-filtered again — `player_ids` is already the right scope).
- `compute_team_need(conn, player_ids, fmt, gender) -> dict`: computes `gaps[phase] = pool_avg[phase] - benchmark[phase]` for every phase with a benchmark. `neediest = min(gaps, key=gaps.get)` (most negative gap); returned as `neediest_phase` only if that gap is actually negative (a pool that's *strong* everywhere gets no bonus target at all).
- `player_team_need_bonus(conn, player_id, team_need, fmt) -> dict`: **never a penalty** — if there's no neediest phase, or the player has no `player_phase_wpa` row for it, returns `bonus=0.0`. Otherwise computes `surplus = player's combined phase WPA - benchmark[phase]`, and `bonus = round(clamp(surplus * 35, 0, TEAM_NEED_CAP), 1)`. The `*35` scaling factor is explicitly justified against the real data: combined phase-WPA has an empirical std of ~0.065–0.078, so a one-std-dev surplus should read as a noticeable ~2–3pt strength, and only a two-std-dev (truly exceptional) surplus should hit the 5.0 cap. The docstring records that an earlier version used `*200`, which capped almost every player regardless of whether they actually filled the team's specific gap — caught by eyeballing real output, a documented real bug-fix, not a hypothetical.

**How it connects:** Called from `recommend/score.py`'s `score_many` (computed once per pool, applied per player). Reads `player_phase_wpa`, `player_match_wpa`, and `matches` tables directly via `pd.read_sql_query`.

### `model-training/criiq_models/recommend/train.py`

**Purpose:** Fits and persists the two WPA regressors (`batting_wpa`, `bowling_wpa`) that `RecommendationScorer.score()` loads and predicts from. Trains them as two fully independent models rather than one blended target, because a pure bowler's near-zero batting WPA would otherwise drag down a single shared target, and all-rounders genuinely need both axes scored separately.

**Key pieces:**

- `_artifacts_dir(fmt, gender)`: returns `RECOMMENDATION_ARTIFACTS_DIR / f"{gender}_{fmt}"`, creating it if needed. The docstring flags a real, previously-live bug this structure fixes: before this per-scope subdirectory existed, every `(fmt, gender)` scope shared identical filenames, so training a men's model would silently overwrite a women's model with no error and no way to tell afterward which gender's model was actually loaded.
- `TARGET_CLIP_QUANTILES = {"batting_wpa": (0.05, 0.95), "bowling_wpa": (0.02, 0.98)}`: quantiles that **training labels only** (never holdout evaluation labels) get clipped to before fitting, via `_clip_target`. Bowling's clip is now *wider* (less aggressive) than batting's, the opposite of an earlier version of this file — the current setting was reached via the tuning history recorded in `training_and_selection_walkthrough.ipynb`/`ALGORITHMS.md`: widening bowling's clip toward the raw labels, together with reweighting its `VotingRegressor` (below), measurably improved holdout correlation on both gender scopes.
- `_rf_pipeline(max_depth, min_samples_leaf, max_features=None, random_state=SETTINGS.random_state)`: builds a `Pipeline` with a `ColumnTransformer` (`SimpleImputer(median)` on numeric features, `OneHotEncoder(handle_unknown="ignore")` on categorical features) feeding a `RandomForestRegressor(n_estimators=300, ...)`. `max_features` defaults to `None` (every tree sees all features per split — not the classifier-sibling default) and is only overridden per the gender-gating below.
- `_make_model(target, gender=SETTINGS.gender)`: model choice is explicitly per-target (and, for batting, per-gender) and cited to `model_comparison.ipynb`/`training_and_selection_walkthrough.ipynb`'s real holdout numbers (re-run and re-check after any feature change):
  - `batting_wpa` → `_rf_pipeline(max_depth=10, min_samples_leaf=5, max_features="sqrt" if gender == "female" else None)`. An unregularized RF overfits this noisy per-match target badly enough to fall *below* the mean-predictor baseline on holdout (confirmed by actually running it). `max_features="sqrt"` (forcing each tree to consider only a random feature subset per split, decorrelating the ensemble) was checked on **both** gender scopes with a paired significance test across 3 holdout fractions × 3 seeds before shipping — it won clearly and consistently for `female` (p<0.05, wins 9/9) but was statistically indistinguishable from doing nothing for `male` (p>0.05, wins ~half the time), so it's gated on gender rather than applied unconditionally — the same discipline the README documents catching a prior gender-conditional bug with.
  - `bowling_wpa` → a `VotingRegressor([("hgb", HistGradientBoostingRegressor(max_depth=2, min_samples_leaf=50)), ("rf", _rf_pipeline(max_depth=6, min_samples_leaf=50))], weights=[0.7, 0.3])` — explicit weights favoring the boosted-tree half, not an equal-weight average. This combination (reweighting + the wider label clip above) was verified to win on **both** gender scopes in the same paired-significance protocol (male's result was the cleanest in that search).
- `_fit_one(df, target, gender=SETTINGS.gender) -> (model, metrics)`: drops rows with a null target, builds `X`/`y`, and — if there are `>= 50` rows — carves out a 20% holdout (`train_test_split`) to compute `holdout_mae`/`holdout_r2` on a cloned probe model, always measured against the **raw, unclipped** holdout labels (clipping only ever touches what the model trains on, never what it's judged against — keeping reported metrics an honest read of real-world error). The final production model is then fit on the *full* dataset (train+holdout) with clipped labels.
- `train(conn, fmt, gender) -> dict`: builds the full training table (`features/historical.build_training_table`), fits both targets via `_fit_one(..., gender)`, dumps each model (`joblib.dump`) into the per-`(gender, fmt)` artifacts directory, writes `training_metadata.json` recording `trained_at`, `n_rows_total`, `date_range`, feature lists, and per-target metrics, then calls `_save_background` (below).
- `_save_background(table, artifacts_dir)`: samples `min(SETTINGS.shap_background_size, len(table))` rows of `MODEL_FEATURES` and `joblib.dump`s them as `BACKGROUND_FILENAME` — the SHAP background sample described below, factored out so it can be rebuilt independently of a full retrain.
- `rebuild_background(conn, fmt, gender) -> dict`: rebuilds *just* `shap_background.joblib` for an already-trained scope, without refitting or overwriting the models themselves. Exists for artifact sets saved before `BACKGROUND_FILENAME` existed — without it, the `bowling_wpa` `VotingRegressor`'s Permutation-based SHAP path (see `shap_explain.py`) has no background to permute against, so every all-rounder/bowler silently lost their bowling-side "Feature impact" breakdown until this is run once. Wired to the CLI's `train --background-only` flag (see `cli.py`).
- `load_models(fmt, gender) -> dict[str, object]` / `load_metadata(fmt, gender) -> dict | None`: simple joblib/json loaders scoped the same way, returning an empty dict / `None` if artifacts don't exist yet (used by `score.py` to detect "no trained model available" cold-start).
- `load_background(fmt, gender) -> pd.DataFrame | None`: loads the SHAP background sample back, returning `None` if training hasn't produced one yet (older artifacts, or never rebuilt) — every caller treats a missing background as "SHAP unavailable for the non-Pipeline sub-estimator" rather than raising.

**How it connects:** Imports `features/historical.build_training_table`, `features/schema` (`CATEGORICAL_FEATURES`, `MODEL_FEATURES`, `NUMERIC_FEATURES`, `TARGETS`), and `config` (`RECOMMENDATION_ARTIFACTS_DIR`, `SETTINGS`, `ensure_dirs`). Its `load_models`/`load_metadata` are called directly by `recommend/score.py`'s `RecommendationScorer.__init__`; `rebuild_background` is called only via `cli.py`'s `train --background-only` path.

**Why the SHAP background sample exists at all:** needed by `shap_explain.py`'s permutation-based explainer for the `bowling_wpa` model's `HistGradientBoostingRegressor` sub-estimator (a non-tree-path-based SHAP method needs a reference/background distribution to permute against; the `RandomForestRegressor` half doesn't need one, since `TreeExplainer` reads the tree structure directly).

### `model-training/criiq_models/recommend/shap_explain.py` *(new)*

**Purpose:** Computes **SHAP (SHapley Additive exPlanations)** values for a single player's WPA prediction — "of this player's predicted win-probability-added, how many percentage points came from their career strike rate vs. their recent form vs. their opponent history, etc." This is a genuinely different kind of explainability from `recommend/explain.py`'s plain-English narrative: SHAP is a formal, game-theoretically-grounded attribution method (each feature's contribution is its average marginal effect across every possible ordering of "adding" features to a baseline prediction), so the numbers here are additive and exact (`base_value + sum(contributions) == predicted_value`), not a heuristic summary.

**Key pieces:**

- `_feature_groups(transformed_names)`: after a `ColumnTransformer` one-hot-encodes `role_bucket`, SHAP naturally computes one value per *encoded* column (e.g. `role_bucket_bowler`, `role_bucket_batter`, ...) — this regroups those back into one combined contribution per *original* `MODEL_FEATURES` name, since "role_bucket contributed +0.02" is the answer a caller actually wants, not four separate fragments of it.
- `_pipeline_shap(pipeline, X)`: the tree-based path — `shap.TreeExplainer(model, feature_perturbation="tree_path_dependent")` reads the `RandomForestRegressor`'s actual tree structure directly (fast, exact, no background sample needed). Used for `batting_wpa` (always a Pipeline) and for `bowling_wpa`'s RF sub-estimator.
- `_categorical_vocab(voting_regressor)`: pulls the fitted `OneHotEncoder`'s learned category lists out of whichever sub-estimator has one — needed to consistently encode/decode `role_bucket` for the *other* sub-estimator, which isn't a `Pipeline` and has no encoder of its own.
- `_hist_gradient_boosting_shap(model, X, background, vocab)`: `HistGradientBoostingRegressor` isn't tree-path-explainable the same way (it natively handles the categorical column itself, with no separate one-hot step to introspect), so this uses `shap.explainers.Permutation` instead — a **model-agnostic** SHAP method that repeatedly perturbs each feature against a background sample and measures the prediction change. Requires manually encoding `role_bucket` to a numeric code and decoding it back inside a local `_predict` closure, since the permutation explainer only works with plain numeric arrays.
- `_voting_regressor_shap(model, X, background)`: `bowling_wpa`'s shipped model is a `VotingRegressor` of the two sub-estimators above — this computes each sub-estimator's SHAP values independently, then combines them via the *same weights* the `VotingRegressor` itself uses to average predictions (defaulting to equal weights if none were set), so the combined SHAP values sum to exactly the combined model's actual prediction, preserving the "attribution is exact" property end to end.
- `compute_shap_values(model, X, background=None) -> (values, base_value)`: dispatches on `type(model)` — `Pipeline` → `_pipeline_shap`, `VotingRegressor` → `_voting_regressor_shap`, else raises `TypeError` (a deliberate fail-fast rather than a silent wrong answer if a future model type is ever swapped in without updating this module).
- `explain_prediction(models, feats, background=None) -> dict`: the public entry point — for each target (`batting_wpa`, `bowling_wpa`) in `models`, builds a one-row feature frame and calls `compute_shap_values`, then returns `base_value`, `predicted_value` (`base_value + sum(contributions)`, an exact reconstruction, not a re-prediction — this is what makes it verifiable rather than just plausible-looking), the full per-feature `contributions` dict, and a `top_contributions` list (the `SETTINGS.shap_top_features` largest-magnitude features, positive or negative) for a UI that only wants to show the few features that actually mattered.

**How it connects:** Imports `config.SETTINGS`, `features/schema` (`CATEGORICAL_FEATURES`, `MODEL_FEATURES`, `NUMERIC_FEATURES`), and the third-party `shap` library. Called directly from `cli.py`'s `cmd_recommend` (per-XI/pool-player breakdown, gated on `--shap`) and `cmd_explain` (single-player breakdown, same flag) — never called from `score.py`/`train.py` themselves, since SHAP is purely an *explanation* of an already-trained model's prediction, not part of scoring or fitting.

### `model-training/criiq_models/selection/optimize.py`

**Purpose:** Solves constrained playing-XI selection as an exact 0/1 linear program via `scipy.optimize.milp`, instead of naive top-11-by-score (which can produce e.g. 9 batters/2 bowlers or zero openers) or ad-hoc greedy-with-quotas (which can lock in a suboptimal pick early with no way to backtrack). Also handles ordering the selected XI into a realistic batting lineup, splitting a pool into role-based views, surfacing specialist-archetype standouts the composite score buries, and scoring/validating a coach's own hand-picked XI against the same rules.

**Key pieces:**

- `is_opener(p, threshold=SETTINGS.opener_position_threshold) -> bool`: `batting_position_median <= threshold`.
- `slot_category(p, opener_threshold) -> str`: returns `"opener"`, `"bowler_tail"` (if `role_bucket == "bowler"`), or `"core_batting"` — the same partition used both for team-sheet ordering and for finding "the next-best alternative in this role" in `explain.py`.
- `_capability_masks(scored_players, opener_threshold)`: builds four parallel `np.array` masks (batting-capable, bowling-capable, is-keeper, is-opener) over the player list — these become the MILP's constraint coefficient vectors.
- `_greedy_fallback(scored_players, xi_size, min_bat, min_bowl, min_keeper, min_opener, opener_threshold) -> list[dict]`: used only if `milp` fails to find a feasible solution (e.g. an extremely thin bowler pool). Starts from the raw top-`xi_size` by score, then for each constraint in turn (`_fix`), repeatedly swaps in the best-scoring qualifying bench player for the worst-scoring non-qualifying XI member until the minimum is met or no more candidates exist.
- `_team_sheet_order(xi, opener_threshold) -> list[dict]`: presents a *selected* XI (who's in) in a realistic batting-lineup *order* (who bats where) — a deliberately separate concern from selection itself.
  - Splits the XI into `openers_pool` (opener-capable, sorted by score desc), `bowler_tail` (bowler role, sorted by score desc), and `core` (everyone else, sorted by score desc) using `slot_category`.
  - The top 2 from `openers_pool` take slots 1–2 outright; any *additional* opener-capable player (`overflow_openers`, e.g. a squad with 3 strong openers) is folded back into `core` and re-sorted by score — she does not automatically get slot 3 just because of her opener tag, matching how real teams actually bat a surplus opener based on overall output.
  - If fewer than 2 opener-capable players exist in the XI (sparse batting-position data), the best remaining `core` players are pulled up to fill slots 1–2, so "who opens" is never left undefined.
  - Final order: `openers + core + bowler_tail`.
- `role_pools(scored_players) -> dict`: splits into `{"batters", "all_rounders", "bowlers", "unknown"}` via `_ROLE_POOL_KEYS`, each independently sorted by `-score` — a presentation view; explicitly does not change what `select_xi` picks.
- `SPECIALIST_ARCHETYPES = ("finisher", "power hitter", "anchor")`; `_highlight_metric(arch, inp)`: the role-*defining* metric to rank by — `bat_best_phase_sr` for finisher (their best phase is presumed to be the death overs), `bat_six_rate` for power hitter, and `None` (falls back to composite score) for anchor. Explicitly *not* the composite score for finisher/power-hitter, since that composite is WPA-based and would just re-bury the exact players this function exists to surface.
- `role_highlights(scored_players, archetypes=SPECIALIST_ARCHETYPES) -> dict`: for each archetype, finds the pool member with that `components.inputs.archetype` maximizing `(highlight_metric, score)` as a tiebreak tuple. The docstring cites a concrete real case: a genuine finisher (RM Ghosh, death-overs SR ~166) rates low on the WPA-based composite score and would otherwise fall entirely outside the headline shortlist — this answers "who's our best finisher" directly by finishing quality, independent of composite rank.
- `MIN_FIELDING_MATCHES_FOR_RATE = 5`: below this many matches, a dismissals-per-match fielding rate is too noisy to rank on. Mirrors `data-collection/criiq_data/fielding.py`'s and the backend's own copies of the same constant (kept in sync by hand across the three packages, which deliberately don't import each other).
- `_fielding_rank_value(inp) -> float`: `fielding_dismissals_per_match` if `fielding_matches >= MIN_FIELDING_MATCHES_FOR_RATE` and the rate is available, else the raw `fielding_dismissals` count as a fallback for a thin sample.
- `best_fielder(scored_players) -> dict | None`: the pool member with the single strongest fielding record (catches + run-outs + stumpings), ranked via `_fielding_rank_value`. Returns `None` if nobody in the pool has any recorded fielding dismissal — a 0-dismissal player is "nobody stood out," not "the best fielder by default." Feeds `explain.py`'s "sharpest fielder in this pool" callout (`is_best_fielder=True`) via `cli.py`.
- `analyze_xi(scored_players, player_ids, settings=SETTINGS) -> dict`: scores a **specific, already-chosen** XI (e.g. a coach's manual pick) against identical constraints to `select_xi`, and reports how it compares. Looks up each requested id in `scored_players`, collecting any not found into `missing_player_ids` rather than dropping silently or raising. Computes `required` constraints the same soft-degradation way `select_xi` does (capped at what the *whole pool* can actually satisfy, for an apples-to-apples comparison), counts what the chosen XI actually has, and lists any `violations` (wrong size, insufficient batting/bowling-capable, no keeper, insufficient openers). Then calls `select_xi` internally to get the true optimum, and reports `score_gap`, players in the optimal XI but not chosen, and vice versa.
- `select_xi(scored_players, settings=SETTINGS) -> dict`: the main solver.
  - Ranks all players by score descending; `xi_size = min(settings.xi_size, n)`.
  - Computes capability masks and each minimum requirement, **soft-degraded** to what the pool can actually supply (`min(settings.min_X, mask.sum())`) — e.g. if the pool has zero flagged keepers, the keeper requirement silently becomes 0 rather than making the MILP infeasible; same for openers.
  - Builds the MILP: `c = -scores` (minimize negative score = maximize score), one equality constraint pinning the selected count to exactly `xi_size`, and four `>=` inequality constraints (batting-capable, bowling-capable, keeper, opener counts) using the mask vectors as constraint coefficients. `Bounds(0, 1)` with `integrality=np.ones(n)` makes every decision variable a binary 0/1 choice.
  - If `milp` succeeds, the XI is every player with `result.x[i] > 0.5`. If it fails, falls back to `_greedy_fallback`.
  - Runs `_team_sheet_order` on the result, then builds a `pool` for display: the top `settings.pool_size` by score, *plus* any XI members not already in that slice (so the selected XI is always fully represented in the returned pool even if a constraint-driven pick — most commonly the keeper, often the weakest all-round scorer by design since keeping isn't captured by the batting/bowling model — falls outside the display cutoff). The docstring stresses the MILP runs over the *entire* candidate list, never a pre-truncated top-N slice, since truncating before optimizing could silently zero out the very constraint it exists to enforce.

**How it connects:** Imports `config.SETTINGS` and `features/common.py` (`batting_capable`, `bowling_capable`). Consumes the output of `recommend/score.py`'s `score_many` (each player dict needs at minimum `player_id`, `score`, `role_bucket`, `is_keeper`, `batting_position_median`). Its output (`select_xi`, `analyze_xi`, `role_pools`, `role_highlights`) feeds `recommend/render.py` and the CLI.

### `model-training/criiq_models/simulate/engine.py`

**Purpose:** The ball-by-ball T20 match engine — the core Monte Carlo simulator everything else in `simulate/` builds on. It reproduces real T20 mechanics documented in `rulebook-cricket.md`: 20 overs, 6 legal deliveries per over (wides/no-balls replayed and not counted), a bowler capped at 4 overs and barred from bowling two overs consecutively (Law 17.6 / ICC PC cl. 13.9.1), free hits after no-balls with restricted dismissal modes, byes/leg-byes counted as legal balls but never credited to the striker or debited to the bowler, correct end-of-over strike rotation, and innings-ending conditions (all-out, overs-complete, or target chased). It explicitly documents scope limits it does NOT model: reduced/rain-shortened-innings bowler-overs rules and DLS, and — inherited from `outcomes.py`'s single-bucket-per-delivery model — a wicket can never coincide with a wide/no-ball in this engine (real but rare cases like stumped-off-a-wide are not modelled).

**Key pieces:**

- Constants: `MAX_OVERS=20`, `MAX_OVERS_PER_BOWLER=4`, `BALLS_PER_OVER=6`, `TOTAL_LEGAL_BALLS=120`; Super Over constants `SUPER_OVER_OVERS=1`, `SUPER_OVER_MAX_WICKETS=2`, `MAX_SUPER_OVER_ROUNDS=10` (a documented, extremely-unlikely bounded fallback to a bare "Tie" result — real cricket plays Super Overs indefinitely, but an unbounded loop here risks hanging on a pathological outcome model).
- `MatchState` (dataclass): all mutable per-innings state — `batting_order`, `target`, `max_wickets`, `striker_idx`/`non_striker_idx`/`next_batter_idx`, `score`, `wickets`, `over`/`ball_in_over`/`balls_bowled`, `free_hit`, `all_out`, `out` (set of dismissed ids), and running per-bowler (`bowler_balls`, `bowler_runs_conceded`, `bowler_wickets`) and per-batter (`batter_runs`, `batter_balls`) tallies, plus `last_over_bowler`. Properties: `striker` (name lookup by index), `balls_remaining`, `chase_won()` (`target is not None and score >= target`), `wickets_exhausted()`, `is_over()` (all-out OR chase won OR wickets exhausted).
- `select_bowler(bowler_pool, bowler_balls, last_over_bowler, rotation=None, over_idx=None, ..., bowler_profiles=None, max_overs=20) -> str`: the bowler-scheduling logic, with two modes:
  - **Explicit rotation** (e.g. from `ga_bowling.optimize_bowling_rotation`): the pre-decided bowler for this over is looked up (`rotation[over_idx]`), but *still validated* — raises `ValueError` if it would mean bowling consecutive overs (Law 17.6) or exceeding the 4-over cap (ICC PC cl. 13.9.1). An illegal rotation is never silently applied.
  - **Auto-scheduling** (no rotation given): first filters to `eligible` bowlers (not the last-over bowler, under their overs cap). If none are eligible, raises with a message telling the caller the minimum bowler-pool size needed (`ceil(20/4) = 5`). Then it decides between two selection strategies:
    - This isn't a simple two-way branch on `bowler_profiles` — there are three distinct cases, and the doc previously conflated the last two:
      1. **`bowler_profiles` given *and* genuine spare capacity** (`has_slack`, computed fresh each over from actual remaining bowler capacity vs. actual overs remaining, not a static pool-size check — avoiding a legal deadlock): sorts by `(_tier(b, phase), overs_bowled_so_far)` — tier *first*, overs-bowled only as the tiebreak. Prefers whoever has the best (lowest) `phase_rank` for the *current over's phase* (powerplay/middle/death), i.e. a captain's real best death bowler bowls the death overs. `_tier` ranks candidates into three tiers: tier 0 = genuinely their best phase (their rank here equals their minimum rank across all phases — use them now); tier 1 = no phase-rank data at all (a safe neutral option, doesn't "waste" a specialist's overs on the wrong phase); tier 2 = a specialist in some *other* phase (real captains hold such bowlers back rather than burning quota outside their specialty, so a neutral bowler is tried first when available).
      2. **`bowler_profiles` given but *no* slack** (capacity is tight enough that legality must come first): sorts by `(overs_bowled_so_far, _tier(b, phase))` — the *reverse* priority of case 1. Overs-bowled decides first (so the innings can still legally complete), and phase tier is only a tiebreak between two bowlers who are equally rested — phase preference doesn't vanish entirely here, it's just subordinate to legality.
      3. **No `bowler_profiles` at all**: plain fewest-overs-bowled-so-far with no tiering, which naturally round-robins through the whole pool. This is the *only* case that's truly "no phase awareness."
- `_classify_and_apply(outcome, sampled_runs) -> dict`: translates one of the outcome-model's string buckets (`"wide"`, `"noball"`, `"bye"`, `"wicket"`, or a run-value string) into `{is_legal, extras, is_wicket, next_free_hit, runs_off_bat}` — the mechanical rules layer sitting on top of the probabilistic outcome model.
- `simulate_ball(state, bowler_id, outcome_model, batter_profiles, bowler_profiles, rng, forced_dismissal=None) -> dict`: simulates one delivery.
  - Checks `forced_dismissal` (used by "what if this player got out at over X, ball Y" scenario analysis) — if it matches the current striker/over/ball exactly, forces a `"wicket"` outcome instead of sampling from the model.
  - Otherwise samples an outcome from `outcome_model.sample(...)`.
  - Applies the classification, updates score/wicket/ball counters (legal balls only advance `balls_bowled`/`ball_in_over`/`bowler_balls`/`batter_balls`), and correctly excludes byes from the bowler's runs-conceded tally (rulebook §4.3) while still crediting the wide/no-ball penalty run and any bat runs to the bowler.
  - **Strike rotation**: swaps striker/non-striker if the delivery was legal, not a wicket, and the total runs scored is odd (covers both bat runs and odd byes).
  - **Wicket handling**: if a wicket falls, the next batter from `batting_order` comes in (`next_batter_idx`); if there are no more batters, sets `all_out=True`.
  - Returns a full per-ball record dict (used to build the ball-by-ball log DataFrame).
- `simulate_over(...)`: loops `simulate_ball` up to 6 legal-ball-equivalents or until `state.is_over()`, then — if the innings isn't over — swaps ends (non-striker faces first next over, regardless of the last ball's runs), increments `state.over`, and records `last_over_bowler`.
- `simulate_innings(batting_order, bowling_pool, outcome_model, batter_profiles, bowler_profiles, target=None, rotation=None, forced_dismissal=None, rng=None, max_overs=20, max_overs_per_bowler=4, max_wickets=None)`: the per-innings driver. Validates `rotation` length matches `max_overs` and that `batting_order` has at least 2 players. Builds a fresh `MatchState` (innings 2 if a `target` is given, else innings 1), then loops over `range(max_overs)`, breaking early if `state.is_over()`, calling `select_bowler` then `simulate_over` each iteration. Returns `(state, ball_log_df)` — the ball log as a pandas DataFrame with a sequential `ball_seq` column added.
- `simulate_super_over(bat_first, bowl_first, outcome_model, batter_profiles, bowler_profiles, rng) -> dict`: one over each side, `max_wickets=2` (innings ends early on 2 wickets, not all-out). Documented simplification: uses each side's *full* main-match batting order/bowling pool rather than the real rule restricting eligibility to nominated, not-yet-dismissed players — reasonable for a single Super Over, understates restrictions in a repeated (re-tied) one.
- `super_over_win_probabilities(team1, team2, batting_first, outcome_model, batter_profiles, bowler_profiles, n_reps=200, rng_seed=None) -> dict`: runs `n_reps` independent Super Overs and tallies win frequency per side plus Tie — a standalone estimator, independent of whether a full match actually tied.
- `_attach_win_prob(ball_log_df, winprob, innings, target=None) -> pd.DataFrame`: for every row in the log, computes `balls_remaining` and (if chasing) `runs_required`, then calls `winprob.predict_one(...)` per row to attach a `win_prob_batting` column (win probability from the *currently batting* side's perspective).
- `simulate_match(team1, team2, batting_first, outcome_model, batter_profiles, bowler_profiles, winprob, forced_dismissal=None, n_reps=1, rng_seed=None) -> list`: the top-level two-innings match driver. `team1`/`team2` are dicts `{"name", "batting_order": [11 ids], "bowling_pool": [...], "rotation": optional}`. For each of `n_reps` Monte Carlo repetitions: simulates innings 1, attaches win-prob, computes `target = score+1`, simulates innings 2 with that target, attaches win-prob (chase perspective). Decides the winner: if the second innings reaches or passes target, bowling-first team wins; if it falls exactly one run short (`target-1`), it's a genuine tie resolved by one or more Super Overs (the side that batted second in the main match bats first in the first Super Over per Appendix F para 11; each repeat swaps who bats first per para 19), looping up to `MAX_SUPER_OVER_ROUNDS`; otherwise the batting-first team wins outright. `winner="Tie"` only ever appears in the final returned dict in the documented extremely-unlikely case of exhausting all Super Over rounds without a decisive one. Each rep's dict includes both innings' logs, scores, target, winner, and `super_over_rounds` (list of each Super Over played, if any).

**How it connects:** Imports `outcomes._phase` (phase classification by over number). Consumed by `ga_batting.py` and `ga_bowling.py` (both call `simulate_innings` repeatedly as their GA fitness function), and by the CLI's match-simulation command (via `simulate_match`). `report.py` and `scorecard.py` and `keymoments.py` all operate on the `ball_log_df` this module produces.

### `model-training/criiq_models/simulate/ga_batting.py`

**Purpose:** A genetic algorithm that searches over **batting order** (which player bats where), given an already-chosen XI — the one combinatorial decision neither the exact-MILP squad selector (`selection/optimize.py`, which picks *who* is in the XI) nor `ga_bowling.py` (which searches bowler rotation) can express. Complements them rather than duplicating their job.

**Key pieces — GA mechanics walked through in detail:**

- **Chromosome representation**: an individual is a *list of permutations*, one per batting-order "group" (`_random_individual` returns `perms: list[list[player_id]]`), not a single flat 11-player permutation. `batting_groups` is an ordered list of player-id groups passed in by the caller, e.g. `[[opener_a, opener_b], [top_middle_1..N], [tail_1..M]]`. This encodes real batting-order structure directly into the search space: the openers group (size 2) can interchange who takes strike first, the middle order rotates among itself, and the tail fills out the rest — but the GA can never move a player across a group boundary (an opener can't suddenly bat at 10). Passing a single group containing all 11 players recovers a fully unconstrained search. `_full_order(group_perms)` concatenates the groups' permutations in order to get the actual batting order used by `simulate_innings`.
- **Population initialization**: `_random_individual()` shuffles each group's player list independently via `rng.shuffle`; the initial `population` is `pop_size` (default 40) such random individuals.
- **Fitness function**: `_fitness(order, bowler_pool, outcome_model, batter_profiles, bowler_profiles, target, rng, n_reps)` runs `simulate_innings` `n_reps` times (default 8) with this batting order and averages the result — if a `target` is given (chasing scenario), fitness is the **win probability** (fraction of reps where `score >= target`); otherwise it's the **expected final score**. This makes fitness explicitly noisy (a Monte Carlo mean over a handful of reps), which the module's protection mechanisms below are built to handle.
- **Crossover — Order Crossover (OX)**: `_ox_crossover(a, b, rng)` picks two random cut points `i < j`, copies the slice `a[i:j]` verbatim into the child at the same positions, then fills the remaining `None` slots in left-to-right order with whichever elements of `b` are *not already in the child* (preserving `b`'s relative order among the leftover elements). This is the standard permutation-preserving crossover — a naive single-point crossover on two permutations would produce a child with duplicate/missing players, which OX structurally cannot do. `_crossover(a, b)` (in `optimize_batting_order`) applies `_ox_crossover` independently per group via `zip(a, b)`.
- **Mutation**: `_swap_mutate(order, rng, rate=0.2)` — with probability `rate`, swaps two random positions within the permutation (a single random transposition); otherwise the order is returned unchanged. Applied per-group via `_mutate`.
- **No repair needed**: unlike `ga_bowling.py`, no legality repair step exists here — because OX and swap-mutation both operate strictly *within* each fixed-membership group, every resulting individual is automatically a valid permutation of that group; there's no way to produce an "illegal" batting order under this representation.
- **Selection / generational loop** (`optimize_batting_order`): each generation, every individual in `population` is scored via `_fitness_of` (using the modest `n_reps`), sorted descending. If the top individual's fitness beats the running `best_fitness`, it is **re-verified** with `n_reps * _VERIFY_REP_MULTIPLIER` (3x more) reps before being accepted as the new `best` — protecting against a lucky noisy evaluation being mistaken for a genuine improvement. `fitness_history` logs the running best-known fitness each generation (monotonically non-decreasing by construction, since `best`/`best_fitness` only ever improve). Survivors are the top `max(2, pop_size//2 - 1)` scored individuals, **plus** `best` appended explicitly (elitism: the true best-known individual can never be dropped from the gene pool even if it scores worse on an unrelated noisy re-evaluation this generation). Children are bred by picking two random survivors, applying `_crossover` then `_mutate`, until the population is refilled to `pop_size`.
- After all generations, `final_fitness` is computed with an even larger rep count (`max(30, n_reps * _VERIFY_REP_MULTIPLIER * 2)`) for a stable final reported number.
- Returns `{"batting_order": full flattened order, "batting_groups": best per-group perms, metric_name: final_fitness, "fitness_history": history}` — `metric_name` is `"win_probability"` if a `target` was given, else `"expected_score"`.
- `_validate_groups(batting_groups)`: rejects empty group lists, duplicate players across groups, or fewer than 2 total players.

**How it connects:** Imports `simulate_innings` from `engine.py` as its fitness evaluator. Called by the CLI's batting-order-optimization command; consumes `outcome_model`/`batter_profiles`/`bowler_profiles` built by `outcomes.py`.

### `model-training/criiq_models/simulate/ga_bowling.py`

**Purpose:** A genetic algorithm that searches over **legal bowler-to-over rotations** (which bowler bowls each of the 20 overs), respecting Law 17.6 (no consecutive overs) and ICC PC cl. 13.9.1 (max 4 overs per bowler) — a sequencing constraint that depends on every earlier choice in the sequence, which the exact-MILP selector (a single "pick 11 from a pool" decision) cannot express. The central design choice, stated explicitly in the docstring: every candidate rotation produced by crossover/mutation is **repaired back to a rules-legal rotation, never merely penalized** — so fitness always reflects an actually-playable match, and the GA never wastes search effort evaluating an illegal sequence.

**Key pieces — GA mechanics walked through in detail:**

- **Chromosome representation**: a flat length-20 list, one bowler id per over — `rotation[over_idx]` is who bowls over `over_idx`.
- **`primary_bowlers` bias**: an up-to-5-strong list of "recognized specialist" bowlers passed in by the caller. The module explicitly departs from an even spread across every bowling-capable player: in a real T20 XI, the ~5 specialists share nearly all 20 overs (4 each), with an all-rounder/part-timer chipping in only occasionally, not as an equal competitor for overs. This bias is baked into initialization and repair (both prefer giving primaries the full quota), while **mutation still reassigns slots uniformly to any eligible bowler**, so a part-timer can still be "introduced" by mutation and evolve into the final result if genuinely better for this specific matchup. Passing `primary_bowlers=None` recovers the old even-spread behaviour.
- **Population initialization**:
  - `_even_quotas(bowler_pool, rng, max_overs_per_bowler, total_overs)`: distributes `total_overs` (20) as evenly as possible (`divmod`) across the pool, each capped at `max_overs_per_bowler` (4), randomizing *which* bowlers absorb the leftover "extra" overs each call (so repeated calls explore different quota splits) — raises if the pool can't legally cover the innings (`base > max_overs_per_bowler`).
  - `_quotas(bowler_pool, rng, primary_bowlers, ...)`: if `primary_bowlers` is given and their combined capacity (`len(primary) * 4`) is enough to cover all 20 overs, quotas go entirely to them via `_even_quotas`. If their capacity is *insufficient* (fewer than needed recognized bowlers — a real captain's forced situation), each primary bowls a full 4-over quota and the remaining overs (`total_overs - primary_capacity`) are spread evenly across the non-primary bowlers.
  - `_sequence(quotas, rng)`: converts a `{bowler: overs}` quota map into an actual legal over-by-over sequence, using a **greedy "most overs remaining, excluding the previous over's bowler"** algorithm — explicitly identified in the docstring as the standard, provably-correct solution to the classic "task scheduler"/"reorganize string" no-two-adjacent-equal problem, guaranteed to succeed whenever the largest quota is at most half the total (always true here, since a single bowler's 4-over cap is well under half of 20). At each step, among bowlers with remaining quota (excluding whoever bowled last), it picks the one with the most overs still remaining (ties broken randomly via `rng.integers`).
  - `_random_valid_rotation`: composes `_quotas` + `_sequence` to produce one legal random rotation; the initial `population` is `pop_size` (default 40) of these.
- **Fitness function**: `_fitness(rotation, batting_order, outcome_model, batter_profiles, bowler_profiles, rng, n_reps)` runs `simulate_innings` (with `rotation` passed through, and `bowling_pool = dict.fromkeys(rotation)` — deduplicated bowlers who actually appear) `n_reps` times and returns the **negative mean runs conceded** (negative so that "higher fitness = better," consistent with `ga_batting.py`'s convention of maximizing). The docstring justifies this proxy explicitly: restricting runs is exactly what a captain choosing a bowling rotation controls, and it avoids simulating a full two-innings match per fitness evaluation (an order of magnitude more expensive) for no extra signal about the rotation itself. No chase `target` is used — it's a single completed innings.
- **Crossover**: `_crossover(a, b, rng)` is single-point on the flat 20-length list: `a[:point] + b[point:]`, `point` random in `[1, 20)`. Unlike batting order, a bowling rotation is *not* a permutation (the same bowler can appear in many slots), so a simple positional crossover is valid here — but it can easily violate the no-consecutive-overs/4-over-cap rules at the splice point or elsewhere, which is why repair is mandatory afterward.
- **Mutation**: `_mutate(rotation, bowler_pool, rng, rate=0.15)` — independently, with probability `rate` per slot, replaces that over's bowler with a uniformly random pick from the *entire* `bowler_pool` (not just primaries) — this is the mechanism that lets a part-timer's slot get "tried."
- **Repair** (`_repair(rotation, bowler_pool, rng, primary_bowlers=None)`): the core legality-restoration step, run on every child after crossover+mutation.
  1. Count how many overs each bowler currently appears for in the (possibly illegal) rotation, capped at `MAX_OVERS_PER_BOWLER` per bowler — this becomes a starting `quotas` dict (anything above 4 for one bowler is simply truncated back down to 4, the excess becoming "shortfall").
  2. `shortfall = total_overs - sum(quotas)` — the overs that got truncated away and need to be reassigned elsewhere.
  3. If there's a shortfall, candidates are sorted by `(not in primary_set, current_quota)` — i.e. primaries with spare room are tried first, in order of how few overs they already have — and each is topped up (`take = min(room, shortfall)`) until the shortfall is exhausted; raises if the pool genuinely can't cover 20 overs even after this.
  4. Finally, `_sequence` re-derives an actually legal over-by-over sequence from the repaired quota map (random tie-breaking again). The docstring explains why this rebuild-from-quotas approach is used instead of a naive left-to-right patch: a naive patch can dead-end on a razor-tight pool even when the pool as a whole can legally cover 20 overs, whereas recomputing global quotas first and only then sequencing cannot.
- **Selection / generational loop** (`optimize_bowling_rotation`): raises immediately if `len(bowler_pool) * 4 < 20` (mathematically impossible to complete the innings legally, telling the caller the minimum pool size needed). Otherwise, structurally identical to `ga_batting.py`'s loop: score all `pop_size` rotations via `_fitness`, sort descending; if the top rotation beats `best_fitness`, **re-verify** with `n_reps * _VERIFY_REP_MULTIPLIER` reps before accepting it as the new best (same noise-protection rationale); `fitness_history` records the running best; survivors are the top half plus explicit elitism (`best` always re-appended); children are bred via `_crossover` → `_mutate` → `_repair` (repair is the mandatory final step every single child goes through, guaranteeing every member of the next generation is legal). Final reported fitness uses an even larger rep count (`max(30, n_reps * 3 * 2)`).
- Returns `{"rotation": best, "expected_runs_conceded": round(-final_fitness, 2), "overs_per_bowler": {...}, "fitness_history": history}`.

**How it connects:** Imports `MAX_OVERS`, `MAX_OVERS_PER_BOWLER`, `simulate_innings` from `engine.py`. Called by the CLI's bowling-rotation-optimization command; its `"rotation"` output is exactly the `rotation` argument `engine.simulate_innings`/`simulate_match` expect and validate against Law 17.6/the 4-over cap.

### `model-training/criiq_models/simulate/lineup_explain.py` *(new — added alongside the `--shap`/explainability work)*

**Purpose:** Answers "why is this the batting order / bowling rotation, and how much better is it than the obvious naive choice?" for the two GA optimizers (`ga_batting.py`, `ga_bowling.py`). Neither GA's raw output tells a coach *why* it's good — this module re-runs the exact same simulation metric against a deliberately naive baseline (sorted-by-strike-rate batting order; an even-overs-split bowling rotation) so the improvement is a real, measured number, not an assertion. It also does a lightweight sensitivity/counterfactual pass (adjacent-swap testing) and a simple heuristic "what to do if things go wrong" contingency plan for batting order.

**Key pieces:**

- `_phase_of_over(over_idx)`: same powerplay/middle/death boundary as `outcomes.py`, duplicated locally rather than imported (this module only needs the boundary values, not the whole outcome model).
- `_effective_strike_rate(profile, target)` / `_chase_strike_rate(profile)`: picks `chasing_strike_rate` when there's a chase `target`, else `setting_strike_rate`, else career `strike_rate` — mirrors the same innings-aware preference `outcomes.py`'s `distribution()` uses.
- `_batting_metric(order, bowler_pool, outcome_model, batter_profiles, bowler_profiles, target, rng, n_reps)`: runs `simulate_innings` `n_reps` times for a given batting order and returns either the mean score (no target) or the fraction of reps that reached the target (chase framing) — the identical metric definition `ga_batting.py`'s own fitness function uses, so the GA's chosen order and the naive baseline are compared on genuinely the same yardstick.
- `_naive_batting_order(batting_groups, batter_profiles, target)`: the baseline to beat — within each role band (openers/top-middle/tail), sort players by `_effective_strike_rate` descending. Deliberately the simplest defensible non-AI heuristic a coach might use by hand.
- `_group_bounds(batting_groups)`: converts the list-of-lists role bands into `(start_idx, end_idx)` index ranges into the flat batting order — used both to baseline-sort and to restrict adjacent-swap testing to swaps *within* a band (swapping across a band boundary isn't a meaningful "was this the right micro-decision" question, since the bands themselves are a separate modeling choice).
- `_contingency_plan(batting_order, batting_groups, batter_profiles)`: a **strike-rate-only heuristic**, explicitly labelled as such in its own docstring — not a re-run of the simulator. Finds the batter with the lowest career strike rate among the "promotable" middle positions (best suited to rebuild after an early collapse) and the batter with the highest chasing strike rate among the same range (best accelerant to send in early during a chase) — reported with plain-language `reason` strings, not just numbers.
- `explain_batting_order(batting_order, batting_groups, bowler_pool, outcome_model, batter_profiles, bowler_profiles, target, chosen_metric, metric_name, rng_seed=None, n_reps=24) -> dict`: the main entry point.
  1. Computes `baseline_metric` for `_naive_batting_order`.
  2. For every **adjacent pair of positions within the same role band**, swaps them and re-measures the metric (`n_reps // 2`, since this is a sensitivity probe, not the headline number) — `adjacent_swaps` reports each swap's `delta` (swapped metric minus the chosen order's actual metric); the swap with the most negative delta is surfaced separately as `most_costly_adjacent_swap` ("if you were going to second-guess one thing about this order, this is the one that would hurt most").
  3. Returns `chosen_metric`, `baseline_metric`, `improvement_over_baseline`, the full `adjacent_swaps` list, `most_costly_adjacent_swap`, and the `contingency` plan from `_contingency_plan`.
- `_bowling_metric(rotation, batting_order, outcome_model, batter_profiles, bowler_profiles, rng, n_reps)`: same idea as `_batting_metric` but for a rotation — mean runs conceded across `n_reps` reps, using the deduplicated bowler set as the bowling pool (mirrors `ga_bowling.py`'s own fitness function exactly).
- `explain_bowling_rotation(rotation, batting_order, outcome_model, batter_profiles, bowler_profiles, overs_per_bowler, expected_runs_conceded, rng_seed=None, n_reps=24) -> dict`: baseline is an even-overs split via `ga_bowling.py`'s own `_even_quotas` + `_sequence` (reusing the GA's internal helpers directly rather than reimplementing the "generate a legal rotation" logic a second time). For each bowler actually used, cross-references which match *phases* their overs fell in against their real, pre-existing `phase_rank` (from `BowlerProfile`) — so the explanation can say something like "bowled 3 death overs, and is genuinely this team's #2-ranked death bowler," not just list raw over counts. Returns `baseline_runs_conceded`, `improvement_over_baseline`, and a per-bowler `phase_overs`/`phase_rank` breakdown.

**How it connects:** Imports `MAX_OVERS`/`MAX_OVERS_PER_BOWLER`/`simulate_innings` from `engine.py`, `_even_quotas`/`_sequence` from `ga_bowling.py` (the only cross-module reuse of a GA's private helpers in the whole `simulate` package), and `PHASES` from `outcomes.py`. Both entry points are called directly from `cli.py`'s `cmd_optimize_batting`/`cmd_optimize_bowling` (see that section's note below) whenever `--explain` is passed, and their output is JSON-serialized alongside the GA's own result.

### `model-training/criiq_models/simulate/outcomes.py`

**Purpose:** The probabilistic per-delivery outcome model that `engine.py`'s `simulate_ball` samples from. Builds an empirical phase-conditioned (powerplay/middle/death) outcome distribution from real ball-by-ball data, then adjusts it per-delivery for the specific batter's strike rate, the specific bowler's economy/wicket rate, and any real recorded head-to-head history between them — shrinking every adjustment back toward the phase-empirical prior so a small sample can't distort the distribution wildly.

**Key pieces:**

- `OUTCOMES = ("0","1","2","3","4","6","wicket","wide","noball","bye")`: the fixed bucket set every delivery is classified into exactly one of (documented limitation: a wicket never coincides with a wide/no-ball here, since that's not one of the enumerated bucket combinations).
- `_phase(over) -> str`: `over <= 5` → `"powerplay"`, `over <= 14` → `"middle"`, else `"death"` — the phase boundary logic reused directly by `engine.py`.
- `_classify_row(runs_off_bat, extras, wides, noballs, wicket_type) -> str`: classifies one real historical delivery row into an `OUTCOMES` bucket, checking wides first, then no-balls, then wickets, then byes (zero bat-runs plus positive extras), else the raw run value — folding rare running-run values (5, 7, ...) into the `"1"` bucket. Uses `pd.notna` rather than plain truthiness because pandas returns (truthy) `NaN` for SQL `NULL`.
- `build_phase_baseline_rates(conn, fmt, gender) -> dict`: reads every delivery for this `(fmt, gender)` from `deliveries` joined to `matches`, classifies each into a phase/outcome bucket, and returns `{phase: {outcome: empirical_frequency}}` — scoped strictly per gender, "never blended," matching every other model in the repo. Raises `ValueError` if no deliveries exist for the scope (points the caller at running the ingestion pipeline first). Falls back to overall (non-phase-specific) rates for any phase with zero rows of its own.
- `league_averages(conn, fmt, gender) -> dict`: average strike rate / economy used as the model's neutral reference point, computed from `player_match_impact` filtered to **recent** (`_LEAGUE_RECENT_YEARS = 2` years) and **qualified** (`_LEAGUE_MIN_BALLS_FACED=15`, `_LEAGUE_MIN_BALLS_BOWLED=18`) performances — explicitly chosen over an unfiltered all-time average, which the docstring notes understates the modern game (~99 SR all-time vs. ~126 for men's T20I once restricted to recent, settled innings). Falls back to hardcoded defaults (`_DEFAULT_LEAGUE_SR=120.0`, `_DEFAULT_LEAGUE_ECONOMY=7.5`) if no qualifying rows exist.
- `BatterProfile` (dataclass): `strike_rate`, plus optional venue-conditioned `setting_strike_rate`/`chasing_strike_rate` (shrunk toward the base rate; `None` unless a venue was supplied and the player has history there — engine picks setting vs. chasing by which innings is in progress).
- `BowlerProfile` (dataclass): `economy`, `wickets_per_match`, and `phase_rank` (dict, per-phase economy rank *within the bowler's own team*, used by `engine.select_bowler` for realistic rotation).
- `_venue_strike_rates(conn, player_id, fmt, venue_id, base_sr)`: looks up `player_by_venue` for real setting/chasing SR at this venue, shrinking each toward `base_sr` via `shrink(..., prior_strength=SETTINGS.shrinkage_prior_matches)` weighted by the player's real match count there. Returns `(None, None)` if no venue given or no row found.
- `build_batter_profile(conn, player_id, fmt, opponent="", venue_id=None) -> BatterProfile`: pulls `feats` from `build_model_features`, prefers `form_bat_sr` (recent form) over `career_bat_sr` if available, then layers in venue-conditioned rates.
- `_phase_ranks(conn, player_id, fmt) -> dict`: reads `player_phase.bowl_team_rank` per phase for this player.
- `build_bowler_profile(conn, player_id, fmt, opponent="") -> BowlerProfile`: same form-over-career preference pattern for economy and wickets-per-match, plus `_phase_ranks`.
- `build_player_profiles(conn, fmt, team1_ids, team2_ids, team1_name="", team2_name="", venue_id=None) -> (batter_profiles, bowler_profiles)`: builds **both** profiles for **every** player on both sides — including bowlers, since even a specialist bowler needs a batting profile as a tailender. Each side is profiled with the *other* side's name as `opponent`.
- `load_matchup_lookup(conn, fmt, ids_a, ids_b) -> dict`: `{(batter_id, bowler_id): {"balls","runs","dismissals"}}` from `dismissal_matchup` for every real recorded pairing between the two rosters — the same table `recommend/matchup_matrix.py` reads.
- `PlayerAdjustedOutcomeModel` (the model class the engine actually samples from):
  - `distribution(phase, batter, bowler, batter_id=None, bowler_id=None, free_hit=False, innings=None) -> dict`: starts from `phase_baseline[phase]` and adjusts it in sequence:
    1. **Effective strike rate**: uses the innings-appropriate venue-conditioned rate if available (`setting_strike_rate` for innings 1, `chasing_strike_rate` for innings 2), else falls back to overall `strike_rate`, else the league SR.
    2. **Boundary scaling**: `sr_factor = effective_sr / league_sr`; `econ_factor = bowler.economy / league_economy`; `boundary_scale = clip(sr_factor / max(econ_factor, 0.3), 0.4, 2.5)` — both the `4` and `6` bucket probabilities are multiplied by this factor. The clip range explicitly bounds how much an extreme record can distort the model.
    3. **Wicket adjustment**: `wkt_factor` starts from the bowler's `wickets_per_match` clipped to `[0.3, 2.5]`; if a real head-to-head pairing exists with `>= 6` balls, the observed dismissal rate is shrunk toward the phase-baseline wicket rate (`shrink(..., prior_strength=SETTINGS.shrinkage_prior_matches)`) and folded in as an additional multiplicative factor clipped to `[0.2, 4.0]`. `base["wicket"]` is scaled by the combined factor.
    4. **Free hit**: if `free_hit=True`, `base["wicket"]` is forced to `0.0` — only run-out/obstructing-the-field dismissals are legally possible off a free hit, neither of which this model buckets under `"wicket"`.
    5. **Renormalization**: wide/no-ball rates stay fixed at their phase-empirical values (`fixed = base["wide"] + base["noball"]`); every other bucket is rescaled proportionally so the whole distribution sums back to `1.0` given that fixed mass. A degenerate all-zero-remaining-mass edge case (only reachable if wicket was already zero and free-hit zeroed it too) falls back to a guaranteed dot ball.
  - `sample(...) -> str`: calls `distribution` then does a single categorical draw (`rng.choice(keys, p=probs)`), returning the bucket name string `engine._classify_and_apply` consumes.
- `build_outcome_model(conn, fmt, gender, team1_ids, team2_ids) -> PlayerAdjustedOutcomeModel`: convenience constructor wiring together `build_phase_baseline_rates`, `league_averages`, and `load_matchup_lookup` for a given matchup.

**How it connects:** Imports `features/common.shrink` and `features/current.build_model_features`, plus `config.SETTINGS`. Its `PlayerAdjustedOutcomeModel.sample` is called directly inside `engine.simulate_ball`; `build_batter_profile`/`build_bowler_profile`/`build_player_profiles` supply the `batter_profiles`/`bowler_profiles` dicts every simulate function requires; `BowlerProfile.phase_rank` is read by `engine.select_bowler`.

### `model-training/criiq_models/simulate/keymoments.py`

**Purpose:** Post-processes a simulated ball-by-ball log into a chronological list of commentary-style "key moments" — the user explicitly wanted the simulation to surface milestones the way real match commentary/scorecards do, not just a bare win-probability line chart. Everything here is derived purely from columns `engine.py` already tracks per ball; no additional state is introduced.

**Key pieces:**

- `_BATTING_MILESTONES = (50, 100, 150, 200)`, `_BOWLING_MILESTONES = (3, 4, 5)`.
- `_ordinal(n)`: standard "1st/2nd/3rd/4th..." English ordinal formatter, handling the 10–20 "teens" exception (11th, 12th, 13th, not "11st"/"12nd"/"13rd").
- `_batting_milestones(df, name_map)`: walks the log in order, keeping a running per-batter run total and a `crossed` set per batter; whenever the running total newly crosses a milestone threshold not already crossed, emits a moment (labelled "century"/"half-century"/the raw number).
- `_boundaries(df, name_map)`: emits one moment per ball where `outcome in ("4","6")`.
- `_bowling_milestones_and_hattricks(df, name_map)`: processed **per innings** (`df.groupby("innings")`), and critically only over the **legal deliveries subset** (`inn_df[inn_df["is_legal"]]`). The docstring explains precisely why: a hat-trick requires 3 wickets off 3 *consecutive legal* deliveries by the same bowler, and a wide/no-ball is not a "ball" in the formal sense (it's replayed and doesn't count toward the over per rulebook §4.1/§4.2) — so an intervening wide/no-ball between two wickets does *not* break a hat-trick under real cricket scoring convention, which is exactly why the sequence check must run over legal deliveries only, not the raw delivery stream. It tracks a running per-bowler wicket count (emitting 3/4/5-for milestones the first time crossed) and a sliding 3-ball window (`recent_wicket_bowlers`) checking whether the last 3 legal balls were all wickets by the same bowler — if so, emits a `"hat_trick"` moment. Only within-innings sequences count (T20 has one innings per side, so no cross-innings hat-tricks are possible or checked).
- `_biggest_swings(df, top_n, name_map)`: ranks the biggest single-ball win-probability changes. Critically, it first sorts chronologically and computes `.diff()` of `win_prob_batting` **grouped by innings** (`d.groupby("innings")["win_prob_batting"].diff()`) rather than across the whole log — the docstring explains `win_prob_batting` is relative to whichever team is *currently* batting, and that reference frame flips at the innings break, so an ungrouped `.diff()` would misreport the innings-1-to-innings-2 boundary as one giant artificial "swing" when it's really just two different reference frames being subtracted. Takes the top `top_n` (default 5) balls by `abs(delta_wp)`, and reports `win_prob_before`/`win_prob_after` by reconstructing "before" as `after - delta`.
- `detect_key_moments(ball_log_df, name_map=None, top_swings=5) -> list`: runs all four detectors and returns their concatenated result, globally sorted by `(innings, over, ball)`. Returns `[]` immediately for an empty/`None` log.

**How it connects:** Takes no upstream imports besides `pandas`; operates purely on the ball-log DataFrame `engine.simulate_match`/`simulate_innings` produce (specifically needs `striker`, `bowler`, `outcome`, `runs_off_bat`, `is_wicket`, `is_legal`, `over`, `ball_in_over`, `innings`, and `win_prob_batting`). Its output feeds `report.py`'s `plot_win_probability` (annotation markers) and `save_simulation_artifacts` (JSON summary), and `scorecard.py`'s `coach_perspective` narrative.

### `model-training/criiq_models/simulate/report.py`

**Purpose:** Charting and artifact-persistence layer for simulated matches — mirrors the same `parquet` + `*_meta.json`/`summary.json` persistence pattern `data-collection/criiq_data/winprob.py` already uses, writing under this package's own `artifacts/simulation/` directory. Turns raw simulation output into a saved win-probability chart plus machine-readable artifacts.

**Key pieces:**

- Headless-backend guard: `if "ipykernel" not in sys.modules: matplotlib.use("Agg")`. The comment documents a real, previously-live bug: unconditionally calling `matplotlib.use("Agg")` on import silently broke chart rendering inside `simulation_demo.ipynb` — even after adding `%matplotlib inline`, this module's import (running afterward in the same cell) switched the backend back to the non-interactive Agg backend, producing a `"FigureCanvasAgg is non-interactive"` warning. Checking for `ipykernel` in `sys.modules` reliably distinguishes "running inside a Jupyter kernel" (never force Agg) from "plain CLI invocation" (always force Agg, since there's no display server to assume).
- `SIMULATION_ARTIFACTS_DIR = ARTIFACTS_DIR / "simulation"`.
- `_MOMENT_MARKERS`: maps each `keymoments` moment type to a `(marker_shape, color)` pair for plotting — `batting_milestone`→circle/blue, `boundary`→dot/gray, `bowling_milestone`→triangle/red, `hat_trick`→star/purple, `turning_point`→diamond/orange.
- `_concat_match_log(rep) -> pd.DataFrame`: concatenates both innings' ball logs into one continuous DataFrame with a `match_ball_index` running across both innings, and re-expresses win probability as **`batting_first_team`'s** perspective throughout (`log2`'s `win_prob_team1_perspective = 1 - win_prob_batting`, since innings 2's `win_prob_batting` is from the chasing team's perspective) — so the resulting chart reads as one continuous story rather than the line flipping perspective at the innings break.
- `plot_win_probability(rep, out_path, scenario_rep=None, key_moments=None) -> Path`: plots the win-probability line (in %) for `batting_first_team` across the whole match, with a dotted vertical line at the innings break and a dotted horizontal line at 50%. If `scenario_rep` is given (e.g. a forced-dismissal counterfactual from `engine.simulate_match`), overlays a second dashed red trace for direct visual comparison. If `key_moments` is given, scatters a marker at each moment's approximate ball position (`over*6 + ball - 1`, offset by the innings-break index for innings 2), using `_MOMENT_MARKERS`, deduplicating the legend so each moment *type* appears only once regardless of how many instances occurred.
- `save_simulation_artifacts(rep, out_dir, key_moments=None, ga_history=None) -> dict`: writes the concatenated ball log to `ball_log.parquet`, and a `summary.json` with scores/wickets/target/winner, a trimmed version of `super_over_rounds` (dropping the bulky per-ball logs from each round, keeping only summary fields), the `key_moments` list, and optionally the `ga_history` (fitness-over-generations trace) if a GA optimization produced this match. Returns the two artifact paths.
- `aggregate_win_probability(reps) -> pd.DataFrame`: given multiple Monte Carlo `reps` (from `simulate_match(..., n_reps=N)`), aligns every rep's win-probability trace by `match_ball_index` and computes the mean, 10th, and 90th percentile band across reps. Handles reps of different lengths (a match ending early on all-out or a chase completed before ball 120) by forward-filling (`ffill`) each rep's last known value out to the longest rep's length — the docstring explains this is because "the outcome is already effectively decided by that point," so holding flat is the sensible extension rather than truncating or padding with NaN.

**How it connects:** Imports `config.ARTIFACTS_DIR`. Consumes `engine.simulate_match`'s rep dicts directly and `keymoments.detect_key_moments`'s output; used by the CLI's match-simulation and rotation/batting-order-optimization commands to produce chart PNGs and JSON/parquet artifacts (the latter optionally carrying a GA's `fitness_history`).

### `model-training/criiq_models/simulate/scorecard.py`

**Purpose:** Derives post-match batting/bowling scorecards and a coach's-eye narrative summary purely from a simulated ball log plus an optional player-name lookup — deliberately has zero team-specific logic anywhere, so the same functions work identically for any two sides, genders, or formats the engine can simulate.

**Key pieces:**

- `batting_scorecard(ball_log_df, name_map=None) -> list`: iterates the ball log in order, building one row per batter *in the order they came to the crease* (`order` list, appended the first time a `striker` id is seen). Tracks `runs`/`balls` per batter — balls-faced excludes wides (rulebook §6: `if row["outcome"] != "wide": balls[striker] += 1`) — and whether they were dismissed. Computes `strike_rate = round(100*runs/balls, 1)` (or `None` if zero balls faced). Highlight logic: any batter with `runs >= 100` gets `"Century! (...)"`, `>= 50` gets `"Half-century (...)"`; separately, the outright top scorer gets `"Top scorer (...)"` **only if** they didn't already get a century/fifty highlight; and among batters with `balls >= 10` ("settled" — enough of a sample to judge pace fairly), the highest-strike-rate batter gets `"Fastest scoring innings (SR ...)"` if not already highlighted for something else. A batter can end up with only one highlight even if they'd technically qualify for multiple, since each check is gated on `highlight is None`.
- `bowling_scorecard(ball_log_df, name_map=None) -> list`: one row per bowler, in order of first over bowled. `overs` is rendered in real cricket ball-count notation (`f"{b//6}.{b%6}"`, e.g. 3.4 = 3 overs and 4 balls). `runs_conceded` excludes byes (rulebook §4.3/§6: `if row["outcome"] != "bye"`). `economy = round(6*runs/legal_balls, 2)`. Highlight logic: the bowler with the most wickets (ties broken by *lowest* runs conceded, via the sort key `(wickets, -economy_or_999)`) gets `"Pick of the bowlers (W-for-R)"` only if `wickets > 0`; separately, among bowlers who bowled `>= 2` overs ("qualified"), the lowest-economy bowler gets `"Most economical (ER ...)"` if not already highlighted.
- `render_scorecard_text(team_name, batting_rows, bowling_rows, opponent_name) -> str`: fixed-width plain-text rendering of both scorecards, with each row's highlight (if any) appended as `-- {highlight}`.
- `bowling_rotation(ball_log_df, name_map=None) -> list`: one row per over (grouped by `over`, sorted chronologically), reporting the over's bowler, phase, legal balls bowled, runs conceded (byes excluded, same rule as above), and wickets.
- `bowling_phase_summary(rotation_rows) -> dict`: re-aggregates `bowling_rotation`'s per-over rows into `{phase: {bowler_name: {balls, runs, wickets, overs, economy}}}` totals.
- `render_bowling_rotation_text(team_name, rotation_rows, phase_summary) -> str`: renders the over-by-over rotation followed by a phase-grouped bowling summary (sorted within each phase by balls bowled descending).
- `coach_perspective(rep, key_moments, coach_team, name_map=None) -> str`: a short narrative from one specific team's point of view, generalizing to either side of `rep` with no hardcoded team names (`coach_bats_first = rep["batting_first_team"] == coach_team`). Reports the total set/chased, filters `key_moments` down to the ones relevant to `coach_team`'s batting innings and bowling innings specifically (matched by `innings` number, derived from `coach_bats_first`), and picks the single biggest `"turning_point"` moment (by `abs(win_prob_after - win_prob_before)`) as "the moment that decided it." Ends with a plain win/loss/tie sentence, calling out that a tie was "resolved by Super Over."

**How it connects:** Imports only `pandas`; operates purely on the `ball_log_df` produced by `engine.py`'s simulation functions and the `key_moments` list from `keymoments.detect_key_moments`. Its rendered text functions are what the CLI actually prints to the user after a simulated match.

### `model-training/criiq_models/simulate/winprob_reader.py`

**Purpose:** A local, read-only mirror of data-collection's `EmpiricalWinProb`/`probability_for_state` win-probability model (`data-collection/criiq_data/winprob.py`) — deliberately reimplemented here rather than imported, following the same architectural rule stated in `features/historical.py` and `roster.py`'s `_player_id_map`: this package never imports data-collection's own code, only mirrors the exact lookup logic locally so results are byte-identical to data-collection's own `criiq-data winprob` CLI output. The stated performance reason for a dedicated class here (vs. reusing data-collection's free function) is that the data-collection-side `probability_for_state` reloads all 5 grid files from disk on every single call — fine for a one-off CLI query, but far too slow if called once per simulated ball across an entire match.

**Key pieces:**

- `MODELS_DIR = ROOT_DIR.parent / "data-collection" / "data" / "models"`: reads the *same* persisted parquet grid files data-collection's win-prob training writes — this is the one place model-training reads a file data-collection produced, without importing its code.
- Bin-width constants: `_BALLS_BIN=6` (bin balls-remaining/balls-bowled by over), `_SCORE_BIN=10` (bin score by 10s), `_RR_CAP=30` (cap runs-required bins).
- `_chase_keys(df)` / `_set_keys(df)`: convert raw match-state columns into the discretized grid-lookup keys used by the persisted parquet tables — `_chase_keys` bins `(balls_remaining, wickets, runs_required)` into `(k_rem, k_wk, k_rr)` for second-innings lookups; `_set_keys` bins `(balls_bowled, wickets, score)` into `(k_bowled, k_wk, k_score)` for first-innings lookups. Wickets are clipped to `[0,10]`.
- `WinProbLookup`: holds `alpha`, `prior_chase`, `prior_set` (shrinkage parameters from the persisted metadata) and the four loaded grid DataFrames (`grids`).
  - `WinProbLookup.load(fmt, gender)`: reads `winprob_{fmt}_{gender}_meta.json` for the shrinkage parameters (raising `FileNotFoundError` with an actionable message — "run data-collection's `criiq-data winprob` first" — if missing), then loads all four grid parquet files: `chase_full`, `chase_coarse`, `set_full`, `set_coarse`. The full/coarse split is a two-tier fallback: `full` is the fine-grained 3-key grid; `coarse` drops the third key (`k_rr` or `k_score`) for a coarser, more densely-populated lookup when the fine cell has no data.
  - `_lookup(keys, full, coarse, full_cols, coarse_cols, prior)`: merges the query keys against the `full` grid first (left join on the full key columns); wherever that merge misses (`NaN`), re-merges just the missing rows against the `coarse` grid (fewer key columns, so more likely to have data); wherever *that* still misses, falls back to the raw `prior` (`prior_chase`/`prior_set`) — a strict three-tier fallback: exact fine-grained empirical cell → coarser empirical cell → global shrinkage prior.
  - `predict_one(*, innings, wickets, balls_remaining=None, runs_required=None, balls_bowled=None, score=None) -> float`: builds a single-row DataFrame from the given match-state kwargs, computes the appropriate key set (`_chase_keys` for `innings==2`, `_set_keys` otherwise), and looks it up via `_lookup` against the matching full/coarse grid pair and prior, rounding the result to 4 decimal places.

**How it connects:** Imports only `config.ROOT_DIR`. Its `WinProbLookup` instance is constructed once per `(fmt, gender)` by the CLI and passed as the `winprob` argument into `engine.simulate_match`, which calls `predict_one` once per ball via `_attach_win_prob` to populate the `win_prob_batting` column every downstream chart/report/key-moment function relies on.

### `model-training/criiq_models/venues.py`

**Purpose:** Resolves a human-typed ground name (as passed to the CLI's `--venue` argument) into the `venue_id` slug the rest of the pipeline actually keys on. Before this module existed, `--venue` required the pre-computed slug directly — a value nobody would know when typing a ground name by hand — so this bridges "what a coach types" to "what the database uses," reusing data-collection's `identity.normalise_venues`-produced `canonical_name` as the human-readable match target.

**Key pieces:**

- `find_venues(conn, name, limit=10) -> list[dict]`: a simple `SELECT DISTINCT venue_id, canonical_name FROM venues WHERE canonical_name LIKE '%name%' ORDER BY canonical_name LIMIT ?` fuzzy substring search.
- `resolve_venue(conn, name) -> (venue_id_or_None, candidates)`: the main entry point with four explicit outcomes:
  1. No `name` given → `(None, [])`, unchanged behaviour.
  2. Exactly one fuzzy match → auto-resolved to that `venue_id`.
  3. Zero matches → falls back to treating `name` itself as an already-valid raw `venue_id` (backward-compatible with any caller — scripts, tests — already passing the slug directly); `candidates` stays empty in this branch too.
  4. Multiple matches → returns `(None, candidates)` — deliberately **unresolved**, listing every match, so the caller can show a "did you mean X or Y?" prompt rather than silently guessing the top `LIKE` hit. The docstring explicitly ties this to a lesson learned elsewhere in the project's history: the CLI's `_find_player` once picked an unintended same-named player by silently taking the top match, and this module is built to not repeat that mistake.
- Documented data-quality caveat, not hidden: `normalise_venues` (on the data-collection side) only has curated aliases for a small set of grounds (`identity._VENUE_ALIASES`); everything else gets a crude `raw.split(",")[0]` canonical name, so fuzzy match quality varies by ground — this is exactly why surfacing every candidate matters instead of picking one confidently.

**How it connects:** Imports nothing from the rest of `criiq_models` besides the standard `sqlite3` connection convention; reads the `venues` table populated by data-collection's `identity.py`. Its `resolve_venue` is called by the CLI wherever a `--venue` argument needs turning into a `venue_id` before being threaded into `recommend/score.py`, `simulate/outcomes.py`'s venue-conditioned strike rates, etc.

## FAQ — the questions someone reading this code actually asks

The questions below are about *why the code is shaped the way it is* — for *why an algorithm/model was chosen* over an alternative (MILP vs. greedy, GA vs. brute force, two regressors vs. one, SHAP vs. a simpler importance ranking), see `ALGORITHMS.md`, which already answers those in depth with worked examples. This list is deliberately about implementation decisions inside the code itself, and about the system-wide "why is it built this way" questions (why a CLI at all, how a new player enters the pipeline, why data is scoped the way it is) — see `../WORKING.md`'s own FAQ for the system/architecture/data-scope side of this; the two lists don't overlap.

**Q: Why does `cli.py` accept both `--X-players` (fuzzy names) and `--X-player-ids` (raw ids) for the same argument, instead of picking one input format?**
Because the two real callers need different things: a person typing a command by hand wants to type a name, not look up an id first; a program calling the CLI programmatically (the backend, via `model_bridge.py`) already has real ids from its own database and shouldn't have to round-trip through fuzzy name matching (which can also be genuinely ambiguous — `_resolve_player_name`'s "did you mean" handling exists precisely because two different real players can share a short display name). `_resolve_player_list`/`_resolve_xi` accept either and resolve to the same internal representation (a list of `player_id`s) before anything downstream ever sees them.

**Q: Why does `roster.py` (`_player_id_map`) duplicate `data-collection/criiq_data/identity.py`'s player-identity-resolution logic instead of importing it?**
Same answer as data-collection re-use generally (see `WORKING.md`'s FAQ on this): `model-training` deliberately never imports `data-collection`'s Python code, only reads what it produces (the SQLite file, persisted model artifacts). `_player_id_map`'s own docstring says this explicitly — it "mirrors data-collection's `identity.player_id_map`... kept local rather than imported." The cost is that if the upstream identity-resolution convention ever changes, this local copy has to be updated by hand to match — a real maintenance tradeoff the codebase accepts in exchange for the two packages staying independently deployable.

**Q: Why does `select_xi` run its MILP over the *entire* candidate pool instead of just the top `pool_size` (20) players shown in the UI?**
Because a required constraint — most often the wicket-keeper — can genuinely score outside the top 20 by raw model score (keeping isn't captured by the batting/bowling WPA model at all), and truncating the pool *before* optimizing would silently make that constraint impossible to satisfy, with no error, just a wrong-looking XI. The function's own docstring calls this out directly. `pool_size` only ever affects the *display* slice returned alongside the XI, never what the solver actually considers.

**Q: If the MILP is supposed to find the true optimal answer, why does `_greedy_fallback` exist at all?**
Because `scipy.optimize.milp` can fail to find a feasible solution in edge cases (e.g. an extremely thin bowling pool where the constraints are right at the edge of what's satisfiable) — and returning nothing at all would be a worse failure than returning a *good-but-not-provably-optimal* XI. `_greedy_fallback` is a safety net for that specific failure mode, not the primary code path; `select_xi`'s return includes a `method` field (`"milp"` vs. `"greedy_fallback"`) so a caller can tell which one actually ran.

**Q: Why does `ga_bowling.py`'s repair step rebuild the whole quota map from scratch instead of directly patching whatever's illegal in the rotation (e.g. swapping just the offending overs)?**
The module's own docstring gives the reason: a naive left-to-right patch can dead-end on a razor-tight bowler pool (e.g. exactly 5 bowlers, zero slack) even when the pool as a whole can legally cover 20 overs — you can patch yourself into a corner with no legal move left, purely because of the *order* you tried fixing things in. Recomputing quotas globally first, then re-deriving the sequence from those quotas via the same greedy algorithm used for initial population generation, can't hit that dead end, because it never commits to a specific over-by-over assignment until the quotas are already known to be globally satisfiable.

**Q: Why is the SHAP background sample only 100 rows (`shap_background_size`), and why does only *one* of the two `bowling_wpa` sub-estimators need one?**
100 rows is a size/accuracy tradeoff inherent to the Permutation explainer's method (it repeatedly perturbs features against every background row, so a larger sample means more accurate attributions at a roughly linear compute cost) — not a value derived from a specific measurement, more a reasonable default for a per-request explanation rather than an offline batch job. Only the `HistGradientBoostingRegressor` half needs a background sample because `TreeExplainer` (used for the `RandomForestRegressor` half, and for all of `batting_wpa`) reads the tree structure directly and computes attributions exactly, with no background/reference distribution required at all — the two SHAP strategies genuinely need different inputs because they're different underlying methods, not an inconsistency.

**Q: Why does `train.py` compute holdout metrics on an 80/20 split (`_fit_one`) and then discard that split, refitting the shipped model on 100% of the data?**
Because those are two different jobs. The 80/20 split's only purpose is to produce an honest `holdout_mae`/`holdout_r2` number to persist in `training_metadata.json` — a sanity-check figure, not a gate on what ships. Once that number is recorded, there's no reason to withhold 20% of real training data from the model that actually gets used in production — more real data almost always helps a model at least a little, and the metrics being reported were never computed *from* the production model anyway. (The evaluation that actually drives model-family/hyperparameter decisions is the separate temporal holdout in `evaluate/backtest.py` — see `ALGORITHMS.md` §3.5.)

**Q: Why are there two independent WPA regressors (`batting_wpa`, `bowling_wpa`) instead of one shared model predicting both?**
Covered in depth in `ALGORITHMS.md` §3.2-3.3, but the short version as it shows up in the code: a specialist bowler's batting involvement is genuinely near-zero, and folding both disciplines into one shared target would let that near-zero batting signal drag down or dilute their real bowling rating (and vice versa for specialist batters). Keeping them as two separate `models[target]` entries, scored and summed with different weights depending on which disciplines a player's `role_bucket` actually supports (`score.py`'s `active_wpa` list, primary at full weight, secondary at `secondary_discipline_weight=0.4`), avoids that cross-contamination entirely.

**Q: Why does `lineup_explain.py` import `ga_bowling.py`'s private, underscore-prefixed helper functions (`_even_quotas`, `_sequence`) instead of having its own copy?**
This is the one deliberate exception to "don't reach into another module's private helpers" in the whole `simulate` package — and it's deliberate specifically because the naive baseline it needs ("an even split of overs, ignoring phase fit") is *exactly* the same "generate a legal rotation from a quota map" logic `ga_bowling.py` already uses to seed its own initial population. Re-implementing that logic a second time would risk the baseline silently drifting out of sync with what "a legal rotation" actually means if the rules ever change, whereas reusing the real functions guarantees the baseline is always exactly as legal as the GA's own output.

**Q: Why does `winprob_reader.py` reimplement `data-collection/criiq_data/winprob.py`'s `EmpiricalWinProb` lookup logic locally instead of just importing that class?**
Two reasons, both stated directly in the module's own docstring: the architectural rule against importing data-collection's code (same as every other cross-package answer above), and a real, specific performance reason — data-collection's own free-function version (`probability_for_state`) reloads all 5 grid parquet files from disk on *every single call*, which is fine for a one-off CLI query but far too slow to call once per simulated ball across an entire match. `WinProbLookup` loads the grids once per `(format, gender)` and reuses them for the whole simulation.

**Q: Why does every `cmd_*` function in `cli.py` open and close its own `sqlite3` connection instead of sharing one connection across the whole program run?**
Each CLI invocation is a single, short-lived process running exactly one subcommand (this is also why `backend/model_bridge.py` calls it via subprocess — see `WORKING.md`'s FAQ) — there's no long-running program state to share a connection across in the first place. Opening/closing per command keeps each `cmd_*` function trivially self-contained and testable in isolation, at essentially zero cost given SQLite connections are cheap to open.

**Q: Why is `role_bucket` (the one categorical feature) handled two completely different ways — `OneHotEncoder` for the RandomForest, native dtype-based handling for `HistGradientBoostingRegressor`?**
Because the two model types have genuinely different native capabilities, and using each one's best-supported approach beats forcing one uniform encoding onto both. `HistGradientBoostingRegressor` (relatively recent in scikit-learn) can consume a pandas `category` dtype column directly (`categorical_features="from_dtype"`) with no preprocessing step at all — using it is strictly better than one-hot-encoding for that model. `RandomForestRegressor` has no such native support and needs the explicit `OneHotEncoder` inside a `Pipeline`. This is a case of "let each estimator do what it's actually built for" rather than an inconsistency to fix.

**Q: Why do `_fitness` (in `ga_batting.py`/`ga_bowling.py`) and the metrics in `lineup_explain.py` re-run the full simulator many times (`n_reps`) instead of scoring a candidate rotation/order just once?**
Because a single simulated innings is one random sample from a distribution, not a stable measurement — the same rotation can look better or worse purely from luck on any one run. Averaging over `n_reps` (and re-verifying an apparent new best with even more reps before trusting it, both GAs' documented noise-protection strategy) is what makes the fitness signal the GA is actually optimizing trustworthy rather than chasing statistical noise — see `ALGORITHMS.md` §2 for the full "why GAs need this" reasoning.

**Q: Why does `--seed` default to being *omitted* (genuine randomness) instead of defaulting to a fixed number for reproducibility, which is normally considered good practice?**
Because the two things reproducibility is useful *for* are in tension here: a fixed seed makes a specific run replayable on demand (useful for debugging one exact result), but a genetic algorithm or Monte Carlo simulation defaulting to the *same* randomness on every invocation would make "run it again" always produce the identical answer — hiding exactly the run-to-run variance a user actually wants to see when asking "how confident should I be in this recommendation." Omitting the seed by default means every real invocation explores fresh randomness; passing `--seed` explicitly is there specifically for the debugging/reproduction case, not the everyday one.

**Q: Why is `config.py`'s `Settings` a frozen `dataclass` instead of a plain dict, a `.env` file, or scattered module-level constants?**
A frozen dataclass gets you attribute access with autocomplete/type-checking (`SETTINGS.min_matches_for_model`, not `SETTINGS["min_matches_for_model"]` or a bare `import` of a loose constant), immutability (nothing downstream can accidentally mutate a shared setting mid-run and affect other code relying on it), and one single object every module imports (`from .config import SETTINGS`) instead of a dozen scattered magic numbers — the whole point stated in that section's own purpose line: "a tuning change only happens in one place."
