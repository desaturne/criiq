# Publishing the handover images

How to produce the two images in `handover/docker-compose.yml`. This is for the
maintainer — the person receiving them only needs `handover/README.md`.

## Why a separate "bundle" image exists

Day-to-day development uses `docker-compose.yml` at the repo root, which
bind-mounts two things the images deliberately do not contain:

| | Size | Why it is mounted, not baked |
|---|---|---|
| `data-collection/data/criiq.db` | 452 MB | Untracked; owned and rebuilt by the pipeline |
| `model-training/artifacts/` | 32 MB | Untracked; regenerated by training runs |

That split is correct for development — but it means the images alone cannot run
anywhere else. `backend/Dockerfile.bundle` layers those two directories on top of
the normal backend image so the result is self-contained.

Baking a 450 MB database into an image is not production practice (data and code
should have separate lifecycles). It is the right trade for a demo handover,
where the goal is that the recipient runs one command and it works.

## Architecture matters

Images are CPU-specific. Building on an Apple Silicon Mac produces **arm64**
images, which will not run on a Windows or Intel machine.

- Recipient on Windows / Intel → build `linux/amd64`
- Recipient on an M-series Mac → build `linux/arm64` (the default here)

Cross-building amd64 on Apple Silicon runs under QEMU emulation and is slow —
budget 30–60 minutes for the backend. Do it once.

## Build

Replace `<user>` with your Docker Hub username throughout.

```bash
cd criiq

# 1. Base backend for the target architecture
docker buildx build --platform linux/amd64 -f backend/Dockerfile \
    -t criiq-backend:amd64 --load .

# 2. Layer the database + model artifacts on top
docker buildx build --platform linux/amd64 -f backend/Dockerfile.bundle \
    --build-arg BASE=criiq-backend:amd64 \
    -t <user>/criiq-backend:demo --load .

# 3. Frontend
docker buildx build --platform linux/amd64 \
    -t <user>/criiq-frontend:demo --load ./frontend
```

`backend/Dockerfile.bundle.dockerignore` exists because the root `.dockerignore`
excludes `data/` and `artifacts/` — precisely what this build must copy in.
BuildKit prefers a `<dockerfile>.dockerignore` when present. It keeps `criiq.db`
and the artifacts while still dropping ~350 MB of pipeline scratch
(`cache/`, `raw/`, `interim/`).

## Ship it — option A: Docker Hub

Needs a free account at hub.docker.com.

```bash
docker login
docker push <user>/criiq-backend:demo
docker push <user>/criiq-frontend:demo
```

Then edit `handover/docker-compose.yml`, replacing `REPLACE_ME` with your
username, and send that file plus `handover/README.md`.

## Ship it — option B: offline tarball

No account needed. Good for a USB drive or a Drive link.

```bash
docker save <user>/criiq-backend:demo <user>/criiq-frontend:demo \
  | gzip > criiq-images.tar.gz     # ~1.5 GB
```

The recipient loads it before running compose:

```powershell
docker load -i criiq-images.tar.gz
docker compose up
```

## Verify before sending

Do not skip this. Run the images exactly as the recipient will — from
`handover/`, with no bind mounts, so a missing file surfaces here and not on
their machine.

```bash
cd handover
docker compose up -d
curl localhost:8000/health          # {"status":"ok","db_connected":true}
curl -s -o /dev/null -w "%{http_code}\n" localhost:5173   # 200
docker compose down
```

`db_connected: true` is the important one — it proves the baked-in database is
present and readable. Then log in at http://localhost:5173 with
`rahul@criiq.local` / `coach1234` and trigger a recommendation, which is the only
check that exercises the model artifacts.
