# data-collection — Code Walkthrough

This is a file-by-file explanation of every module in `data-collection/`, what it does, and how it works internally. It complements `README.md` (setup/usage) — this document is about the *code itself*: what each function computes, why it's built the way it is, and how the files connect to each other.

`data-collection` is stage one of the whole system: it downloads raw Cricsheet ball-by-ball data, ingests it into SQLite, resolves player/venue identities, and builds every derived analytics table (career stats, phase splits, matchup history, win probability, WPA, player cards, the registry of who's active/retired, and the ML feature tables that `model-training` consumes). Nothing here trains a predictive model — that's `model-training`'s job; this package's job is turning raw match data into clean, queryable, deduplicated facts.

A pattern that recurs constantly throughout this package, flagged in almost every file below: a small number of Cricsheet's raw player identifiers are reused across two different real people of different genders (e.g. one `"A Sharma"` identifier covers both a real man and a real woman in the raw data). `identity.py` is where this is detected and resolved into distinct, stable `player_id`s — and nearly every aggregation module downstream groups by `(identifier, gender)` rather than `identifier` alone specifically to avoid silently blending two different people's careers together.

## How the pipeline actually runs, in order

The sections below are organized alphabetically by filename, which is convenient for looking up one function but doesn't show the end-to-end sequence. That sequence lives entirely in `refresh.py`'s `run()` — here it is traced up front, straight from that function's current code (see `refresh.py`'s own section for the full per-step detail):

1. `download_register.download_register` → `people` table (Cricsheet's global identifier→name/Cricinfo-key register).
2. `download_cricsheet.download_all` → raw zips into `RAW_DIR`, one per enabled `CricsheetSource`.
3. `ingest.ingest_all` (parses zips into `matches`/`deliveries`/`match_players`/`identifier_map`, holdout-routing anything dated after `SETTINGS.data_cutoff_date`) **immediately followed by `ingest.backfill_fielders`** (a one-time, no-network re-read of already-downloaded zips to backfill `fielder_1/2/3` on wicket-ball rows ingested before those columns existed).
4. `identity.run` (`resolve_players` + `normalise_venues`) — the collision-handling step nearly everything downstream depends on.
5. Optionally `scrape_cricinfo.enrich_players` (only with `--enrich`, best-effort, skipped by default).
6. `styles.load_manual_csv` (always) + optionally `styles.seed_from_wikidata`/`enrich_from_wikipedia` (only with `--seed-styles`).
7. Optionally `rss_monitor.scan_feeds` (retirement-announcement scan).
8. `rankings.load` → `overrides.load_csv` → `registry.build_registry` → `career.build_career` → **`fielding.build_fielding`** → `player_card.build_cards` — note the dependency chain: registry/overrides/career/fielding all feed into the player card that's built last in this step.
9. `advanced.build_advanced` (vs-pace/vs-spin splits and more).
10. `opponents.build_vs_opponent` → `impact.build_impact` → `venue_stats.build_venue_stats` → `matchups.build_matchups` → `phases.build_phases`.
11. `ml_features.build_all` (`match_features`, the `ball_state_<fmt>.parquet` files, `player_match_impact`) — the bridge to `model-training`.
12. `winprob.build_winprob` — last, because it depends on step 11's `ball_state_<fmt>.parquet` output.

**Two real, working modules are deliberately *not* in this list, and never run automatically:**
- `wpa.py` (Win-Probability-Added and domestic-form aggregates) — only reachable via `cli.py`'s `wpa` subcommand.
- `role_finalize.py` (the batting-position-corrected role/keeper flag, and the external-squad-page role merge) — only reachable via `cli.py`'s `role-finalize` subcommand.

Both are real and tested, they're just manual, on-demand steps rather than something a `refresh run` (or a cron job calling it) will ever trigger by itself — worth knowing before assuming "refresh ran recently" means WPA or finalized-role data is current.

## data-collection/criiq_data — core files (batch 1)

### `data-collection/criiq_data/__init__.py`

**Purpose:** This is the package marker for `criiq_data`. It contains a single line, `__version__ = "0.1.0"`, and nothing else — no imports, no re-exports. Its only job is to make `criiq_data` importable as a Python package and expose a version string.

**Key pieces:** None — just the `__version__` string constant.

**How it connects:** Nothing in the package imports `__version__` (based on the files reviewed here); it exists purely as package metadata/convention.

### `data-collection/criiq_data/advanced.py`

**Purpose:** Builds the "advanced profile" for every player-format combination: a rich JSON blob (`player_advanced.profile_json`) covering batting phase splits, matchup splits (vs pace/spin, vs bowling sub-type, vs LHB/RHB), acceleration curves, and a rule-based batting "archetype" label (finisher / power hitter / anchor / balanced), plus a human-readable list of "strengths" sentences. It sits downstream of `ingest.py` (raw deliveries), `identity.py` (player_id resolution), and `styles.py` (batting hand / bowling style lookups), and is invoked by `cli.py`'s `advanced` and `profile` subcommands. Its output feeds UI player cards/recommendation explanations elsewhere in the app.

**Key pieces:**

- `_phase(over)` — maps a 0-indexed over number to `"powerplay"` (over ≤5), `"middle"` (≤14), or `"death"` (else). This is the phase taxonomy used throughout the whole codebase (T20-shaped: overs 1-6 / 7-15 / 16-20).
- `_name_to_id(conn)` — loads the whole `identifier_map` table into a `{player_name: identifier}` dict for fast vectorized `.map()` lookups later (avoids per-row SQL).
- `_bat_rate(runs, balls)` — plain strike-rate formula, `100*runs/balls` rounded to 1dp, or `None` if no balls (avoids division by zero).
- `build_for_format(conn, fmt)` — the core builder, run once per format (e.g. "T20"):
  1. Pulls every legal-and-illegal delivery for international matches of that format via a `deliveries JOIN matches` query, including `wicket_type`, `player_dismissed`, and `gender`.
  2. Bails out early (`return 0`) if there are no deliveries.
  3. Builds several lookup dicts: name→identifier, bowler style buckets (coarse pace/spin and detailed e.g. off-spin/leg-spin from `styles.bowler_buckets`), batting hand per name (`styles.batter_hands`), and the `unambiguous`/`split` player-id maps from `identity.player_id_map`.
  4. Builds `style_meta`, keyed by `(cricsheet_identifier, gender)`, from the `players` table's `batting_hand`/`bowling_style` columns. `_style_meta` looks up by `(ident, gender)` first, falling back to `(ident, None)` — the comment explains this is because a handful of colliding identifiers (same Cricsheet id used for two different real people of different genders, see `identity.py`) can have different style data per person, so gender must be part of the key.
  5. Derives per-delivery boolean/int flags: `legal` (not a wide), `legal_bowl` (not a wide or no-ball), `phase`, `rc` (total runs conceded on the ball = bat runs + wides + no-balls), `bwkt` (a wicket credited to the bowler, i.e. `wicket_type` in `BOWLER_WICKETS` from `h2h.py` and someone was actually dismissed).
  6. **Batting side:** filters to deliveries with a resolved `striker_id`, then derives `four`/`six`/`bdry` (boundary) flags, `dot` (legal ball, 0 runs), `scored` (legal ball, runs>0), `rotate` (legal ball, 1/2/3 runs — i.e. strike rotation), and `lb` (legal ball counter). These get summed via `groupby(["striker_id","gender"])` into `bat_overall`, and `bat_innings` counts distinct (match_id, innings) per striker — the innings-played count.
     - Every groupby key here includes `gender` even though `striker_id` should already be unique — the comment says this is deliberate, to avoid two different people who share a colliding Cricsheet identifier from having their stats summed together before the final `player_id` resolution step.
  7. `_nest_phase` groups by `(idcol, gender, phase)` and reshapes the resulting multi-index Series into a nested dict `{(id, gender): {phase: {...}}}` — used for both batting and bowling phase splits.
  8. `_vs_type(col_map, colname)` — maps each ball's bowler name to a bucket (via `_lookup_by_name_gender`, which does an exact `(name, gender)` lookup and falls back to `(name, None)` for unsplit style entries — same fallback precedence pattern as `_style_meta`), then groups by `(striker_id, gender, bucket)` to produce vs-pace/vs-spin (coarse) and vs-specific-bowling-type (detail) splits.
  9. Acceleration: only legal balls are kept, sorted by match/innings/over/ball, and `ball_no` is a running per-innings-per-striker ball count (`cumcount()+1`). Balls after the 10th are labeled `"after10"`, else `"first10"` — a simple two-bucket "does she start slow and accelerate" signal.
  10. **Bowling side:** mirrors the batting side — `lbb` (legal delivery for bowling purposes, excludes wides+no-balls), `dotb`, `wktb` — grouped into `bowl_overall`, `bowl_phase`, and (via a batting-hand lookup on the striker) `bowl_vs_hand` (economy/wickets broken out by RHB vs LHB faced).
  11. `_gender_archetype_thresholds` computes **per-gender percentile bars** (75th/50th percentile of six-rate, strike rate, boundary%, rotation%, death-SR) across all batters with at least `_ARCHETYPE_MIN_BALLS=120` balls faced (roughly two T20 innings, chosen so one big cameo can't skew the bar). This exists, per the comment, because men's and women's six-hitting/SR distributions differ enough that one shared absolute threshold would mislabel most of one gender.
  12. The main loop iterates over the union of batting and bowling `(identifier, gender)` keys, resolves each to a `player_id` via the unambiguous/split maps (skipping unresolved ones), attaches style metadata, and builds the batting block (if she has ≥1 ball faced) and bowling block (if ≥1 ball bowled) via the helper functions below, plus a `strengths` summary and a `meta.updated_at` timestamp.
  13. Writes everything as one row per `(player_id, format)` into `player_advanced` via an upsert (`INSERT ... ON CONFLICT DO UPDATE`).
- `_phase_block(d)` — turns one phase's raw sums into a display dict: runs, balls, strike_rate, boundary_pct, dot_pct, dismissals.
- `_vs_type_block(vs)` — same idea per bowling-type/hand bucket, additionally computing `average = runs/dismissals` (undefined, i.e. `None`, if never dismissed against that type).
- `_batting_block(...)` — assembles the full per-player batting JSON block: innings, runs, balls, strike_rate, average, boundary_pct, dot_pct, `scoring_pct` (100 − dot%, i.e. share of balls where she scored), `rotation_pct`, `six_rate` (sixes per 100 balls — chosen, per the inline comment, specifically because it's "scale-stable" for feeding the archetype classifier regardless of total sample size), phase splits, matchup splits, acceleration, and finally calls `_archetype` to attach a label.
- `_archetype(b, th)` — the rule-based classifier, evaluated in a fixed precedence order against the gender-specific thresholds `th`:
  1. If total balls faced < `_ARCHETYPE_MIN_CLASSIFY_BALLS` (60), always returns `"balanced"` — too small a sample to trust a specialist label.
  2. **finisher**: needs ≥40 death-overs balls (`_ARCHETYPE_MIN_DEATH_BALLS`), death overs making up ≥25% of her total balls faced, AND death strike-rate/boundary% both above the 75th-percentile bar for her gender.
  3. **power hitter**: six-rate and strike-rate both above their respective 75th-percentile bars (checked only if not already a finisher — finisher wins on precedence, per the docstring).
  4. **anchor**: powerplay balls ≥40% of total, overall strike-rate ≤ the *median* (50th percentile, a looser "not aggressive" bar than the others), and rotation% above the 75th-percentile bar.
  5. Otherwise **balanced** (the default/fallback label).
- `_bowling_block(bo, phase, vs_hand)` — assembles bowling JSON: overs (formatted `balls//6 . balls%6`), economy (`6*runs/balls`), strike_rate (`balls/wickets`), average (`runs/wickets`), per-phase economy/wickets/dot%, `usage_share` (fraction of total balls bowled in each phase — a proxy for what role the captain uses her in), and vs-batting-hand splits.
- `_strengths_summary(profile)` — turns the numeric profile into a list of human-readable sentences, e.g. "Best phase: death (SR 145.2, 22.0% boundaries)", "Stronger vs pace (SR X vs Y vs spin) — attack with spin" (triggered when one strike rate is >15% higher than the other), "Least effective vs off-spin (...) — a matchup to exploit" (the single worst detailed bowling-type matchup, gated on ≥`MIN_PHASE_BALLS`=24 balls sample), and bowling equivalents (tighter to one hand by >10% economy gap, most economical phase, "Used as a death-overs bowler" if usage_share≥0.3, etc). These generated strings are clearly meant to power a UI explanation/rationale panel.
- `build_advanced(conn)` — top-level entry: runs `build_for_format` for every enabled format from `config.enabled_sources()`, records a `advanced_built_at` meta timestamp, commits, returns per-format counts.
- `get_advanced(conn, player_id, fmt)` — simple read-through: fetches the stored `profile_json` and `json.loads`s it, or `None`.

**How it connects:** Imports `config.enabled_sources`, `db.set_meta`, `h2h.BOWLER_WICKETS`, `identity.player_id_map`, `logging_utils.get_logger`, and the whole `styles` module. `cli.py` calls `build_advanced` and `get_advanced` directly (subcommands `advanced` and `profile`).

### `data-collection/criiq_data/career.py`

**Purpose:** Builds simple, format-scoped career totals (the `player_career` table) — the "classic stats" view (runs, average, strike rate, 50s/100s, wickets, economy, best bowling) as opposed to `advanced.py`'s richer phase/matchup breakdown. It's a thin aggregation layer over `stats.build_innings`, which does the heavy per-innings extraction from raw deliveries.

**Key pieces:**
- `_overs(balls)` — `balls//6 . balls%6` formatting helper, identical pattern to the one in `advanced.py` (duplicated rather than shared).
- `career_from_group(g)` — takes one player's DataFrame of per-innings rows (`g`, one row per match/innings she was involved in) and returns a dict with `batting` and (if she ever bowled) `bowling` sub-dicts:
  - Batting: filters to `balls_faced>0` rows as "innings batted"; average = `runs/outs` (undefined if never out — she may be not-out every time); strike_rate = `100*runs/balls`; `high_score` = max single-innings runs; fifties = innings with 50≤runs<100; hundreds = runs≥100 (note fifties strictly excludes centuries, no double counting).
  - Bowling (only computed if `balls_bowled.sum()>0`): economy, average (`runs_conceded/wickets`), strike_rate (`balls/wickets`), and `best_bowling` — found by sorting bowled innings by `(wickets desc, runs_conceded asc)` and taking the top row, i.e. most wickets, tie-broken by fewest runs conceded (the standard cricket "best bowling figures" definition).
- `build_career_for_format(conn, fmt)`:
  1. Gets the per-innings table from `stats.build_innings(conn, fmt)`; bails early if empty.
  2. Loads `players` metadata keyed by `(cricsheet_identifier, gender)` — same gender-scoping pattern as `advanced.py`, with the same rationale (avoid blending two people who share a colliding Cricsheet identifier).
  3. Groups the innings table by `["identifier", "gender"]`, resolves each group to a `player_id` via `identity.player_id_map`'s unambiguous/split maps, looks up her canonical name/role (falling back from `(ident, gender)` to `(ident, None)` for non-colliding/unsplit players), skips if either lookup fails, then calls `career_from_group` and flattens the result into a row tuple.
  4. Upserts all rows into `player_career` in one `executemany` with `ON CONFLICT ... DO UPDATE`.
- `build_career(conn)` — loops `build_career_for_format` over every enabled format (`config.enabled_sources`), stamps `career_built_at` meta, commits.

**How it connects:** Imports `config.enabled_sources`, `db.set_meta`, `identity.player_id_map`, `stats.build_innings`. Called by `cli.py`'s `career` subcommand.

### `data-collection/criiq_data/cli.py`

**Purpose:** The command-line entry point for the entire data-collection pipeline (`criiq-data <subcommand>`). It doesn't contain analytical logic itself — every `cmd_*` function is a thin wrapper that opens a DB connection, initializes the schema, calls into the relevant module (`ingest`, `identity`, `career`, `advanced`, `impact`, `winprob`, `refresh`, etc.), pretty-prints the JSON result, and closes the connection. This is the operational "front door" a human (or a cron/refresh script) uses to run each pipeline stage independently or query built data.

**Key pieces:**
- `_pp(obj)` — `json.dumps(obj, indent=2, default=str)` then print; the `default=str` lets it serialize things like dates/Decimals without erroring.
- `_find_player(conn, name)` — fuzzy-ish player lookup by substring: `WHERE canonical_name LIKE '%name%' OR unique_name LIKE '%name%' LIMIT 10`. Used by every subcommand that takes a `--name` and needs to resolve it to a `player_id`.
- 31 `cmd_*` functions (verified via `grep -c '^def cmd_'`, not the ~25 an earlier count of this doc estimated), each mapping 1:1 to a subparser: `init` (schema only), `download` (register + cricsheet zips), `ingest`, `identity`, `registry`, `cards`, `enrich` (Cricinfo scraping), `rss`/`alerts` (retirement news monitor), `career`, `advanced`, `opponents`, `impact`, `venues`, `matchups`, `phases`, `role-finalize`, `ml`, `wpa`, `winprob`, `rankings`, `status-override`, `sheet`, `styles`, `profile`, `refresh`, `status`, `card`, `h2h`, `vs-team`, and **`fielding`** (`cmd_fielding` → `fielding.build_fielding`, catches/run-outs/stumpings per player — see the new `fielding.py` section).
- `cmd_winprob` is the most logic-heavy handler: it supports three mutually distinct modes via CLI flags — `--state` (ad-hoc probability query, parsing a comma-separated `key=value` string into an int dict, validating allowed keys `{innings, wickets, balls_remaining, runs_required, balls_bowled, score}` and required keys `{innings, wickets}`, raising `SystemExit` with a helpful message on bad input), `--match` (prints a formatted per-over win-probability timeline table for one match id), or neither (rebuilds the whole win-prob model via `winprob.build_winprob`).
- `cmd_status` is the pipeline health-check command: reports row counts across ~15 core tables, a breakdown of `retirement_status` values, count of age-advisory-flagged players, styles coverage, Cricinfo-linked player count, players needing manual review, data freshness (`refresh.freshness`), and the last successful refresh timestamp.
- `cmd_vs_team` — a player's matchup breakdown against one specific opponent team, both as batter (bowlers she's faced) and bowler (batters she's dismissed/bowled to), built by calling into `matchups.batter_vs_team_bowlers` / `matchups.bowler_vs_team_batters`. Its docstring explicitly frames this as "for an all-rounder" — both sections can be populated for one player.
- `cmd_h2h` resolves both players' names via `_find_player`, then their full name-variant lists + gender via `h2h.names_for_player`, then calls `h2h.batter_vs_bowler` — showing this file already threads through the identity collision-handling pattern established elsewhere.
- `build_parser()` — constructs the full `argparse` subcommand tree; notable non-trivial argument wiring: `role-finalize --load-external CSV` (merge externally researched roles instead of running the local batting-position heuristic), `winprob --gender` (defaults to `"female"`, and the help text clarifies the model itself is gender-agnostic to build but per-gender to query), `rankings --scaffold`/`--fetch` (write a template vs pull live ICC data).
- `main(argv=None)` — parses args and dispatches to `args.func(args)`; the `if __name__ == "__main__"` guard makes the module directly runnable.

**How it connects:** Imports nearly every other module in the package (`advanced`, `career`, `download_cricsheet`, `download_register`, `fielding`, `identity`, `impact`, `ingest`, `matchups`, `ml_features`, `opponents`, `overrides`, `phases`, `player_card`, `rankings`, `refresh`, `registry`, `role_finalize`, `rss_monitor`, `scrape_cricinfo`, `sheet`, `styles`, `venue_stats`, `winprob`, `wpa`), plus `db.connect/get_meta/init_schema/table_count` and `h2h.batter_vs_bowler/names_for_player`. Nothing else in the package imports from `cli.py` — it's the top of the call graph.

### `data-collection/criiq_data/config.py`

**Purpose:** The single source of truth for paths, data-source definitions, and tunable constants used across the whole pipeline. Every other module that needs a filesystem path, a Cricsheet download URL, or a numeric threshold (fuzzy-match cutoff, staleness windows, archetype sample sizes) imports it from here rather than hardcoding it.

**Key pieces:**
- Path constants: `PACKAGE_DIR`/`ROOT_DIR` derived from `__file__`; `DATA_DIR` defaults to `<repo>/data` but is overridable via the `CRIIQ_DATA_DIR` env var (so tests or alternate environments can redirect all data). All the specific subdirectories (`RAW_DIR`, `REGISTER_DIR`, `CACHE_DIR`, `STYLES_DIR`, `MODELS_DIR`, `RANKINGS_DIR`, `OVERRIDES_DIR`, etc.) and file paths (`MANUAL_STYLES_CSV`, `ICC_RANKINGS_CSV`, `PLAYER_STATUS_CSV`, `DB_PATH`) are derived from it. `DB_PATH` is also independently overridable via `CRIIQ_DB`.
- `ALL_DIRS` — the list `ensure_dirs()` iterates to `mkdir(parents=True, exist_ok=True)` every directory the pipeline might write to, including a nested `CACHE_DIR/"cricinfo"`.
- External URLs: `WIKIDATA_SPARQL`, `CRICSHEET_BASE`, `REGISTER_URL`, and `ICC_RANKINGS_SOURCE_URL`/`ICC_RANKINGS_CLIENT_ID` (both env-overridable, since the ICC rankings source is a semi-private sportz.io API needing a client id).
- `CricsheetSource` — a frozen dataclass (`fmt`, `gender`, `filename`, `enabled`) representing one downloadable Cricsheet zip. `.url` builds the full download URL; `.label` strips the `.zip` suffix from the filename rather than combining gender+fmt — the comment explains this is deliberate because several competitions share the same `(gender, fmt)` pair, and `label` is used elsewhere (`ingest.py`) as a meta dictionary key that must be unique per file.
- `CRICSHEET_SOURCES` — the master list of all known sources: internationals (T20 male/female enabled; ODI male/female disabled/scaffolded), and domestic T20 leagues. Comments note women's domestic leagues (WBBL, WPL, The Hundred Women, Women's T20 Blast/Challenge/Super League, and the Women's Caribbean Premier League) are all `enabled=True` — reflecting the project's stated focus. Men's domestic leagues are *mostly* disabled (IPL, BBL, PSL, CPL, T20 Blast all `enabled=False`), but **not uniformly** — the Nepal Premier League (`npl_male_csv2.zip`) is `enabled=True`, so "men's domestic data is off" is not a blanket truth; it's off for the major global T20 leagues specifically.
- `enabled_sources()` — filters `CRICSHEET_SOURCES` to `enabled=True`; this is what every builder module (`career.py`, `advanced.py`, `impact.py`, etc.) iterates over to know which formats to build for.
- `RSS_FEEDS` / `RETIREMENT_KEYWORDS` — feed URLs and a keyword list (e.g. "retires", "steps down", "hangs up") used by `rss_monitor.py` to detect retirement announcements in news text.
- `Settings` (frozen dataclass, single instance `SETTINGS`) — every tunable numeric knob in the system in one place, with inline comments explaining several non-obvious ones:
  - HTTP behavior: `cricsheet_delay_s`/`cricinfo_delay_s` (per-host politeness delay), `http_timeout_s`, `http_retries`, `http_backoff_s`.
  - `fuzzy_threshold=88` — the RapidFuzz WRatio score cutoff for accepting a fuzzy name match (used in `identity.fuzzy_match_name`).
  - Registry/activity windows: `recall_flag_days`, `active_window_days`, `inactive_window_days`, `selection_window_days=730` with `min_window_team_matches=8` (a team must have played at least 8 matches in the rolling window before a selection rate is trusted) and `regular_selection_rate=0.35` (share of team matches a player must appear in to count as ACTIVE rather than INCONSISTENT — kept low deliberately for heavily-rotated squads), `age_advisory_pace=38`/`age_advisory_default=40` (age thresholds for flagging an aging player), `registry_refresh_days`, `staleness_warn_days`.
  - Form/impact: `form_window_innings=20`, `rfi_lambda=0.85` (presumably a recency-weighting decay factor for a "recent form index"), `form_sparkline_len=10`, `impact_recent_matches=10`.
  - `min_innings_bayesian=20` — confirmed (by grepping the package) to be **unreferenced anywhere outside its own definition** — currently dead configuration, not wired into any actual shrinkage/Bayesian calculation despite the name suggesting otherwise.
  - `winprob_shrinkage=12.0` and `winprob_test_fraction=0.2` — shrinkage strength toward the innings prior for sparse win-probability buckets, and the held-out fraction of matches used for calibration.
  - `data_cutoff_date="2026-06-15"` — anything dated after this is routed to the `*_holdout` tables (see `db.py`) instead of production tables, explicitly to prevent future data leaking into training/scoring.
- `ensure_dirs()` — creates every directory in `ALL_DIRS` if missing.

**How it connects:** This is a leaf/foundation module — it imports nothing from the rest of `criiq_data`. Virtually every other file in the package imports from it (`SETTINGS`, path constants, `enabled_sources`, or `CricsheetSource`).

### `data-collection/criiq_data/db.py`

**Purpose:** Owns the SQLite schema definition and connection lifecycle for the whole project. It's the only file that defines `CREATE TABLE` statements, runs schema migrations, and exposes small generic helpers (`set_meta`/`get_meta`/`table_count`) that every builder module uses to read/write bookkeeping metadata and row counts.

**Key pieces:**
- `SCHEMA` — one large SQL script (`CREATE TABLE IF NOT EXISTS ...` for 25+ tables plus indexes, including `player_fielding` — see the new `fielding.py` section below), executed wholesale via `executescript`. Notable design points visible in the schema comments:
  - `matches`/`deliveries`/`match_players` each have a parallel `*_holdout` table with an identical shape. Per the comment, rows dated after `SETTINGS.data_cutoff_date` are routed to the holdout tables by `ingest.py` (the only writer of either set) so they form an untouched forward-test set — a deliberate anti-leakage design.
  - `deliveries`/`deliveries_holdout` also carry `fielder_1`/`fielder_2`/`fielder_3` columns, populated on wicket-ball rows by `ingest.py` (see that section) and consumed by `fielding.build_fielding_for_format` to credit catches/run-outs/stumpings.
  - `matches.team_type` (default `'international'`) is explicitly distinguished from `match_type` (the actual cricket format) in a comment — `team_type` is Cricsheet's international-vs-club flag, letting domestic league matches share the same table while staying filterable.
  - `players.cricsheet_identifier` is **not** globally unique by itself — the table's `UNIQUE` constraint is on `(cricsheet_identifier, gender)`. The comment explains Cricsheet's registry rarely reuses one identifier across two different real people of different genders, and `gender` (NULL for the vast majority) is how the schema disambiguates those rare collisions — this is the schema-level anchor for the pattern seen repeatedly in `identity.py`, `career.py`, `advanced.py`, `impact.py`.
  - `player_registry.recent_domestic_activity` — a comment clarifies this is intentionally a separate signal from `retirement_status`: an internationally INACTIVE/INCONSISTENT player can still be domestically active/eligible, and `roster.team_pool` (elsewhere) checks this flag rather than overloading the status label.
  - `player_by_venue` has `setting_*`/`chasing_*` column pairs mirroring `player_impact`'s career-level batting-first vs chasing split, but scoped per venue.
  - `venue_dismissal_matchup` mirrors `dismissal_matchup` (batter-vs-bowler dismissal counts) but scoped to one venue — "who's gotten her out most *here*."
  - `player_domestic_form` is explicitly kept separate from `player_career`/`player_impact` (which are international-only) so domestic-league-only recent form is its own distinct signal.
- `_MIGRATIONS` — a flat list of `ALTER TABLE ADD COLUMN` statements applied unconditionally (wrapped in try/except `sqlite3.OperationalError` so already-migrated databases don't error) — this is how the schema has evolved incrementally (adding ICC ranking columns, domestic setting/chasing splits, etc.) without a full migration framework.
- `connect(db_path=None)` — opens a SQLite connection to `db_path` or the configured `DB_PATH`, calling `ensure_dirs()` first, setting `row_factory = sqlite3.Row` (so query results are dict-like by column name) and enabling `PRAGMA foreign_keys=ON`.
- `_migrate_players_gender_scoped(conn)` — a one-time structural migration: since SQLite can't `ALTER` a `UNIQUE` constraint in place, this checks whether the `players` table already has a `gender` column (no-op if so), and if not, recreates the whole table under a new name with the new `UNIQUE(cricsheet_identifier, gender)` constraint, copies all existing rows across (which get `gender=NULL` until `identity.resolve_players` fills them in), drops the old table, and renames.
- `_backfill_international_team_type(conn)` — sets `team_type='international'` on any row where it's still NULL (i.e. matches ingested before domestic leagues existed, which were all international by construction) — a targeted, idempotent backfill.
- `init_schema(conn)` — runs `SCHEMA`, then the players migration, then every `_MIGRATIONS` statement, then the team_type backfill, then commits. This is called at the start of virtually every CLI command, so it's cheap/idempotent by design.
- `set_meta`/`get_meta` — a generic key-value store on the `meta` table (upsert via `ON CONFLICT DO UPDATE`), used throughout the codebase for bookkeeping like `"advanced_built_at"`, `"last_successful_refresh"`, per-source download fingerprints, etc.
- `table_count(conn, table)` — `SELECT COUNT(*)` on an arbitrary table name (f-string interpolated, not parameterized — acceptable here since callers always pass a fixed literal table name, never user input).

**How it connects:** Imports only `config.DB_PATH`/`ensure_dirs`. Nearly every other module imports `connect`, `init_schema`, `set_meta`, `get_meta`, or `table_count` from here — this is the shared persistence layer for the entire pipeline.

### `data-collection/criiq_data/fielding.py`

**Purpose:** Builds career catches/run-outs/stumpings per player from `deliveries`' `fielder_1`/`fielder_2`/`fielder_3` columns, following the same attribution rules ESPNcricinfo uses so the numbers read as familiar to a coach rather than a bespoke house convention. Feeds `model-training`'s `recommend/score.py` (a descriptive, never-scored input) and `selection/optimize.best_fielder`, and the backend's own fielding display — all three keep an independently-maintained copy of `MIN_MATCHES_FOR_RATE`/`MIN_FIELDING_MATCHES_FOR_RATE = 5` since the three packages deliberately don't import each other.

**Key pieces:**
- `_CAUGHT`/`_CAUGHT_AND_BOWLED`/`_STUMPED`/`_RUN_OUT` — the four `wicket_type` values that ever carry fielding credit (a run-out with no fielder recorded, or a bowled/lbw/hit-wicket dismissal, are the ones that don't).
- `MIN_MATCHES_FOR_RATE = 5` — below this many matches, a dismissals-per-match rate is too noisy to rank on; `better_fielder` falls back to the raw dismissal count instead.
- `build_fielding_for_format(conn, fmt, team_type="international") -> int`:
  1. Pulls every wicket-ball delivery of the four creditable types (joined to `matches` for `gender`), including `fielder_1/2/3`.
  2. Credits dismissals per ESPNcricinfo's own rules: **caught** → `fielder_1` only (the actual catcher, ignoring any listed backup names); **caught and bowled** → the *bowler*, not a fielder at all (Cricsheet leaves `fielder_*` blank for this case, so this is looked up via the bowler's name instead); **stumped** → `fielder_1` only (always the keeper); **run out** → *every* fielder Cricsheet lists on that ball (a direct-hit fielder and whoever set up the run-out both get credited).
  3. Maps each credited name to a Cricsheet `identifier` via `identifier_map`, groups by `(identifier, gender)`, and counts catches/run-outs/stumpings per player.
  4. Separately computes real **matches appeared** (not just matches batted/bowled in) from `match_players`, since a specialist fielder can take catches without ever facing a ball or bowling one — the fielding-per-match rate needs the true appearance count, not a batting/bowling-derived one.
  5. Resolves each `(identifier, gender)` to a real `player_id` via `identity.player_id_map`'s unambiguous/split maps (the same collision-handling pattern used throughout the codebase), skipping any that don't resolve to a known player/name.
  6. Upserts into `player_fielding` (`ON CONFLICT(player_id, format) DO UPDATE`): `matches`, `catches`, `run_outs`, `stumpings`, `dismissals` (the sum of the three), and `dismissals_per_match` (`None` if `matches == 0`, not a division error).
- `build_fielding(conn) -> dict` — loops `build_fielding_for_format` over every format present in `enabled_sources()`, stamps `fielding_built_at` in `meta`.
- `get_fielding(conn, player_id, fmt="T20") -> dict | None` — a single-row lookup against `player_fielding`.
- `better_fielder(conn, player_id_a, player_id_b, fmt="T20") -> dict` — ranks two players by fielding record: once *both* have `>= MIN_MATCHES_FOR_RATE` matches, compares `dismissals_per_match`; otherwise falls back to comparing raw `dismissals`, since a per-match rate over a handful of matches is noise, not signal. Returns `{"comparable": False, ...}` if either player has no fielding record at all, rather than guessing.

**How it connects:** Imports `config.enabled_sources`, `db.set_meta`, `identity.player_id_map`, `logging_utils`. Called by `cli.py`'s `fielding` subcommand and by `refresh.py` (step 8 of the pipeline, after `registry`/`career`, before `player_card` — `player_card.py` attaches its output to every card). Its output table (`player_fielding`) is read directly by `model-training`'s `recommend/score.py` and `selection/optimize.py` (never through this module — that package only reads the DB, never imports `data-collection`'s own code).

### `data-collection/criiq_data/download_cricsheet.py`

**Purpose:** Downloads the raw Cricsheet match-data zip files (one per `CricsheetSource` defined in `config.py`) into `RAW_DIR`, with change-detection so it doesn't re-download unchanged files on every run. This is stage one of the pipeline, run before `ingest.py` can parse anything.

**Key pieces:**
- `_fingerprint(resp_headers)` — builds a cheap identity string from `Last-Modified|Content-Length` HTTP response headers. Not a real content hash, just enough to detect "has this file plausibly changed since we last saw it."
- `download_source(conn, src, *, force=False)`:
  1. If the destination file already exists and `force` is not set, does a lightweight `HEAD` request (`http.head`) to get fresh headers without downloading the body, computes a new fingerprint, and compares it against the previously stored one (`meta` table, key `cricsheet_fp::{filename}`). If they match, skips the download entirely and returns a `"status": "unchanged"` result — this is the efficiency mechanism that lets `refresh.py`/cron jobs call this frequently without re-pulling gigabytes of data each time.
  2. Otherwise, streams the GET response in 64KB chunks (`chunk_size=1<<16`) to a temporary `.part` file, then atomically renames it to the final destination (`tmp.replace(dest)`) once fully written — this atomic-rename pattern avoids leaving a half-written file at the real path if the download is interrupted mid-stream.
  3. Records the new fingerprint and a `cricsheet_downloaded_at::{filename}` timestamp in `meta`, commits, and returns a `"status": "downloaded"` result with byte count.
- `download_all(conn, *, force=False)` — loops `download_source` over every `enabled_sources()` entry, catching exceptions per-source so one failing download (e.g. a dead URL) doesn't abort the rest — each source's result or error is collected into a list and returned.

**How it connects:** Imports `http` (for `get`/`head`), `config` (`RAW_DIR`, `SETTINGS`, `CricsheetSource`, `enabled_sources`, `ensure_dirs`), `db` (`get_meta`, `set_meta`), `logging_utils`. Called by `cli.py`'s `download` subcommand and by `refresh.py`.

### `data-collection/criiq_data/download_register.py`

**Purpose:** Downloads Cricsheet's global "people register" CSV (`people.csv` — the canonical identifier→name/Cricinfo-key mapping for every player Cricsheet knows about) and loads it into the `people` table. This register is what lets `identity.py` link a Cricsheet match identifier to a real Cricinfo profile key.

**Key pieces:**
- `_KEEP = ["identifier", "name", "unique_name", "key_cricinfo", "key_cricinfo_2"]` — the subset of CSV columns actually persisted; anything else in the upstream CSV is discarded.
- `download_register(conn)`:
  1. Downloads the CSV via `http.get`, decoding as UTF-8 with `errors="replace"` (tolerant of any encoding glitches in the upstream file rather than crashing).
  2. Writes the raw text to `REGISTER_DIR/people.csv` as a local cache/audit copy, independent of the DB write.
  3. Parses it with `csv.DictReader`, and for each row builds a cleaned record: every kept field is stripped of whitespace, and empty strings become `None` (`(r.get(k) or "").strip() or None`) rather than being stored as `""` — rows with no `identifier` are skipped entirely since that's the primary key.
  4. Counts how many rows have a non-null `key_cricinfo` (tracked separately as `with_cricinfo`, purely for the log line / return value — a useful data-quality signal since not every Cricsheet player has a matched Cricinfo profile).
  5. Upserts all rows into `people` (`ON CONFLICT(identifier) DO UPDATE`), stamps `register_downloaded_at` in `meta`, commits.

**How it connects:** Imports `http`, `config` (`REGISTER_DIR`, `REGISTER_URL`, `SETTINGS`, `ensure_dirs`), `db.set_meta`, `logging_utils`. Called from `cli.py`'s `download` subcommand (alongside `download_cricsheet.download_all`).

### `data-collection/criiq_data/h2h.py`

**Purpose:** Provides head-to-head query functions — batter-vs-bowler and player-vs-opponent-team — directly against the raw `deliveries`/`matches` tables. Unlike `advanced.py`/`career.py` (which precompute and store aggregate tables), this module runs its SQL live per request, since head-to-head queries are naturally sparse/long-tail (most batter-bowler pairs have few or zero deliveries) and aren't worth precomputing for every pair. It also defines `BOWLER_WICKETS`, the shared vocabulary of dismissal types credited to the bowler, which is imported by several other modules (`advanced.py`, `impact.py`).

**Key pieces:**
- `BOWLER_WICKETS = {"bowled", "caught", "lbw", "stumped", "caught and bowled", "hit wicket"}` — the set of `wicket_type` values that count as a bowler's wicket (as opposed to e.g. run-out, retired hurt, or obstructing the field, which aren't the bowler's doing). This constant is the canonical definition used everywhere in the codebase that needs to credit a dismissal to a bowler.
- `names_for_player(conn, player_id)` — resolves a `player_id` back to (a) every raw name string Cricsheet ever recorded for her (`identifier_map`, since a player can appear under slightly different name spellings across matches) and (b) her `gender`. The docstring is explicit about *why* gender must travel alongside the name list: `identifier_map` itself has no gender column, so any query built from just the name list would, for a colliding identifier (two different real people sharing one Cricsheet id, disambiguated by gender in `players`), blend both people's deliveries together unless the caller also filters by the returned gender. Returns `([], None)` if the player/identifier can't be found.
- `batter_vs_bowler(conn, fmt, batter_names, bowler_names, batter_gender=None, bowler_gender=None)`:
  1. Short-circuits to a zeroed dict if either name list is empty.
  2. `gender = batter_gender or bowler_gender` — takes whichever was actually passed (both should agree when both come from a resolved `player_id`, per the docstring warning).
  3. Builds a single SQL query joining `deliveries`+`matches`, filtered to the given format, `team_type='international'`, striker in `batter_names`, bowler in `bowler_names`, and (if a gender is known) `m.gender=?`. It computes `balls` (wides excluded), `runs` (sum of `runs_off_bat`), and `dismissals` (count where `player_dismissed` is one of the batter's names AND `wicket_type` is in `BOWLER_WICKETS`).
  4. Returns strike_rate (`100*runs/balls`) and `dismissal_rate` (`dismissals/balls`, to 4dp — a fine-grained rate since dismissals are rare per-ball events), both `None` if zero balls.
- `player_vs_team(conn, fmt, player_id, opponent_team)` — resolves the player's names+gender via `names_for_player`, then runs two separate queries: one for her batting record against `bowling_team=opponent_team` (balls, runs, dismissals, strike rate) and one for her bowling record against `batting_team=opponent_team` (balls — excluding both wides and no-balls this time since it's total bowling workload — runs conceded as `runs_off_bat + wides + noballs`, wickets via `BOWLER_WICKETS`, economy). Each half of the result dict (`batting`/`bowling`) is only included if she has at least one relevant ball recorded, so a specialist bowler's `vs_team` result has no spurious empty `batting` key.
- `_in(names)` — trivial helper generating the right number of `?` placeholders for a SQL `IN (...)` clause.

**How it connects:** Imports only `logging_utils`. `BOWLER_WICKETS` is imported by `advanced.py` and `impact.py`; `batter_vs_bowler`/`names_for_player` are imported directly by `cli.py` for the `h2h` subcommand.

### `data-collection/criiq_data/http.py`

**Purpose:** A thin shared wrapper around the `requests` library providing a persistent session, a configurable User-Agent, per-host rate limiting, and retry/backoff on transient failures — used by every module that fetches external data (`download_cricsheet.py`, `download_register.py`, and presumably `scrape_cricinfo.py`/`styles.py`/`rankings.py` elsewhere in the package).

**Key pieces:**
- `session()` — lazily creates and caches a single module-level `requests.Session` (`_session` global) with the `User-Agent` header set from `SETTINGS.user_agent` (which self-identifies as `"criiq-data-collector/0.1 (academic project; ...)"` — a courteous, transparent UA string for scraping external sites). Reusing one session across calls keeps connections/cookies alive.
- `_last_request_at: dict[str, float]` — a module-level dict tracking, per hostname (`urlparse(url).netloc`), the monotonic timestamp of the last request made to it.
- `_respect_delay(url, delay_s)` — before making a request, checks how long it's been since the last request to that same host; if less than `delay_s` has elapsed, sleeps for the remaining time. This is a simple **per-host** rate limiter (not global), so hitting Cricsheet and Cricinfo in quick succession from the same process doesn't force artificial delays between them — only repeated hits to the *same* host are throttled.
- `get(url, *, delay_s=None, stream=False, timeout=None, **kwargs)`:
  1. Falls back to `SETTINGS.cricsheet_delay_s`/`http_timeout_s` if not overridden by the caller.
  2. Retries up to `SETTINGS.http_retries` times. Before each attempt, calls `_respect_delay`.
  3. Treats HTTP 429/500/502/503/504 as retriable by manually raising an `HTTPError` for them (even though `requests` wouldn't raise automatically until `raise_for_status()`), so those specific transient status codes trigger the retry/backoff path rather than being returned to the caller as a "successful" response with an error status.
  4. On any `requests.RequestException` (network error or the manually raised HTTPError above), if attempts remain, sleeps for an exponentially increasing backoff (`http_backoff_s * 2**(attempt-1)`) and logs a warning, then retries; if attempts are exhausted, re-raises the last exception.
- `head(url, *, delay_s=None)` — a single-attempt (no retry loop) `HEAD` request with `allow_redirects=True`; returns `None` (rather than raising) on any `RequestException`, logging a warning instead — used by `download_cricsheet.py` purely as a best-effort "has this changed" probe where failure just means "assume it might have changed, download it."

**How it connects:** Imports `config.SETTINGS` and `logging_utils`. Imported by `download_cricsheet.py` and `download_register.py` (and likely other scraping modules like `scrape_cricinfo.py`/`rankings.py`, not reviewed in this batch).

### `data-collection/criiq_data/identity.py`

**Purpose:** The identity-resolution layer that turns Cricsheet's raw per-match player identifiers (and raw venue name strings) into stable, deduplicated `player_id`s and canonical venue names used by every downstream aggregation module. This is arguably the most structurally important file in the package, because nearly every other builder module's "gender-scoped groupby" pattern exists specifically to work around the edge case this file documents and handles: a small number of Cricsheet identifiers are reused across two different real people of different genders.

**Key pieces:**
- `_NS` — a fixed UUID namespace constant used to deterministically derive player ids.
- `player_id_for(identifier, gender=None)` — generates a stable `player_id` via `uuid.uuid5(_NS, f"cricsheet:{identifier}{suffix}")` where `suffix` is `":{gender}"` only if gender is given. The docstring instructs callers to only pass `gender` when the identifier is known to collide across genders (per `_colliding_identifiers`), so that the vast majority of stable, non-colliding ids don't change unnecessarily.
- `player_id_map(conn)` — reads the whole `players` table and splits it into two dicts: `unambiguous` (`cricsheet_identifier -> player_id`, for rows where `gender IS NULL`, i.e. ~99.5% of players per the docstring) and `split` (`(cricsheet_identifier, gender) -> player_id`, for the disambiguated collision rows). The docstring is explicit about the *why*: a single plain `identifier -> player_id` dict would silently pick one of the two colliding people's ids and misattribute all of the other person's stats to them.
- `resolve_player_ids(conn, identifiers, genders=None)` — a vectorized/pandas version of the same lookup: maps a Series of identifiers through `unambiguous` first, and for any still-unmapped rows (only relevant if `split` is non-empty), falls back to mapping `(identifier, gender)` tuples through `split`. Explicitly converts the result to `object` dtype and replaces `NaN` with real `None`, because `pandas.map()` misses produce a *truthy* `nan` value that would silently defeat any caller doing `if not pid: continue`.
- `_slug(text)` — lowercases and collapses everything that isn't `[a-z0-9]` into single hyphens, trimming leading/trailing hyphens — a simple slugify used for venue ids.
- `_derived_roles(conn)` — computes a fallback batting/bowling role per `(identifier, gender)` when no external metadata exists. **Rewritten** to fix real cross-sport contamination (a player's Cricsheet-adjacent name matching some unrelated sport's data was pulling in bogus ball counts) — raw ball-count thresholds alone weren't enough to separate cameo bowlers from genuine ones:
  1. Builds a name→identifier→gender mapping (joining `identifier_map`, `match_players`, `matches`).
  2. Separately aggregates total legal balls faced (`wides=0`) and legal balls bowled (`wides=0 AND noballs=0`) per `(player_name, gender)`, **plus now also `matches_played` (distinct match count from `match_players`/`matches`) and `matches_bowled_in` (distinct match count where she bowled at least one legal ball)**.
  3. Merges all four onto the identity mapping, fills missing counts with 0, and sums by `(identifier, gender)`.
  4. Classifies via `_BOWLER_MIN_BALLS = 60` **and** `_BOWLER_MATCH_FRACTION_THRESHOLD = 0.30`: `is_bowler = balls_bowled >= 60 and (matches_bowled_in / matches_played) >= 0.30` — i.e. bowled at least 10 legal overs' worth *and* actually bowled in at least 30% of the matches she appeared in, not just accumulated 60 balls total across a long career of occasional overs. Then: `is_bowler and balls_faced >= 60` → `"all-rounder"`; `is_bowler` alone → `"bowler"`; `balls_faced >= 1` → `"batter"`; else `"unknown"`. The code comment gives the real numbers that justify the 30% cut: cameo bowlers Kohli (~11%) and Rohit Sharma (~5%) sit clearly below it, genuine bowlers like Bates (~45%) and Perry (~80%) sit clearly above it.
- `_colliding_identifiers(conn)` — finds every Cricsheet identifier that appears under more than one distinct gender across the whole per-match registry (joining `identifier_map`→`match_players`→`matches`, grouping distinct `(identifier, gender)` pairs). Returns only the identifiers with `len(genders) > 1` — this is the authoritative detection of the "collision" edge case referenced throughout the codebase.
- `resolve_players(conn)` — the main builder for the `players` table:
  1. Gathers every distinct identifier that's actually appeared in a match (via `identifier_map` joined to `match_players`); bails with a warning if none exist (ingest hasn't run yet).
  2. Loads the `people` register (from `download_register.py`) keyed by identifier, plus `_derived_roles` and `_colliding_identifiers`.
  3. For name display, builds `name_variants`: for each identifier, the *first* `player_name` alphabetically (`ORDER BY player_name` + `setdefault`) — used only as a last-resort canonical name when the identifier isn't in the official register at all.
  4. For each identifier: pulls the register row if present, derives `canonical` name (prefers `unique_name`, falling back to `name`, falling back to the name-variant guess) and `unique` name similarly. Sets a `resolution_method` label: `"register"` if she has a Cricinfo key, `"register_no_cricinfo"` if she's in the register but has no linked Cricinfo profile, `"cricsheet_only"` if she's not in the register at all — and correspondingly sets `needs_review=1` whenever there's no Cricinfo key (i.e. whenever `resolution_method != "register"` with a key), flagging her for manual review downstream.
  5. **Handles the collision case directly here**: if the identifier is in `_colliding_identifiers`, it mints one row *per gender* she appears under (each with its own gender-specific `player_id` from `player_id_for`); otherwise it mints a single row with `gender=None`. The role lookup (`role_key`) mirrors this: use `(ident, gender)` directly if gender is known, else search `roles` for any key matching just that identifier.
  6. Bulk-upserts all rows into `players` (`ON CONFLICT(player_id) DO UPDATE`).
  7. **Cleans up stale rows**: deletes any `players` row whose `player_id` isn't in the just-computed `valid_ids` set. The comment clarifies this serves two purposes — removing identifiers no longer present in the data at all, *and* removing the old gender-agnostic id of an identifier that has just been newly split into per-gender ids (since that identifier's original single row's `player_id` won't be in the new `valid_ids` list once it's split).
  8. Returns summary counts (total, in-register, with-cricinfo, needing review, how many identifiers were split by gender).
- `fuzzy_match_name(name, candidates)` — thin wrapper over `rapidfuzz.process.extractOne` with the `WRatio` scorer, only accepting a match if its score is ≥ `SETTINGS.fuzzy_threshold` (88); otherwise returns `(None, score)` so the caller still sees how close the best miss was.
- `normalise_venues(conn)`:
  1. Pulls every distinct non-null `venue_raw` string from `matches`.
  2. For each, looks up a lowercased/stripped key in the hardcoded `_VENUE_ALIASES` dict (documented case-by-case fixes — e.g. mapping "punjab cricket association is bindra stadium, mohali" and the shorter variant both to `"PCA Stadium, Mohali"`; the largest comment block explains that the **default fallback** rule (`raw.split(",")[0]`) would otherwise incorrectly merge several distinct grounds that share a bare prefix like "County Ground" or "National Stadium" — e.g. Bristol/Chelmsford/Derby/Hove/Northampton/Worcester all have a ground literally called "County Ground", and Hamilton NZ / Karachi both have a "National Stadium" — so each of those is given its own explicit alias entry instead, with a `"(ground unspecified)"` label used when the raw string genuinely doesn't disambiguate).
  3. Falls back to `raw.split(",")[0].strip()` (take everything before the first comma) for anything not in the alias table.
  4. Upserts `(venue_raw, slug(canonical), canonical)` into `venues`, then updates every `matches` row's `venue_id` via a correlated subquery joining back to `venues.venue_raw`.
- `run(conn)` — calls `resolve_players` then `normalise_venues`, merging both result dicts.

**How it connects:** Imports `config.SETTINGS` (for `fuzzy_threshold`) and `logging_utils`; imports `rapidfuzz` lazily (only inside `fuzzy_match_name`) to avoid a hard dependency at module-import time if that function is unused. `player_id_map`/`resolve_player_ids`/`player_id_for` are imported by essentially every stats-building module (`career.py`, `advanced.py`, `impact.py`, and presumably `opponents.py`, `phases.py`, `wpa.py`, `venue_stats.py`, `matchups.py`, `ml_features.py`, `role_finalize.py`). `resolve_players`/`normalise_venues`/`run` are called from `cli.py`'s `identity` subcommand.

### `data-collection/criiq_data/impact.py`

**Purpose:** Computes a composite "importance/impact score" per player-format (the `player_impact` table) — a single 0-100 number meant to summarize how much a player has actually mattered to her team's results, beyond raw batting/bowling averages. It blends team-contribution share, win association, standout (Player-of-the-Match) rate, clutch bowling (top-order wicket-taking + economical spells), and clutch batting (frequent substantial innings), plus situational batting splits (setting vs chasing). This is one of the more "designed metric" files in the codebase, with unusually extensive comments justifying specific formula choices — including an explicit note about a past scoring bug that's since been fixed.

**Key pieces:**
- `TOP_ORDER = 4` — batting positions 1-4 count as "top order" for the purposes of "top order scalps" (wickets of top-order batters).
- `_wicket_events(deliv, name2id)` — reshapes delivery-level data into one row per credited bowler wicket, with partnership context:
  1. Sorts deliveries chronologically within each match/innings, and computes a running total (`cum`) of `runs_total` per innings via `cumsum()` — the cumulative team score at each ball.
  2. Determines each batter's **batting position**: builds a "long" table pairing every ball with both the striker and non-striker (each tagged with the ball's chronological order index `o`), takes the *first* ball index at which each batter appears in the innings (`groupby(...)["o"].min()`), then ranks those first-appearance indices within the innings (`rank("first")`) to get an integer batting position (1st in, 2nd in, etc.) — this is a purely data-derived batting order, not read from any explicit "position" field, since Cricsheet doesn't provide one directly.
  3. Filters to deliveries where someone was dismissed, computes `prev_cum` (the team's score just before this wicket, via a `shift(1)` within match/innings, defaulting to 0 for the very first wicket), and `partnership_broken = cum - prev_cum` — literally the number of runs added by the partnership that just ended, i.e. how big a partnership this wicket broke.
  4. `credited` flags whether the dismissal type is in `BOWLER_WICKETS` (imported from `h2h.py`) — non-bowler dismissals (run outs, etc.) are excluded from bowling-impact stats.
  5. Merges in the dismissed batter's `position` (computed above), maps the bowler's name to an identifier, and returns only rows that are both bowler-credited and have a resolved bowler id.
- `build_impact_for_format(conn, fmt)`:
  1. Pulls the format's per-innings table (`stats.build_innings`) and the raw deliveries (with `gender`), plus name→identifier and `players` metadata maps, plus `unambiguous`/`split` player-id maps, plus `opponents.potm_match_to_ident` (maps each match to which identifier was named Player of the Match).
  2. Computes each team's total runs and total wickets lost per match (`team_runs`, `team_wkts` dicts keyed by `(match_id, team)`), then attaches each innings-row's own team's totals as `team_runs`/`team_wkts` columns, and derives:
     - `bat_contrib = runs / team_runs` (only if she actually faced a ball and the team scored something) — her share of the team's total runs in that innings.
     - `bowl_contrib = wickets / team_wkts` (only if she bowled and the team took wickets) — her share of the opposition wickets taken.
     - `potm` — boolean, whether she was this match's Player of the Match.
  3. Computes situational (`sit`) batting splits by `innings` number (1 = setting/batting first, 2 = chasing) per `(striker_id, gender, innings)`: runs, legal balls, and separately, dismissals per `(dismissed_id, gender, innings)` — used later for `setting_strike_rate`/`chasing_strike_rate` and their averages.
  4. Calls `_wicket_events` and aggregates `bowl_impact` per `(bowler_id, gender)`: total credited wickets, mean `partnership_broken` (`avg_pp` — the average size of partnership she typically ends), and count of wickets where the dismissed batter's position was ≤`TOP_ORDER`.
  5. Main loop, grouped by `(identifier, gender)`, resolving `player_id` and metadata the same way as `career.py`/`advanced.py`:
     - `matches` = distinct match count for this player.
     - `bat_contrib`/`bowl_contrib` are averaged (mean of the per-innings contribution fractions) across all her innings where she batted/bowled, expressed as a percentage.
     - `win_pct` = mean of the `won` flag across all her appearances.
     - `avg_runs_in_wins`/`avg_runs_in_losses` — mean runs scored in innings where her team won vs lost (only among innings she actually batted).
     - `potm_awards`/`mwp` (match-winning performances) — count of PotM awards, and count of PotM awards that were *also* in a winning match.
     - Bowling-impact fields pulled from `bowl_impact` if she has any credited wickets, else zeroed.
     - **"Economical spell"** definition, explicitly calibrated per the comment: a bowled innings with ≥12 legal balls (2 overs) and economy ≤6.0 runs/over; the comment states the 12-ball/6.0 cutoff was chosen so the *qualifying rate*'s 75th percentile lines up with the top-order-scalps-per-match rate's 75th percentile, so both later "bonus" terms cap out at a comparably rare threshold (an attempt at fairness between the wicket-taking and economy sub-scores).
     - `_sit(innum)` — looks up the situational batting stats for innings 1 or 2, computing strike rate and average (average uses the separately-tracked dismissal count for that innings, not batting-innings count).
     - `big_innings` — count of innings with ≥30 runs, described as the batting-side equivalent of `top_order_scalps`; the multiplier used later (`*70`) is likewise explicitly calibrated ("so both bonuses hit their 15.0 cap at a comparably rare percentile") to keep the batting and bowling bonus terms comparably attainable.
     - **The importance-score formula** — five weighted components summing to a 0-100 scale, each independently capped:
       - `contribution_part = min(35.0, (bat_contrib + bowl_contrib) * 0.9)` — up to 35 points from combined batting+bowling team-contribution share.
       - `winning_part = 25.0 * win_pct / 100` — up to 25 points, linear in win percentage.
       - `standout_part = 25.0 * min(1.0, (potm_awards/matches) / 0.12)` — up to 25 points, scaling linearly with PotM rate up to a 12% rate (beyond which it's capped at the full 25).
       - `bowling_part = wicket_rate_part + economy_part`, each independently `min(7.5, (rate_per_match) * 15)` — a 15-point bowling bonus split evenly between top-order wicket-taking rate and economical-spell rate. A long comment explicitly documents that this 50/50 split is a **deliberate fix** to a previous version of the formula where the entire 15-point bowling bonus came from wicket-taking rate alone, meaning two bowlers with identical wicket rates scored identically even if one leaked boundaries constantly and the other bowled tight — the fix halves each sub-bonus's multiplier (`*15` instead of `*30`) so each half still hits its own 7.5-point cap at the same rate-percentile the original single bonus did, keeping a genuinely elite economical wicket-taker's total 15-point ceiling unchanged.
       - `batting_impact_part = min(15.0, (big_innings/matches) * 70)` — up to 15 points from frequency of substantial (≥30-run) innings.
       - The comment also notes this change means a genuine dual-threat all-rounder can now earn *both* the 15-point batting and (implicitly, elsewhere) other bonuses simultaneously where before it may not have been possible, and that the final `min(100.0, ...)` clamp exists specifically to keep the total on a proper 0-100 scale now that more combinations of bonuses can stack — pure specialists are described as unaffected since they'd only ever earn one bonus type anyway.
     - `components` — a JSON-serializable breakdown of every sub-score plus the raw input rates, stored in `importance_components` for later explainability (so a UI can show *why* a player scored what she did, not just the final number).
  6. Bulk-upserts all rows into `player_impact`.
- `build_impact(conn)` — loops over enabled formats, stamps `impact_built_at` meta.
- `get_impact(conn, player_id, fmt)` — fetches one row, JSON-decoding `importance_components` back into a dict if present.

**How it connects:** Imports `config.enabled_sources`, `db.set_meta`, `h2h.BOWLER_WICKETS`, `identity.player_id_map`, `opponents.potm_match_to_ident`, `stats.build_innings`, `logging_utils`. Called from `cli.py`'s `impact` subcommand.

### `data-collection/criiq_data/ingest.py`

**Purpose:** Reads raw Cricsheet zip archives (one per data source: e.g. international women's T20, men's T20, "Blaze" domestic T20, etc — as declared in `config.enabled_sources()`) and loads them into the SQLite database as rows in `matches`, `match_players`, `identifier_map`, and `deliveries` (or their `_holdout` twins). This is the very first step of the pipeline (`refresh.py` step 3/12) — everything downstream (identity resolution, career stats, ML features) depends on the shape this file produces.

**Key pieces:**
- `_parse_info(text)`: Cricsheet's `<match_id>_info.csv` is a flat `info,key,value[,value2]` CSV. This function walks each row with `csv.reader` and buckets rows by key: `team` rows append to `info["teams"]`, `date` rows to `info["dates"]`, `player` rows (team, name) to `info["players"]`, `registry,people,name,id` rows to `info["registry"]` (the Cricsheet-to-real-person identifier mapping), and `winner_runs`/`winner_wickets`/`winner_innings` go into `info["extra"]` by exact key (not the generic fallback) so `_win_margin` can find them; everything else is captured into `extra` via `setdefault` (first occurrence wins, since some info files repeat keys like multiple `player` rows aren't hit here but generic single-value keys could appear more than once).
- `_norm_date(raw)`: normalizes `/`-separated dates to ISO format via `dt.date.fromisoformat`; if parsing fails, returns the raw string unchanged rather than raising — a deliberate "don't crash on messy data" choice.
- `_win_margin(info)`: builds a human-readable margin string, preferring `winner_runs` > `winner_wickets` > `method` (e.g. rain-affected results) > generic `result`, in that priority order.
- `_existing_match_ids(conn)`: unions match_ids from both `matches` and `matches_holdout` tables so that re-running ingest never re-inserts a match that already landed in either table — the comment explains this is needed so holdout matches (see below) aren't re-ingested as if new.
- `ingest_source(conn, src)`: the main per-zip-file loader. Opens the zip, filters `namelist()` down to files matching `<match_id>.csv` that aren't summary/info files. For each match file not already ingested: reads the paired `_info.csv`, and — if the source declares `fmt == "T20"` — skips matches whose `match_type` isn't `T20`/`IT20` (non-T20 games bundled in a supposedly-T20 zip get discarded, counted as `non_t20_skipped`). It computes whether the match date is after `SETTINGS.data_cutoff_date`; if so, it's routed to `matches_holdout`/`match_players_holdout`/`deliveries_holdout` instead of the production tables — this is a leakage guard so that model training never sees matches beyond the declared cutoff. It reads the raw delivery CSV as all-string columns (avoiding pandas' automatic type inference, which can mis-parse things like over numbers), passes it through `validate_deliveries` (from `validate.py`), quarantines any rejected rows, reshapes the survivors via `_shape_deliveries`, and inserts everything with `INSERT OR IGNORE` (idempotent against partial re-runs). It commits after every single match — deliberately, so a crash partway through a large zip doesn't lose all prior progress.
- `_shape_deliveries(df, match_id)`: converts the raw Cricsheet CSV columns into the fixed `_DELIV_COLS` schema, which now includes `fielder_1`/`fielder_2`/`fielder_3` (carried straight through via `df.get("fielder_1")` etc. — `None` for any Cricsheet variant that doesn't provide them). The `ball` column (e.g. `"12.4"`) is split on `.` into `over` and `ball_in_over` via string splitting, not float parsing — because float division would be lossy/ambiguous for something that's actually two separate integers glued with a dot. `runs_total = runs_off_bat + extras` is computed explicitly rather than trusted from the source (some Cricsheet variants omit a total column). Missing numeric fields default to 0 via `fillna(0)`. The final `.astype(object).where(pd.notna(out), None)` step converts pandas' NaN sentinels into real Python `None` so SQLite stores actual NULLs, not the string `"nan"`.
- `backfill_fielders(conn) -> list[dict]`: a one-time, no-network enrichment for matches ingested *before* `fielder_1/2/3` existed in the schema. Re-reads already-downloaded zips (nothing is re-fetched over the network) purely to recover the fielder columns on wicket-ball rows, and `UPDATE`s them in place. Idempotent by construction — guarded on `fielder_1 IS NULL`, so already-backfilled rows are never touched twice, and it's safe to run on every `refresh` even once every match has been backfilled (it'll just find nothing left to do).
- `ingest_all(conn)`: loops `config.enabled_sources()`, calling `ingest_source` for each, catching and logging (not raising) any per-source exception so one bad zip doesn't abort the whole pipeline.

**How it connects:** imports `config` (`RAW_DIR`, `SETTINGS`, `CricsheetSource`, `enabled_sources`), `db.set_meta` (records last-ingested timestamp per source), `logging_utils.get_logger`, and `validate` (`quarantine`, `validate_deliveries`). It's called by `refresh.py` (step 3, immediately followed by `backfill_fielders` as part of that same step) and directly by `tests/test_pipeline.py`, which builds synthetic Cricsheet-shaped zips in memory to exercise `ingest_source` end-to-end (including the holdout-routing behavior).

### `data-collection/criiq_data/logging_utils.py`

**Purpose:** A tiny shared logging setup so every module in the package logs consistently to stdout with the same timestamp/level/module format, without each module reconfiguring the root logger (which would duplicate handlers if done more than once).

### `data-collection/criiq_data/matchups.py`

**Purpose:** Builds batter-vs-bowler "dismissal matchup" tables — both a global one (`dismissal_matchup`) and a venue-specific one (`venue_dismissal_matchup`) — that answer "how has player X fared against player Y (optionally at ground Z)?" These feed `sheet.py`'s "bogey bowler" summaries and the model-training recommendation engine's matchup matrix.

**Key pieces:**
- `build_for_format(conn, fmt)`: pulls every delivery for the format (international-only), maps `striker`/`bowler` names to Cricsheet `identifier`s via `identifier_map`, computes `legal` (wides excluded — a wide isn't a fair ball faced), and `dismissed` (true only if `player_dismissed == striker` AND the wicket type is in `BOWLER_WICKETS` from `h2h.py` — run-outs etc. aren't credited to the bowler). It groups by `(sid, bid, gender)` — gender is in the key because, as the comment explains, some Cricsheet identifiers are shared by two real people of different genders, and grouping without gender would blend their separate careers together. Rows with fewer than `MIN_MATCHUP_BALLS = 6` (about one over) balls are dropped as too small a sample — but rows with 0 dismissals are deliberately kept, since "never been dismissed by X" is itself a real, useful fact, not a null result. The most common team a bowler bowled for (`bteam`, via `.mode()`) fills in `bowler_team` for opponent-scoped queries later. Resolves each `(identifier, gender)` pair to a stable `player_id` via `identity.player_id_map`, using the split-map first for ambiguous identifiers, and inserts/updates via `ON CONFLICT`.
- `build_venue_matchups_for_format(conn, fmt)`: identical logic, but also joins on `m.venue_id` and includes it in the groupby key and unique constraint, producing a ground-specific version of the same table.
- `top_dismissers_at_venue` / `top_dismissers` / `favourite_victims`: straightforward read queries ordered by dismissals then balls.
- `batter_vs_team_bowlers(conn, player_id, fmt, opponent_team)`: for a given batter, returns every bowler from `opponent_team` she's faced at least `MIN_MATCHUP_BALLS`, computing `strike_rate = 100*runs/balls` and `dismissal_rate = dismissals/balls`, sorted by dismissals then balls (so the "bogey_bowler" — first in the list — reflects real dismissal history, not just raw ball volume or rate).
- `bowler_vs_team_batters(conn, player_id, fmt, opponent_team, gender)`: the bowler-side mirror. Since `dismissal_matchup` has no `batting_team` column, it can't filter batters by opponent team directly — instead it calls `role_finalize.team_candidates` to get the roster of players who've appeared for that team, and filters `batter_id IN (...)` against that roster. Computes `economy = 6*runs/balls` and sorts by `(-wickets, -balls)`. `best_matchup` (most wickets) is `None` if no wickets were taken at all (guarding against a false "best matchup" when nothing actually happened); `most_expensive` is simply the max-runs entry.

**How it connects:** imports `config.enabled_sources`, `db.set_meta`, `h2h.BOWLER_WICKETS`, `identity.player_id_map`, `logging_utils`. `role_finalize.team_candidates` is imported lazily inside `bowler_vs_team_batters` to avoid a circular import. Called from `refresh.py` (step 10/12) and `sheet.py` (for the player one-pager). Tested in `test_pipeline.py` (`test_dismissal_matchup`, `test_venue_dismissal_matchup`, `test_batter_and_bowler_vs_team_breakdowns_include_safe_matchups`).

### `data-collection/criiq_data/ml_features.py`

**Purpose:** Builds the three datasets that feed model-training: `match_features` (win/loss prediction features per match, per team), `ball_state_<fmt>.parquet` (ball-by-ball game-state features used to train the win-probability model in `winprob.py`), and `player_match_impact` (per-player per-match derived stats). This is the bridge between the raw ball-by-ball database and the model-training package.

**Key pieces:**
- `_team_totals` / `_team_wickets`: simple SQL aggregates giving each `(match_id, team)` pair's total runs scored / wickets lost, used by several functions below as denominators for contribution percentages.
- `build_match_features_for_format(conn, fmt)`: builds a "long" table with one row per `(match, team)` (so two rows per match — team1's perspective and team2's), including `won` (1/0/None if the match had no clear winner e.g. no-result), `scored`, `conceded`. It then computes rolling-form features *per team* using pandas' `groupby("team").transform`: `form_winpct` and `avg_score`/`avg_conceded` are rolling means over the trailing 10 matches (`rolling(10, min_periods=1)`), and critically `.shift()` is applied before rolling — this excludes the current match from its own rolling window, preventing the label from leaking into the feature. `h2h_winpct` is an `expanding().mean()` (also shifted) over the specific team-vs-opponent pairing, i.e. all-time head-to-head win rate up to (not including) this match. It then re-splits the long table back into team1/team2 perspective (`t1`, `t2` indexed by match_id) and assembles one row per match with `label_team1_won` as the target label, plus derived `winpct_diff` and `avg_score_diff` (team1 minus team2). `result_type` is `"result"` vs `"no_result"` based on whether `winner` is set. Writes via upsert to `match_features`.
- `build_ball_state_for_format(conn, fmt)`: reconstructs cumulative game state ball-by-ball for T20 international matches: `score` and `balls_bowled` are cumulative sums (`.cumsum()`) within each `(match_id, innings)` group, `wickets` similarly. `phase` buckets overs into powerplay (≤5)/middle(≤14)/death using the same convention as `phases.py`. `current_run_rate = 6*score/balls_bowled`. For the second innings, `target = <innings-1 max score> + 1` and `runs_required`/`req_run_rate` are computed, masked to only apply when `chase` (innings==2) — first-innings rows get NaN/null for these chase-specific columns via `.where()`. The label `label_batting_team_won` is set to NA when the match has no winner. Writes to a parquet file (not the SQL DB) at `FEATURES_DIR/ball_state_<fmt>.parquet`, since this is meant for bulk ML consumption, not per-row lookup.
- `build_player_match_impact_for_format(conn, fmt)`: takes `stats.build_innings` (per-player per-match batting+bowling summary) and computes, per row: strike rate, economy, `bat_contribution_pct = 100*runs/team_total_runs`, `bowl_contribution_pct = 100*wickets/team_total_wickets`, `dot_pct`/`boundary_pct` (both `None`, not 0, if the player didn't bowl at all — a deliberate choice so a non-bowler doesn't silently read as "0% dots"), `bowl_strike_rate = balls/wickets` (also `None` for a wicketless spell, so it doesn't average toward "instant wickets" when aggregated later), and a combined `impact = bat_contribution_pct + bowl_contribution_pct` (treating missing contributions as 0 only for this sum). Player IDs are resolved gender-aware via `identity.resolve_player_ids` because of the identifier-collision issue documented elsewhere in the codebase.
- `build_match_features`, `build_ball_state`, `build_player_match_impact`, `build_all`: per-format loop wrappers that also stamp `set_meta` timestamps.

**How it connects:** imports `config` (`FEATURES_DIR`, `enabled_sources`), `db.set_meta`, `identity.resolve_player_ids`, `logging_utils`, `stats.build_innings`. Called by `refresh.py` step 11/12. `winprob.py` reads the `ball_state_<fmt>.parquet` this module writes; `wpa.py` reuses `T20_BALLS` from here (but rebuilds ball state itself, deliberately, per its own docstring, to include all team types). Tested extensively in `test_pipeline.py` (`test_match_features_winloss`, `test_player_match_impact`, `test_ball_state`).

### `data-collection/criiq_data/opponents.py`

**Purpose:** Builds the `player_vs_opponent` table — a player's full batting+bowling record broken down by opposing team (e.g. "how has this player performed specifically against Australia?"). Feeds the player card ("record vs opponent" section) and `sheet.py`'s selector summary.

**Key pieces:**
- `potm_match_to_ident(conn, fmt)`: maps each match_id to the Cricsheet identifier of that match's Player of the Match, by resolving the stored `player_of_match` name string through `identifier_map`. Used to compute per-opponent PotM counts.
- `build_vs_opponent_for_format(conn, fmt)`: starts from `stats.build_innings` (one row per player per match with both batting and bowling numbers), drops rows without a resolvable `opponent`, flags whether each row's player was PotM for that match. Groups by `["identifier", "gender", "opponent"]` (gender in the key for the usual identifier-collision reason) to get `matches`, `won`, `potm` sums. Separately aggregates batting-only rows (`balls_faced > 0`) for `bat_innings`, `runs`, `balls_faced`, `dismissals`, `high_score`, plus counts of `fifties` (50 ≤ runs < 100) and `hundreds` (runs ≥ 100) computed as separate group-by-size counts. Similarly aggregates bowling-only rows, and computes `best` bowling figures per opponent by sorting `(wickets desc, runs_conceded asc)` and taking the first row per group (standard "best bowling figures" tie-break: most wickets, fewest runs). All these partial aggregates are left-merged onto the base `results` table (so a player with batting-only data against a team still gets a row, with bowling columns filled as 0/None). Final per-row math: `win_pct`, `bat_average = runs/outs` (None if never out — division by zero avoided), `bat_strike_rate`, `economy = 6*runs_conceded/balls_bowled`, `bowl_average`, `bowl_strike_rate`, `best_bowling` formatted as `"W/R"` string. Upserts to `player_vs_opponent`.
- `build_vs_opponent(conn)` / `get_vs_opponent(conn, player_id, fmt)`: format-loop wrapper and a simple ordered read.

**How it connects:** imports `config.enabled_sources`, `db.set_meta`, `identity.player_id_map`, `logging_utils`, `stats.build_innings`. Called by `refresh.py` step 10/12, `sheet.py`, and `matchups.py` doesn't use it but `player_card.py` doesn't either — it's read standalone via `get_vs_opponent`. Tested by `test_vs_opponent_record`.

### `data-collection/criiq_data/overrides.py`

**Purpose:** Lets a human manually override a player's retirement/availability status (e.g. "V Kohli retired from T20Is on 2024-06-29") via a CSV, because the ball-by-ball data alone can't detect retirement announcements — it can only infer inactivity from absence. This manual signal takes priority over the automatically-computed status in `registry.py`.

**Key pieces:**
- `_resolve(conn)`: builds a `key_cricinfo -> player_id` dict and a list of `(player_id, canonical_name)` pairs, used for matching CSV rows to known players.
- `load_csv(conn, path=None)`: reads the overrides CSV (default `PLAYER_STATUS_CSV`); if missing, logs and returns a zero-result dict rather than raising (overrides are optional). For each row, validates `retirement_status` is one of the fixed vocabulary (`ACTIVE`, `RETIRED_ALL`, `RETIRED_FORMAT`, `UNAVAILABLE`, `UNKNOWN`) — rows with anything else are silently skipped. Matching prefers exact `key_cricinfo` lookup; if absent, falls back to fuzzy name matching via `rapidfuzz.process.extractOne` with `fuzz.WRatio`, only accepting a match scoring ≥90 (a conservative threshold to avoid silently misattributing a status to the wrong player). `RETIRED_ALL` forces `fmt = "ALL"` regardless of what the CSV said, since retiring from all cricket isn't format-scoped. Upserts into `status_overrides` keyed on `(player_id, format)`.
- `scaffold_csv(path=None)`: writes a template CSV with example rows (Kohli, Lanning) to help a human fill it in.
- `overrides_map(conn, fmt)`: reads all override rows where `format IN ('ALL', fmt)` into a dict keyed by `player_id`. If a player has both an `ALL` row and a format-specific row, the format-specific one wins (the `if prev is None or r["format"] != "ALL"` condition means a later `ALL` row won't overwrite an earlier format-specific one, but a format-specific row will overwrite an earlier `ALL` one — order-dependent, but SQL doesn't guarantee row order here without an ORDER BY, which is a subtle latent assumption in the code, not something explicitly guarded).

**How it connects:** imports `config` (`OVERRIDES_DIR`, `PLAYER_STATUS_CSV`), `logging_utils`, `rankings.normalise_format` (reuses the same format-name normalization used for ICC rankings). `overrides_map` is consumed by `registry.py` to force-override the computed activity status. Called by `refresh.py` step 8/12. Tested by `test_status_override`.

### `data-collection/criiq_data/phases.py`

**Purpose:** Builds the `player_phase` table: batting and bowling performance split by match phase (powerplay/middle/death overs), plus each player's rank/percentile within their own team for that phase — this tells a coach "is this player specifically good at death bowling *relative to her own teammates*," not just in absolute terms.

**Key pieces:**
- `phase_of(over)`: the phase-bucketing rule shared by this file: overs 0–5 = powerplay, 6–14 = middle, 15+ = death (T20-specific split; consistent with `ml_features.py`'s inline equivalent).
- `_team_map(conn, fmt)`: for each `(identifier, gender)`, finds their most common team via `stats.build_innings` and `.mode()` — needed because rank-within-team requires knowing which team a player belongs to.
- `build_for_format(conn, fmt)`: pulls all deliveries, tags each with `phase`, `legal` (excludes wides), `legal_bowl` (excludes wides AND no-balls), and `rc` (runs conceded off that ball = runs off bat + wides + no-balls). Splits into a batting frame (`bat`, one row per delivery where `sid` — striker identifier — resolves) and bowling frame (`bw`). For batting: computes `bdry` (boundary flag, runs is 4 or 6 and legal), `dot` (legal ball with 0 runs), `out_self` (this striker was the one dismissed on this ball). Groups by `(sid, gender, phase)` for `balls`, `runs`, `bdry`, `dots`, `dis` sums, then `sr = 100*runs/balls`. Bowling side mirrors this with `dotb` (legal-bowl ball with 0 total runs conceded) and `wkt` (dismissal credited to the bowler, using `BOWLER_WICKETS`), producing `econ = 6*runs/balls`.
- `_rank(df, value, ascending, min_balls)`: the team-relative ranking logic — filters to rows meeting `min_balls` (30 for both bat/bowl), then within each `(team, phase)` group ranks players by the given `value` column (`method="min"` — tied values get the same rank, next rank skips accordingly, i.e. standard competition ranking) and records both `rank` and `size` (team's qualifying player count for that phase). Batting ranks by strike rate descending (higher SR = better rank); bowling ranks by economy ascending (lower economy = better rank).
- Main assembly loop: for every `(identifier, gender, phase)` combination seen in either the batting or bowling index, resolves `player_id`, and computes a batting-percentile (`bpct`) as `100*(size - rank)/(size - 1)` — this maps rank 1 of N to ~100th percentile and rank N of N to 0th, guarding the `size == 1` case (only one qualifying player: no basis for percentile, hardcoded to 100.0). Upserts to `player_phase`.
- `get_phases(conn, player_id, fmt)`: reads back all three phases ordered logically (powerplay, middle, death) via a `CASE` expression rather than alphabetically.
- `phase_vs_opponent(conn, player_id, fmt)`: a separate, un-persisted, on-demand computation (not stored in a table) — for a given player, looks up all her balls faced across all opponents, buckets each by `(opponent, phase)`, and computes ad-hoc strike rate per bucket. Uses `h2h.names_for_player` to get all name variants for the player (handling the same identifier possibly mapping to multiple display-name spellings).

**How it connects:** imports `config.enabled_sources`, `db.set_meta`, `h2h.BOWLER_WICKETS`, `identity.player_id_map`, `logging_utils`, `stats.build_innings`; lazily imports `h2h.names_for_player` inside `phase_vs_opponent`. Called by `refresh.py` step 10/12, and by `sheet.py` for the "best batting phase" and "phase vs opponent" summaries. Tested by `test_phase_intra_team_rank`.

### `data-collection/criiq_data/player_card.py`

**Purpose:** Assembles the single richest artifact in the pipeline — a JSON "player card" per `(player_id, format)` combining identity, career stats, latest match detail, recent form, contribution/impact metrics, retirement/status, and ICC ranking — stored as a JSON blob in `player_cards.card_json` for fast lookup by the API/UI layer, without re-querying dozens of tables per request.

**Key pieces:**
- `_overs(balls)`: formats a ball count as cricket's `overs.balls` notation (e.g. 13 balls → `"2.1"`).
- `_rfi(runs_series)`: "Recent Form Index" — an exponentially-weighted average of a batter's last `SETTINGS.form_window_innings` scores, with weight `lam**i` for the i-th-most-recent innings (`lam = SETTINGS.rfi_lambda`, presumably <1 so more recent innings count more). Computed as a weighted mean (`sum(w*r)/sum(w)`), not a simple average — deliberately recency-biased.
- `_trend(bat_runs)`: needs at least 4 innings to judge; splits the innings list in half, compares the mean of the second half to the first half. `>1.15x` → `"up"`, `<0.85x` → `"down"`, else `"flat"` — hardcoded thresholds for "meaningfully different," not statistical significance testing.
- `_support_tables(conn, fmt)`: precomputes three lookup dicts reused across all players in the format loop (to avoid re-querying per player): team totals per match (`tr`), team wickets per match (`tw`), and total death-overs (`over >= 15`) runs per `(identifier, gender)` for the "pressure index" metric later.
- `_ident_to_player(conn)`: maps `(cricsheet_identifier, gender)` to the full player row; documents that unsplit players (not affected by the identifier-collision issue) have `gender=NULL` in `players`, so callers must try the real-gender key first, then fall back to `(ident, None)`.
- `_registry_status(conn, fmt)`: pulls the precomputed `player_registry` row (built by `registry.py`) for status/ICC-rank fields, keyed by `player_id`.
- `_fielding_status(conn, fmt) -> dict[str, dict]`: a single-query read of `player_fielding` (matches/catches/run-outs/stumpings/dismissals/dismissals-per-match), keyed by `player_id` — the fielding equivalent of `_registry_status` above.
- `build_cards_for_format(conn, fmt)`: the main assembly. For each `(identifier, gender)` group in `build_innings` output (sorted by date), takes the `latest` (most recent) innings row and builds `latest_block` (date, opponent, venue, won/lost, and — only if the player actually batted/bowled that match — nested `batting`/`bowling` sub-dicts). It cross-references `matches_meta` to attach a `match_summary` (both teams' totals, winner, margin). `form_block` uses `_rfi`/`_trend` on the trailing `form_sparkline_len` innings. `impact_block` looks at the last `impact_recent_matches` (`n_recent`) matches: `runs_share = player_runs/team_runs` over that window, `wickets_share` similarly, `wicket_contribution_rate = total_wickets / matches_where_she_bowled` (only among matches she actually bowled in, not all matches), `pressure_index = death_overs_runs / total_career_runs` (what fraction of her career runs came under death-overs pressure), `win_contribution = mean(won)` over the recent window. Age is computed from `date_of_birth` if present, using `.days/365.25` (accounting for leap years) — wrapped in try/except for malformed DOB strings. `h2h` for the latest opponent comes from `h2h.player_vs_team`. The final `card` dict nests all these sections plus `icc_ranking` (from `rankings.player_rankings`), `status` (from `_registry_status`), and **`fielding`** (from `_fielding_status`, attached even when `None` — a player with no fielding record still gets the key, just with a null value). A flattened summary row (name, role, nationality, rfi, trend, latest date, matches played, and the full `card` serialized via `json.dumps`) is upserted into `player_cards`.
- `get_card(conn, player_id, fmt)`: simple read + `json.loads` of the stored blob.

**How it connects:** imports `career.career_from_group`, `config` (`SETTINGS`, `enabled_sources`), `db.set_meta`, `h2h.player_vs_team`, `logging_utils`, `rankings.player_rankings`, `stats.build_innings`, `styles` (`classify_bowling_detail`, `classify_hand`). Called by `refresh.py` step 8/12 — immediately after `fielding.build_fielding`, whose output (`player_fielding`) this module reads via `_fielding_status` — and read by `sheet.py` and multiple test cases (`test_player_card_contents`, `test_card_age_from_dob`, `test_rankings_load_marks_active`).

### `data-collection/criiq_data/rankings.py`

**Purpose:** Loads ICC player rankings (batting/bowling/all-rounder, by format and gender) either from a manually-curated CSV or a live public ICC endpoint, matches each ranked name to an internal `player_id`, and stores results in `icc_rankings`. This is a key signal for `registry.py`'s "is this player still relevant" classification (an ICC-ranked player is always `ACTIVE`).

**Key pieces:**
- `_unmatched_id(...)`: builds a synthetic stable ID string (`UNMATCHED::fmt::discipline::gender::rank::slug`) for ranking rows that couldn't be matched to a known player — so an unmatched entry still gets a deterministic identity for storage/dedup rather than being silently dropped.
- `normalise_format(value)`: maps loose format strings (`T20`, `T20I`, `IT20` → `"T20"`; `TEST`/`TESTS` → `"Test"`; `ODI` stays `"ODI"`) to the internal canonical format labels used throughout the DB schema.
- `_resolve(conn)`: same pattern as `overrides.py` — builds `key_cricinfo -> player_id` and a name list for fuzzy fallback matching.
- `_load_rows(conn, rows, ...)`: the shared ingestion logic for both CSV and live-fetched rows. Matches each row to a `player_id` by `key_cricinfo` first, then fuzzy name match (`rapidfuzz.WRatio`, ≥90 threshold, same conservative bar as overrides). Unmatched rows still get inserted, tagged with the synthetic `_unmatched_id` and `matched=0` — so unmatched entries are visible/auditable rather than silently discarded, but `ranked_ids`/`current_rank` (used by registry.py) explicitly filter `matched=1`, so an unmatched row never falsely marks someone ACTIVE. Upserts to `icc_rankings` keyed on `(player_id, format, discipline)`.
- `load_csv(conn, path=None)`: reads the manual CSV; returns a zero-result dict if the file doesn't exist (rankings are optional, don't crash the pipeline).
- `_response_rows(payload, ...)`: parses the ICC public JSON API's response shape — finds the first key ending in `-rank` in the payload's `data` dict (the API's key naming varies by discipline/format), then extracts `rank`/`Player-name`/`Points` (or `Rating`) fields per entry, handling the ICC's occasional `"="` tie notation in the `no` field by falling back to a separate `rank` field.
- `_ranking_url_is_public(url)`: a safety check requiring `https` scheme + non-empty host, used to refuse fetching from a non-public/malformed URL.
- `fetch_live_rows(...)`: iterates the cross-product of formats (`Test`/`ODI`/`T20`), genders (male/female), and disciplines (batting/bowling/allrounder), skipping the nonsensical `Test` + `female` combination (women's Test rankings don't exist in this system's model), calling the ICC endpoint once per combination with the appropriate `comp_type` parameter. Raises `RankingsFetchError` if no client ID is configured (refusing to guess/bypass ICC's access control) or if the endpoint returns 401/403.
- `write_csv`, `load_live`, `load(conn, prefer_live=True)`: `load` tries the live fetch first if a client ID is configured, falling back to the CSV on any exception — a resilience pattern so a network hiccup doesn't block the whole refresh.
- `scaffold_csv`, `ranked_ids`, `current_rank`, `player_rankings`: template writer and read helpers; `current_rank` returns the single best (lowest-numbered) rank across disciplines.

**How it connects:** imports `config` (several `ICC_RANKINGS_*` constants, `RANKINGS_DIR`, `SETTINGS`), `logging_utils`; lazily imports `rapidfuzz` inside `_load_rows` (an optional dependency only needed when actually loading rankings). Consumed by `registry.py` (`current_rank`, `ranked_ids`) and `player_card.py` (`player_rankings`). Called by `refresh.py` step 8/12. Tested by `test_rankings_load_marks_active`, `test_rankings_parse_public_payload`, `test_rankings_live_fetch_loads_mocked_public_feed`.

### `data-collection/criiq_data/refresh.py`

**Purpose:** The orchestrator — a single `run()` function that executes the entire 12-step data-collection pipeline in order, from downloading raw data through building every derived table, and records a summary + timestamp. This is what the CLI's main "refresh" command ultimately calls.

**Key pieces:**
- `run(*, force_download=False, enrich=False, scan_rss=True, seed_styles=False, db_path=None)`: connects to the DB, initializes the schema, then runs, in fixed order: (1) `download_register.download_register` (Cricsheet's player registry), (2) `download_cricsheet.download_all` (the zip files), (3) `ingest.ingest_all` **followed by `ingest.backfill_fielders`** (fielder_1/2/3 backfill for matches ingested before those columns existed — part of the same step 3, not separately numbered), (4) `identity.run` (resolve Cricsheet identifiers to stable player_ids), (5) optionally `scrape_cricinfo.enrich_players` (only if `enrich=True` — described as "best-effort," skipped by default presumably because it's slow/rate-limited), (6) `styles.load_manual_csv` always, plus `styles.seed_from_wikidata`/`enrich_from_wikipedia` only if `seed_styles=True` (each wrapped in its own try/except so a Wikidata/Wikipedia outage doesn't abort the run), (7) `rss_monitor.scan_feeds` if `scan_rss=True` (also try/except-guarded), (8) rankings, overrides, registry, career, **fielding (`fielding.build_fielding`, after career, before cards)**, player cards, (9) advanced profiles, (10) per-opponent/impact/venue/matchups/phases, (11) the three ML feature datasets, (12) win probability. Each step's return value is stored under a matching key in `summary`. At the end, stamps `last_successful_refresh` in the meta table, computes row counts across the major tables into `summary["totals"]`, and logs total elapsed time.
- **Notably absent from every step above:** `wpa.py` (WPA / domestic-form) and `role_finalize.py` (finalized role/keeper flag, external-role merge) are **not** part of `run()` at all — confirmed by this file's own import list (`wpa`/`role_finalize` aren't imported here), unlike every other builder module which is. Both are real, working modules, just only reachable manually via `cli.py`'s `wpa` and `role-finalize` subcommands, not something `refresh run` (or a cron job calling it) will ever trigger on its own. Worth knowing before assuming "refresh ran" means WPA/finalized-role data is current.
- `freshness(conn)`: reads `last_successful_refresh` from meta and classifies staleness into `"never"`/`"ok"`/`"warn"`/`"stale"` based on `SETTINGS.registry_refresh_days` and `SETTINGS.staleness_warn_days` day-count thresholds.

**How it connects:** imports nearly every other module in the package (`advanced`, `career`, `download_cricsheet`, `download_register`, `fielding`, `identity`, `impact`, `ingest`, `matchups`, `ml_features`, `opponents`, `overrides`, `phases`, `player_card`, `rankings`, `registry`, `rss_monitor`, `scrape_cricinfo`, `styles`, `venue_stats`, `winprob`) — notably **not** `wpa` or `role_finalize` (see above) — plus `config.SETTINGS` and `db` (`connect`, `get_meta`, `init_schema`, `set_meta`, `table_count`). It is the top-level entry point called from `cli.py`.

### `data-collection/criiq_data/registry.py`

**Purpose:** Builds the `player_registry` table — the single source of truth for whether a player is currently ACTIVE, INCONSISTENT, INACTIVE, or RETIRED for a given format, plus derived career-phase/age-advisory flags. This drives roster eligibility in downstream selection tooling: a squad-picker should never recommend a genuinely retired or long-inactive player.

**Key pieces:**
- `PHASE_BANDS`: per-role-category `(emerging_end, peak_end, experienced_end)` age boundaries, e.g. batters: <23 emerging, <33 peak, <37 experienced, else declining; pace bowlers have a slightly earlier decline curve (22/30/34) reflecting the generally accepted view that fast bowling careers peak/decline earlier.
- `_category(role, bowling_style)`: classifies a player into `keeper`/`allrounder`/`pace`/`spin`/`batter` by checking role text first (keeper/all-rounder keywords), then falling back to `styles.classify_bowling` on the bowling style string, then a generic "bowl" keyword check, defaulting to `batter`.
- `_career_phase(age, cat)` / `_age_advisory(age, cat)`: bucket age into a phase label using `PHASE_BANDS[cat]`; flag `age_advisory=1` if age exceeds `SETTINGS.age_advisory_pace` (pacers) or `SETTINGS.age_advisory_default` (everyone else) — a lower bar for pace bowlers matching the same "declines earlier" logic.
- `_classify(is_ranked, days_since, selection_rate)`: the core status-decision function, documented step by step: (1) currently ICC-ranked → always `ACTIVE` regardless of anything else; (2) absence longer than `SETTINGS.inactive_window_days` and unranked → `INACTIVE`; (3) within `SETTINGS.active_window_days` → check selection rate: if defined and ≥ `SETTINGS.regular_selection_rate`, `ACTIVE`/`"regular_selection"`; if defined but below that, `INCONSISTENT`/`"in_and_out"` (picked, but not regularly — a genuine in-and-out player, not injured/retired); if `None` (too small a sample to judge), default to `ACTIVE`/`"recent_appearance"` rather than penalize a debutant for lack of selection-rate history; (4) otherwise (aging gap, no rank) → `UNKNOWN`/`"aging_no_rank"`.
- `_status(is_ranked, days_since)`: thin wrapper calling `_classify` with `selection_rate=None`, used by an older/simpler test path.
- `_players_meta(conn)`: `(cricsheet_identifier, gender)` → player row dict, same gender-scoping pattern seen throughout the codebase.
- `build_registry_for_format(conn, fmt)`: the heavy function. Pulls all match-player appearances for the format, maps names to identifiers, computes `opponent` (the other team in each match). Splits appearances into `apps_intl` (international only) for team-selection-window logic, versus the full `apps` (any team_type) for raw recency tracking — the code has an explicit, commented bug-fix note: status must be computed **only** from international appearances, because using the broad set caused a domestic-only player (example cited: "E Bisht") to read as `ACTIVE` despite being internationally inactive. Selection rate is computed within a rolling `SETTINGS.selection_window_days` window: `player_win` = matches the player appeared in during the window; `window_team_matches` = the team's total matches in that window *starting from the player's own first appearance in the window* (via `bisect.bisect_left` on a sorted date list) — this specific detail (comment: "so a mid-window debutant who plays every game reads as regular rather than in-and-out") avoids penalizing a recent debutant for matches that happened before she was even in the squad. Team-date lookups are keyed by `(team, gender)`, not team name alone — another explicitly-documented real bug fix (men's/women's sides sharing a team name like "Nepal" were pooled together, halving selection rates and wrongly flagging regulars as `INCONSISTENT`; the corresponding test is `test_selection_rate_denominator_is_gender_scoped`). `days_since_intl` (international-only recency) drives the actual status label, separate from the broader `days_since` (informational, feeds `last_appearance_date` fields even for domestic-only recency). `recall_flag` — meant to flag a borderline-stale-but-recallable player — is explicitly guarded to never fire for players who are either ICC-ranked or beyond `inactive_window_days`; the code comments cite a real found bug ("RK Parwin", last international appearance 2012, was surfacing with `recall_flag=1` in current squad picks before this guard). Manual `overrides` (from `overrides.py`) take final precedence, overwriting the computed `status`/`activity_signal`/`status_reason` if present. Upserts one row per player into `player_registry`.
- `build_registry(conn)`: per-format loop wrapper.

**How it connects:** imports `config.SETTINGS`, `db.set_meta`, `logging_utils`, `overrides.overrides_map`, `rankings` (`current_rank`, `ranked_ids`), `styles.classify_bowling`. Consumed heavily by `player_card.py` and presumably model-training's roster-eligibility logic. Called by `refresh.py` step 8/12. Very heavily tested — `test_registry_conservative_and_recency`, `test_recall_flag_never_overrides_a_genuinely_inactive_player`, `test_domestic_activity_flagged_without_faking_the_international_status`, `test_registry_flags_inconsistent_selection`, `test_status_and_age_helpers`, `test_classify_selection_consistency`, `test_registry_flags`, `test_selection_rate_denominator_is_gender_scoped`, `test_status_override`.

### `data-collection/criiq_data/role_finalize.py`

**Purpose:** Computes each player's finalized playing role (batter/bowler/all-rounder) plus a wicket-keeper flag, correcting a known blind spot in the purely-statistical `derived_role` column (computed elsewhere from ball counts, which the module docstring says conflates a genuine batting all-rounder with a tail-end specialist bowler who's faced enough balls to look like an all-rounder). Also provides squad-page name-matching utilities used to merge externally-sourced role/keeper data.

**Key pieces:**
- `compute_batting_positions(conn, fmt)`: for every `(match_id, innings)`, determines each player's first appearance order (as striker or non-striker) using the delivery table's natural row order as a proxy for chronological order (`order = deliv.index.to_series()`, then `.min()` per player per innings), ranks players by that order to get `position` (1st, 2nd, ... in the batting order), then returns the median position and innings-batted count per `(identifier, gender)`.
- `_classify(derived_role, position_median)`: if `derived_role == "all-rounder"` but the median batting position is ≥ `TAIL_POSITION_THRESHOLD = 8`, reclassifies as `"bowler"` — the stated rationale being that batting position 8+ (i.e., in most XIs, the tail) is inconsistent with being a genuine batting all-rounder.
- `_role_field_keepers(conn)`: scans `players.role` and `player_styles.playing_role` text for wicket-keeper indicators (`"wicket-keeper"`, `"wicketkeeper"`, `"wk-batsman"`), explicitly excluding "goalkeeper" (noted as a Wikidata mis-tag that would otherwise falsely flag someone a keeper).
- `finalize_local_roles(conn, fmt)`: merges `players` with the computed batting positions — split-gender players merge on `(identifier, gender)`; unsplit players (gender=NULL) merge on identifier alone against a gender-agnostic version of the positions table (`.groupby("identifier").first()`), since they have no gender to match on. Upserts to `player_role_final`, with `is_keeper` merged via `MAX(COALESCE(existing,0), new)` in the SQL — deliberately a one-way ratchet so this "local" pass (based only on internal role-field text) never demotes a keeper flag that a later external-data merge set.
- `finalize_all_local(conn) -> dict`: the per-format loop wrapper around `finalize_local_roles` — this is what `cli.py`'s `role-finalize` subcommand actually calls by default. Stamps `role_finalize_local_built_at` in `meta`.
- `merge_external_roles(conn, records, fmt)`: merges externally-sourced role/keeper records (e.g. scraped from Wikipedia squad pages), matched strictly by `key_cricinfo` — the docstring is explicit that name-based matching is never used here, to avoid silently creating duplicate player identities. Unmatched records are reported in the return value, not dropped or inserted as new rows. `bowling_style` from these records is merged into `player_styles` (never overwriting an existing value, via `COALESCE`) and also backfilled onto `players.bowling_style` directly — the code comments that both columns need the backfill because `advanced.py`'s vs-pace/vs-spin split reads `players.bowling_style` specifically, not `player_styles`.
- `team_candidates(conn, team, gender)`: returns the roster of players who've appeared for a given international team/gender — used to narrow a squad-page name-matching problem from "all ~7000 players" down to a small candidate set.
- `_surname`/`_initials`/`match_full_name_to_cricsheet`: a bespoke name-matching heuristic explaining why: plain fuzzy string matching scores a "First Last" (Wikipedia) name against a "XY Surname" (Cricsheet) name too low to trust, so instead it matches by surname first, then disambiguates multiple same-surname candidates using the leading initial of the "First" name against Cricsheet's initials. Returns both the matched row and a method label (`"surname+initial"`, `"surname_only"`, `"surname+initial_disambiguated"`, or a failure reason) so callers can assign confidence.
- `_map_primary_role` / `_map_bowling_style`: keyword-based text classifiers for squad-page role strings (e.g. "Wicketkeeper batter" → treated as `"batter"` for playing-role purposes, since keeper-ness is tracked as a separate flag, not a primary role).
- `match_squad_to_roster(conn, team, entries, source_url, gender)`: applies `match_full_name_to_cricsheet` across a list of squad-page entries, assigns a numeric `confidence` per match method via `_CONFIDENCE_BY_METHOD` (95/90/75), and returns `records` ready for `merge_external_roles` plus an `unmatched` list for manual follow-up.
- `load_external_roles_csv(path)`: reads a CSV in the exact shape `merge_external_roles` expects.

**How it connects:** imports `config.enabled_sources`, `db.set_meta`, `logging_utils`. `team_candidates` is imported by `matchups.py`'s `bowler_vs_team_batters`. **Not called by `refresh.py`** — confirmed by checking `refresh.py`'s import list, which doesn't include `role_finalize` at all, and no `role_finalize.*` call appears anywhere in `refresh.run()`. `finalize_all_local`/`finalize_local_roles` are only reachable manually via `cli.py`'s `role-finalize` subcommand, and `merge_external_roles` only via whatever external-scrape workflow calls it directly (not part of the automatic `refresh run` pipeline either). Directly tested: `test_map_bowling_style_from_squad_page_role_text`, `test_merge_external_roles_backfills_bowling_style_without_overwriting`, `test_local_pass_promotes_role_field_keepers_and_never_demotes`.

### `data-collection/criiq_data/rss_monitor.py`

**Purpose:** Scans a configured list of cricket-news RSS feeds for retirement-announcement keywords, logging candidate alerts into a `retirement_alerts` table for manual review — a lightweight early-warning signal to catch retirements the ball-by-ball data can't detect on its own (complementing `overrides.py`'s manual entry).

**Key pieces:**
- `_matches_keyword(text)`: lowercases the combined title+summary text and checks it against `RETIREMENT_KEYWORDS` from config, returning the first matching keyword (or `None`).

- `list_alerts(conn, status="PENDING")` / `set_alert_status(conn, alert_id, status)`: simple read/update helpers for a human reviewing the alert queue (presumably surfaced in a CLI or admin UI) to mark alerts as confirmed/dismissed.

Its output presumably feeds a manual-review workflow that ultimately produces entries for `overrides.py`'s CSV, though that connection isn't automated in code shown here.

### `data-collection/criiq_data/scrape_cricinfo.py`

**Purpose:** Best-effort enrichment of player biographical data (date of birth, nationality, role, batting hand) by calling ESPNcricinfo's public athlete API, with local caching to avoid re-fetching the same player repeatedly across runs.

**Key pieces:**
- `_load_cache()` / `_save_cache(cache)`: the cache is a parquet file (`CACHE_DIR/cricinfo/athletes.parquet`) storing `key_cricinfo -> JSON payload` as two columns (`key_cricinfo`, `payload`), read back into a dict by `json.loads`-ing each payload. Load failures are caught and logged, returning an empty cache rather than crashing (cache corruption shouldn't block enrichment).
- `fetch_athlete(key_cricinfo)`: calls the ESPN core API for one athlete ID via the shared `http` module (rate-limited by `SETTINGS.cricinfo_delay_s`), extracting `dateOfBirth` (truncated to the first 10 chars, i.e. `YYYY-MM-DD`), `citizenship`/`nationality`, `position.name` as role, and the first entry of the `style` list's `description` as batting hand. Any exception (network, malformed JSON, missing keys) is caught and logged at debug level, returning `None` — enrichment failures for one player shouldn't be noisy or fatal.
- `enrich_players(conn, limit=None, refetch=False)`: selects players with a non-empty `key_cricinfo`; if `refetch=False` (the default), further restricts to players missing `date_of_birth` OR `role` (i.e. skip players already enriched — incremental by default). For each target, checks the cache first (unless `refetch=True` forces a fresh fetch); on a cache miss, calls `fetch_athlete` and stores the result in-memory (persisted at the end via `_save_cache`). Only issues a DB `UPDATE` if `any(meta.values())` (i.e. the fetch actually returned something useful), using `COALESCE(?, existing)` so a `None` field never overwrites a previously-known value.

**How it connects:** imports the shared `http` module, `config` (`CACHE_DIR`, `SETTINGS`), `logging_utils`. Called by `refresh.py` step 5/12, but only when `enrich=True` is explicitly passed (off by default, presumably because it's slow / makes many external HTTP calls).

### `data-collection/criiq_data/sheet.py`

**Purpose:** Assembles a human-readable "scouting sheet" for a player — a richer, narrative-flavored view than `player_card.py`'s structured JSON, combining career stats, impact, strengths, phase breakdowns, matchups, and a bullet-point `selector_summary` meant to read like a quick coach's briefing.

**Key pieces:**
- `find_player(conn, like)`: fuzzy-ish lookup by SQL `LIKE` pattern on canonical name, returning whichever matching player has the most matches played (a disambiguation heuristic when a name pattern matches multiple people — presumably picks the most prominent/likely one).

### `data-collection/criiq_data/stats.py`

**Purpose:** The single shared function, `build_innings`, that reconstructs a "one row per player per match" batting+bowling summary from raw deliveries — this is the foundational aggregate that `opponents.py`, `phases.py`, `venue_stats.py`, `player_card.py`, and `ml_features.py` all build on top of, rather than each re-deriving it from scratch.

**Key pieces:**
- `build_innings(conn, fmt, team_type="international")`: pulls all deliveries for the format (filtered by `team_type` unless `None` is passed for "all matches" — the docstring flags that `wpa.py`'s domestic-form aggregate specifically needs `team_type='club'`, and warns against blending the two). `legal` excludes wides; `legal_bowl` further excludes no-balls. Batting aggregate (`bat`): groups by `(match_id, striker)` for `runs` (sum of `runs_off_bat`) and `balls_faced` (sum of `legal`). Dismissals (`outs`): deduplicated `(match_id, player_dismissed)` pairs flagged `out=1` — deduplication matters because a player is either out or not in a given match, not counted multiple times even if multiple delivery rows somehow reference the same dismissal. Bowling aggregate (`bw`): computes `_bb` (legal ball bowled), `_rc` (runs conceded — bat runs + wides + no-balls, i.e. everything except byes/leg-byes, which the comment on `_dot` clarifies are deliberately excluded from "runs conceded" credit), `_wk` (wicket credited to bowler per `BOWLER_WICKETS`), `_dot` (legal ball, zero total runs — the code comment notes wides/no-balls already concede a run so they're excluded automatically; this schema has no separate byes/leg-byes column at all, so there's no third case to call out), `_bdry` (legal ball where the batter hit 4 or 6 off the bat) — then groups by `(match_id, bowler)` summing each. Batting and bowling aggregates are outer-merged on `(match_id, player_name)` (a player can appear in one, both, or as a name with no delivery involvement at all if she was in the XI but didn't bat/bowl — handled by the subsequent merge with `match_players`), then `outs` is left-merged in, and all numeric columns are `fillna(0)`. Team/opponent/win context comes from merging `match_players` (team) and `matches` (date/gender/team1/team2/winner/venue_id); `opponent` and `won` are computed the same way seen in several other modules (`team2 if team==team1 else team1`; `won = team == winner`). Finally merges through `identifier_map` to attach the Cricsheet `identifier`, dropping unresolvable names, and does a final `groupby(["identifier", "match_id"])` aggregate (collapsing any residual duplicate name variants within one identifier/match) using `"first"` for context columns and sums for stat columns, returning one row per `(identifier, match_id)`.

**How it connects:** imports `h2h.BOWLER_WICKETS`, `logging_utils`. This is consumed by `matchups.py` (indirectly, no — actually matchups queries deliveries directly), but directly by `opponents.py`, `phases.py`, `player_card.py`, `venue_stats.py`, and `ml_features.build_player_match_impact_for_format`. It has no direct tests of its own in `test_pipeline.py`, but is exercised transitively by every test that calls one of its callers (e.g. `test_vs_opponent_record`, `test_player_card_contents`, `test_venue_record`).

### `data-collection/criiq_data/styles.py`

**Purpose:** Manages player "style" metadata — bowling type (pace/spin, and a finer classification), batting hand (left/right) — sourced from three places in priority-agnostic-but-never-overwriting order: a manual CSV, Wikidata SPARQL queries, and Wikipedia infobox scraping. This metadata feeds role classification (`registry.py`), matchup analysis (`advanced.py`'s vs-pace/vs-spin splits), and player card display.

**Key pieces:**
- `classify_bowling(style)`: keyword-matches a raw bowling-style string against `_SPIN` (off break, offbreak, leg break, legbreak, orthodox, spin, googly, chinaman, slow, wrist, finger) and `_PACE` (fast, medium, seam, pace, swing) tuples, checking spin keywords first — so an ambiguous string mentioning both would resolve to spin. Returns `None` if neither matches.
- `classify_bowling_detail(style)`: a finer classifier used for batter-matchup purposes (the docstring explains the type of turn matters — off-spin turns into a right-hander, leg-spin away, etc.): detects left-arm indicators, then classifies off-spin (contains "off" + "break"/"spin"), leg-spin (contains "leg"+"break"/"spin", or "googly"/"wrist"/"chinaman"), slow-left-arm (left-arm + orthodox/slow/spin), falling back to the coarse pace/spin classification if none of the finer patterns match.
- `classify_hand(hand)`: simple left/right keyword match returning `"LHB"`/`"RHB"`.
- `_sparql(query)`: fires a SPARQL query at Wikidata's endpoint via the shared `http` module with a 1.5s delay (rate limiting) and 60s timeout.
- `is_cricket_role(role_text) -> bool`: guards against Wikidata's `P413` ("position played on team / speciality") being cross-sport — a real, seen problem where a cricketer's linked Wikidata entity carried a role from an unrelated sport. Lowercases and checks for any of `_CRICKET_ROLE_KEYWORDS`; `False`/no match means "don't trust this value."
- `seed_from_wikidata(conn, chunk=150, limit=None)`: finds players with a `key_cricinfo` who are missing `date_of_birth`/`role`/`nationality`, batches them (default 150 per SPARQL query, since Wikidata SPARQL has query-size limits), and runs a SPARQL query mapping ESPNcricinfo IDs (Wikidata property P2697) to date of birth (P569), role (P413), and nationality (P27) via `VALUES` clause + `SERVICE wikibase:label`. Any role that fails `is_cricket_role` is dropped (logged, set to `None`) before it's ever written anywhere, specifically because P413 isn't cricket-specific. Updates `players` with `COALESCE(existing, new)` (never overwrites) and also writes the (validated) `playing_role` into `player_styles`.
- `_clean_wiki(v)`: a small regex pipeline for cleaning raw MediaWiki markup extracted from an infobox field: truncates at the first `<br`/`<ref` tag (keeps only the first listed value when a field has multiple, e.g. multiple bowling styles), converts `[[link|display]]`/`[[link]]` wikilinks to their display text, strips `{{template}}` markup, truncates at the next `|` (stopping at the next infobox parameter boundary), strips remaining HTML tags, and removes bold/italic quote markup.
- `_infobox_field(text, field)`: regex-extracts a named infobox parameter's raw value and cleans it via `_clean_wiki`.
- `_wiki_titles(cricinfo_ids)`: SPARQL query mapping ESPNcricinfo IDs to their English Wikipedia article title, via Wikidata's `schema:about`/`schema:isPartOf` sitelink properties.
- `_wiki_pages(titles)` / `_resolve_title(...)`: fetches raw wikitext for a batch of titles via the MediaWiki API's `revisions`/`rvprop=content` endpoint, handling title normalization and redirects (Wikipedia titles can differ from what was requested due to capitalization normalization or redirect pages) via the API's own `normalized`/`redirects` response metadata.
- `enrich_from_wikipedia(conn, limit=None, chunk=40)`: finds players missing `bowling_style` or `batting_hand`, resolves their Wikipedia titles via `_wiki_titles`, fetches page content in batches of 40, extracts `batting`/`bowling` infobox fields, validates the batting field actually parses to a real hand via `classify_hand` before accepting it (guards against junk infobox text), and updates both `players` and `player_styles` with `COALESCE`-style non-overwriting merges.
- `scaffold_csv`, `load_manual_csv`: same CSV template/load pattern as `overrides.py`/`rankings.py`; `load_manual_csv`'s upsert uses `COALESCE(excluded.X, player_styles.X)` — meaning a **manual CSV value always wins** over whatever was there before, in contrast to the Wikidata/Wikipedia paths which never overwrite. This is the one place manual data is allowed to clobber existing values, consistent with manual CSVs being treated as authoritative overrides elsewhere in the codebase (`overrides.py`).
- `bowler_buckets`, `batter_hands`: build `(player_name, gender) -> bucket/hand` lookup dicts (used by `advanced.py` for matchup splits), gender-keyed for the same identifier-collision reason documented throughout.
- `coverage(conn)`: a simple diagnostic — total player count vs. how many have each style field populated.

**How it connects:** imports the shared `http` module, `config` (`MANUAL_STYLES_CSV`, `STYLES_DIR`, `WIKIDATA_SPARQL`), `logging_utils`. `classify_bowling`/`classify_hand`/`classify_bowling_detail` are imported by `registry.py`, `player_card.py`, `advanced.py`. Called by `refresh.py` step 6/12. Tested by `test_styles_classifiers`, `test_styles_bowling_detail`, `test_wikipedia_infobox_parse`.

### `data-collection/criiq_data/validate.py`

**Purpose:** Validates raw delivery rows straight out of a Cricsheet CSV before they're allowed into the database, splitting each match's rows into "clean" (insertable) and "rejected" (quarantined for later inspection) — a data-quality gate sitting between `ingest.py`'s CSV read and its DB insert.

**Key pieces:**
- `DELIVERY_REQUIRED`: the list of columns a delivery CSV must have at all (`match_id`, `innings`, `ball`, `batting_team`, `bowling_team`, `striker`, `non_striker`, `bowler`, `runs_off_bat`, `extras`) — note this doesn't include `wides`/`noballs`/`wicket_type`/`player_dismissed`, which are optional/sparse columns handled elsewhere with defaults.
- `validate_deliveries(df, match_id)`: if any required column is entirely absent from the dataframe, the whole file is rejected (returns an empty "clean" slice and the entire dataframe as "rejected", tagged with the missing-columns reason) — a whole-file failure, not a row-by-row one, since a structurally broken CSV can't be salvaged row by row. Otherwise, builds a per-row `reasons` string Series (empty string = no problem): coerces `runs_off_bat`/`extras`/`innings` to numeric via `pd.to_numeric(errors="coerce")`, flagging rows where coercion produced NaN as `"non-numeric <col>"` (and — notably — only the *first* reason found for a row is kept, via the `reasons == ""` guard, so a row with multiple problems just reports the first one detected); flags rows where any of `striker`/`non_striker`/`bowler`/`batting_team`/`bowling_team` is null or blank-after-strip as `"null <col>"`. Rows with any non-empty reason go to `rejected` (tagged with `_reject_reason` and `_match_id`); everything else is `clean`.
- `quarantine(rejected, tag)`: writes the rejected rows to a timestamped CSV under `QUARANTINE_DIR` (returns `None` if there's nothing to quarantine) for manual review, logging a warning with the row count.

**How it connects:** imports `config.QUARANTINE_DIR`, `logging_utils`. Called directly by `ingest.py`'s `ingest_source` for every match file. Tested by `test_validate_deliveries_rejects_bad_rows`.

### `data-collection/criiq_data/winprob.py`

**Purpose:** Trains and serves an *empirical* (frequency-based, not a parametric model) ball-by-ball win-probability estimator for T20 cricket — "given the current game state, what's the historical win rate of teams in a similar state?" — fit and persisted separately for each `(format, gender)` pair since the module docstring notes men's and women's T20 scoring distributions differ enough that a shared model would be miscalibrated for both.

**Key pieces:**
- `_chase_keys(df)` / `_set_keys(df)`: discretize continuous game state into small integer bins for the empirical lookup table. Chasing state: `k_rem` (balls remaining, binned by 6 = one over), `k_wk` (wickets, capped at 10), `k_rr` (runs required, binned by 5, capped at index 30 to avoid a combinatorial explosion of near-impossible chase states). Setting (first-innings) state: `k_bowled` (balls bowled so far, binned by 6), `k_wk`, `k_score` (binned by 10). Chase and set use structurally different keys because the target/runs-required only exists once chasing.
- `EmpiricalWinProb` class: 
  - `_shrunk(keys, y, cols, prior)`: for each unique combination of `cols`, computes `(sum_of_wins + alpha*prior) / (count + alpha)` — this is Bayesian/Laplace-style shrinkage toward the innings-wide prior win rate, so a bin with very few observed balls doesn't report an extreme (e.g. 100% or 0%) win rate just from noise; `alpha` (`SETTINGS.winprob_shrinkage`) controls how strongly sparse bins get pulled toward the prior.
  - `fit(balls)`: drops unlabeled rows (matches with no clear winner), computes separate priors for chase (`prior_chase`) and set (`prior_set`) innings. Fits four grids: `chase_full` (3-key: rem/wk/rr), `chase_coarse` (2-key: rem/wk, dropping the runs-required dimension), `set_full` (3-key: bowled/wk/score), `set_coarse` (2-key: bowled/wk) — the "coarse" grids exist as a fallback for game states unseen in the full grid (see `_lookup`).
  - `_lookup(keys, full, coarse, full_cols, coarse_cols, prior)`: left-merges the query keys against the fine-grained (`full`) grid first; wherever that produces no match (`NaN`), falls back to merging just the missing rows against the coarser grid; any state still unmatched after both levels falls back to the innings-wide `prior`. This three-tier backoff (specific → coarse → prior) is the mechanism that lets the model generalize to rare or unseen game states without ever returning `NaN`.
  - `predict(states)`: splits the input rows into chasing vs. setting based on `innings`, applies the corresponding key function and lookup, and reassembles results in the original row order (important since callers expect batch-predict order preservation, verified explicitly in `test_winprob_empirical_learns_and_calibrates`).
  - `save(fmt, gender)` / `load(fmt, gender)`: persists each grid as its own parquet file plus a small JSON metadata file (`alpha`, `prior_chase`, `prior_set`) — files are named per `(fmt, gender)` so genders never share a model.
- `_brier(p, y)` / `_logloss(p, y)`: standard probability-calibration metrics (mean squared error and log loss), with `logloss` clipping predictions away from exactly 0/1 to avoid `log(0)`.
- `_test_mask(match_ids)`: a deterministic (not random-seeded) train/test split — hashes each match_id with `zlib.crc32` and buckets it into 0-99 based on the hash, assigning to test if below `SETTINGS.winprob_test_fraction*100`. The comment explains this splits **by match, not by ball**, specifically to avoid leakage between balls of the same match (which are highly correlated) landing on both sides of the split.
- `_fit_and_score_one_gender(balls, fmt, gender)`: fits a model on the training split, evaluates Brier/log-loss against the held-out test split (compared against a trivial "always predict the innings prior" baseline, so the eval report shows whether the model actually beats a naive baseline), then re-fits a *final* model on all labelled data for that gender (train+test combined) and persists that as the production model — a common pattern of "evaluate on held-out, but ship trained-on-everything."
- `build_for_format(conn, fmt)`: reads the `ball_state_<fmt>.parquet` file built by `ml_features.py` (skips if it doesn't exist, logging that `ml` needs to run first), splits by `gender` and calls `_fit_and_score_one_gender` per gender, concatenates the scored output, adds a `ball_seq` (cumulative count within `(match_id, innings)`) column, and writes the final scored parquet to `win_prob_<fmt>.parquet`.
- `probability_for_state(...)`: an ad-hoc single-state query function — loads the persisted model and predicts on a one-row dataframe built from the given keyword arguments.
- `match_timeline(fmt, match_id)`: reads back the scored parquet, filters to one match, and for each `(innings, over)` keeps only the last ball's state (i.e. the over's closing win probability) — producing an over-by-over timeline suitable for a win-probability chart.

**How it connects:** imports `config` (`FEATURES_DIR`, `MODELS_DIR`, `SETTINGS`, `enabled_sources`), `db.set_meta`, `logging_utils`. Consumes `ml_features.py`'s `ball_state_<fmt>.parquet` output. `wpa.py` imports `EmpiricalWinProb` directly to compute win-probability swings per ball. Called by `refresh.py` step 12/12 (the last step, since it depends on `ml_features` having already run). Tested by `test_winprob_empirical_learns_and_calibrates` and `test_winprob_save_load_roundtrip`.

### `data-collection/criiq_data/wpa.py`

**Purpose:** Computes Win-Probability-Added (WPA) — crediting individual players with how much their specific actions (runs scored, wickets taken) actually shifted the win probability computed by `winprob.py`, rather than just tallying raw runs/wickets. This is a more predictive-value-aware alternative to simple contribution-share metrics, broken down per match, per career-phase, and separately for domestic form.

**Key pieces:**
- `_phase(over)`: the same powerplay/middle/death bucketing as `phases.py`/`ml_features.py`.
- `_build_ball_state_with_players(conn, fmt)`: rebuilds cumulative ball-by-ball state (score, wickets, balls bowled/remaining, target/runs-required while chasing) — deliberately *not* reused from `ml_features.build_ball_state_for_format`, which the module docstring says is kept player-agnostic (pure training data). This version keeps `striker`/`non_striker`/`bowler` columns so WPA can be attributed to individuals. Crucially, it includes **all `team_type`s** (not just international), because the docstring explains domestic matches are scored using the same internationally-trained win-probability model, not excluded from scoring.
- `_win_prob_inputs(d)`: selects just the columns `EmpiricalWinProb.predict` needs (`innings`, `wickets`, `balls_remaining`, `runs_required`, `balls_bowled`, `score`).
- `_starting_state_wp(model, d)`: computes P(win) at the very start of each `(match_id, innings)` (0 runs, 0 wickets, full balls remaining) — needed as the "previous" probability for the first ball of every innings, since there's no prior ball to diff against.
- `_score_one_gender_ball_wpa(d, model)`: scores every ball's win probability, then computes `prev_wp` as the previous ball's probability within the same `(match_id, innings)` group via `.shift(1)`; for the first ball of each innings (where `shift` produces NaN), fills in the innings-start probability from `_starting_state_wp`. `delta_wp = win_prob_batting - prev_wp` is the per-ball WPA swing.
- `compute_ball_wpa(conn, fmt)`: the shared building block — rebuilds ball state, then scores each gender's balls using *that gender's own* persisted `EmpiricalWinProb` model (loaded via `EmpiricalWinProb.load(fmt, gender)`), concatenating results — mirroring `winprob.py`'s never-mix-genders policy.
- `_name_to_ident` / `_resolve_ids_by_name`: maps player names to Cricsheet identifiers then to gender-aware resolved `player_id`s via `identity.resolve_player_ids`, again citing the identifier-collision issue as the reason gender must be threaded through.
- `build_wpa_for_format(conn, fmt)`: the main assembly. Attribution rule (stated in the module docstring): the striker on a ball is credited `delta_wp` on a "batting" axis; the bowler is credited `-delta_wp` on a "bowling" axis (since a ball good for the batting team is, by construction, bad for the bowling team — complementary probabilities); the non-striker gets nothing, which the docstring notes is "standard WPA convention." Builds two event tables (`bat_events`, `bowl_events`) and concatenates them into one `events` table tagged with an `axis` column. From `events`, it computes: (a) `player_match_wpa` — per `(match_id, player_id)`, summed `batting`/`bowling` WPA via `.groupby(...).unstack()` (pivoting the axis dimension into columns), joined with team/opponent/date/team_type context, plus a `phase_breakdown_json` blob (nested `{phase: {axis: wpa}}` dict) for detailed per-phase inspection; (b) `player_phase_wpa` — a career-level aggregate, but explicitly filtered to `team_type == "international"` only (mirroring how `player_career`/`player_impact` are international-only elsewhere), computing `batting_wpa_per_match`/`bowling_wpa_per_match` as the mean per phase across all her international matches. Both tables are upserted via `ON CONFLICT`.
- `build_domestic_form_for_format(conn, fmt)`: a separate, deliberately domestic-only aggregate reading back from the already-computed `player_match_wpa` table (not raw deliveries) filtered to `team_type='club'`, taking the most recent `SETTINGS.impact_recent_matches` matches per player and averaging their batting/bowling WPA — surfacing "how has she been doing domestically lately" without polluting the international-only career tables.
- `build_wpa(conn)`: per-format loop calling both `build_wpa_for_format` and `build_domestic_form_for_format`.

**How it connects:** imports `config.SETTINGS`/`enabled_sources`, `db.set_meta`, `identity.resolve_player_ids`, `logging_utils`, `ml_features.T20_BALLS`, `winprob.EmpiricalWinProb`. **Not called by `refresh.py` at all** — confirmed by checking `refresh.py`'s import list, `wpa` isn't among them, and nothing in `refresh.run()` calls `build_wpa`/`build_wpa_for_format`/`build_domestic_form_for_format`. This module is only reachable via `cli.py`'s `wpa` subcommand (`cmd_wpa`), run manually and on demand — not part of the automatic pipeline the way `winprob`/`fielding`/`career` etc. are. Tested extensively: `test_wpa_credits_striker_and_debits_bowler` (verifies the exact sign convention: striker's batting_wpa should be negative when a wicket swings probability down, bowler's bowling_wpa should be the exact positive mirror) and `test_domestic_matches_tagged_and_kept_out_of_international_phase_wpa` (verifies domestic matches get `team_type='club'`, are correctly WPA-scored, but never leak into the international-only `player_phase_wpa` aggregate, while still being correctly picked up by `player_domestic_form`).

### `data-collection/tests/test_pipeline.py`

**Purpose:** The integration test suite for the entire data-collection pipeline, using an in-memory/temp-file SQLite schema and small hand-built fixtures (two matches, `M1` and `M2`, with a handful of deliveries) to exercise nearly every builder module end-to-end against known, hand-computable expected outputs — rather than mocking each module in isolation.

**Key pieces (fixtures):**
- `_add_match`, `_add_player_meta`, `_add_match_player`, `_ball`: small helper functions for hand-inserting rows into `matches`, `identifier_map`/`people`, `match_players`, `deliveries` respectively, without going through the real ingest pipeline — used by most tests to build precise, minimal scenarios.
- `_cricsheet_zip(matches)`: constructs a real-shaped in-memory Cricsheet csv2-format zip (info CSV + delivery CSV per match) so that tests exercising `ingest.ingest_source` go through the actual file-format parsing path, not a shortcut.
- `conn` fixture: builds a shared two-match scenario (`M1`: 2024-01-01, Team A vs Team B, AA Batter scores 7 off 5 balls then is bowled; `M2`: 2025-06-01, AA Batter scores 13 off 4 balls not out) used by most of the read-side tests below, then calls `identity.resolve_players(c)` to populate `players` from the raw identifier/name data.

**What each test actually verifies:**
- `test_player_id_stable`: `identity.player_id_for` is a pure, deterministic function of the Cricsheet identifier — same input always yields the same ID, different inputs yield different IDs (i.e., it's a stable hash/derivation, not random).
- `test_identity_join_attaches_cricinfo` / `test_identity_missing_cricinfo_flagged`: confirms identity resolution correctly attaches a `key_cricinfo` when the registry provides one (and marks `needs_review=0`, `resolution_method="register"`), and correctly flags `needs_review=1` with a null `key_cricinfo` when no registry entry exists.
- `test_derived_role`: confirms a player who only ever bats gets `derived_role == "batter"`.
- `test_h2h_batter_vs_bowler`: verifies `h2h.batter_vs_bowler` correctly aggregates the AA-Batter-vs-BB-Bowler matchup across both matches (10 total legal balls faced from BB Bowler, 20 runs, 1 dismissal, 10% dismissal rate) — confirming ball/run/dismissal counting is exactly right at a hand-verifiable scale.
- `test_registry_conservative_and_recency`: confirms a recently-appeared player (`M2`, 2025-06-01) reads `ACTIVE` with `recall_flag=0`, while a player whose last appearance was only in the older `M1` reads `recall_flag=1` — validating the recency-based classification logic actually distinguishes the two.
- `test_recall_flag_never_overrides_a_genuinely_inactive_player`: a regression test for a documented past bug — confirms a player whose only appearance was in 2012 (long past `inactive_window_days`) is `INACTIVE` with `recall_flag=0`, not incorrectly flagged recallable.
- `test_domestic_activity_flagged_without_faking_the_international_status`: verifies the international/domestic separation in `registry.py` — a player with an old international appearance but a recent domestic one shows `retirement_status="INACTIVE"` (an honest international-only fact) alongside `recent_domestic_activity=1` (a separate carve-out signal), while `days_since_last_appearance` reflects the more recent domestic date — confirming the two concerns (status label vs. informational recency) stay properly decoupled.
- `test_winprob_empirical_learns_and_calibrates`: fits `EmpiricalWinProb` on synthetic chase data engineered so "gettable" asks (rem//2) always win and "hopeless" asks (rem*2) always lose, then confirms the model correctly predicts a higher win probability for the easy state than the hard one (`p_hard < 0.5 < p_easy`), and separately confirms batch prediction preserves row order/count.
- `test_winprob_save_load_roundtrip`: confirms a fitted model's `save`/`load` cycle produces identical predictions before and after persistence.
- `test_wpa_credits_striker_and_debits_bowler`: injects a hand-crafted win-probability grid (0.55 → 0.45 only on the wicket ball) and confirms the resulting `batting_wpa` for the striker is exactly -0.10 and the bowler's `bowling_wpa` is exactly +0.10 — directly verifying the sign convention and exact-value attribution described in `wpa.py`'s docstring.
- `test_domestic_matches_tagged_and_kept_out_of_international_phase_wpa`: adds a domestic match for the same batter and confirms it's tagged `team_type='club'`, correctly WPA-scored on its own, but the international-only `player_phase_wpa` aggregate still shows only 2 matches (not 3) — while `player_domestic_form` correctly picks up exactly the 1 domestic match.
- `test_registry_flags_inconsistent_selection`: builds a 10-match season where one player appears in all 10 (confirmed `ACTIVE`/`regular_selection`, `selection_rate=1.0`) and another in only 2 (confirmed `INCONSISTENT`/`in_and_out`, `selection_rate=0.2`) — validating the selection-rate-based distinction between a regular and an in-and-out player.
- `test_player_card_contents`: end-to-end check of `player_card.build_cards_for_format`/`get_card` — confirms the latest match's date/runs/not-out flag, the form sparkline (`[7, 13]`), the RFI computed with the exact expected weighted-average formula, impact metrics being in sensible ranges, and the match-summary team totals/winner being correctly attached.
- `test_vs_opponent_record`: confirms `opponents.build_vs_opponent_for_format` correctly aggregates across both matches (2 matches, 2 wins, 100% win rate, 20 runs, average 20, strike rate 200, high score 13, 1 dismissal) against "Team B".
- `test_impact_metrics` / `test_importance_score_batting_bonus_symmetric_with_bowling`: verifies `impact.py`'s contribution/importance-score computations, including a detailed hand-built scenario proving the batting bonus and bowling bonus (split into wicket-rate and economy sub-parts) are symmetric (both cap at 15.0 when performance is maximal), and that the overall `importance_score` correctly clamps at 100.0 when the raw sum would exceed it.
- `test_ingest_tags_team_type_and_keeps_within_cutoff_data_in_production` / `test_ingest_routes_matches_after_data_cutoff_to_holdout_tables`: builds real Cricsheet-shaped zips and confirms `ingest.ingest_source` correctly tags `team_type` from the info CSV, and — critically — that matches dated after `SETTINGS.data_cutoff_date` are routed entirely into the `*_holdout` tables (matches, deliveries, match_players) instead of production tables, and that re-running ingest against the same zip doesn't duplicate the holdout rows (validating `_existing_match_ids`'s union-of-both-tables logic).
